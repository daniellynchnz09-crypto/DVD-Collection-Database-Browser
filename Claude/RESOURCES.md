**TV field semantics refined 2026-09-18** (ahead of building TV scanning support - see Claude/TECH STACK AND ARCHITECTURE/barcode-review-screen-fields.md's TV Scanning section for the full design and the real-data audit behind these decisions): auditing the live collection's `season_no` found several genuine, recurring conventions beyond this original spec, now resolved with the user and formalized in `packages/shared/src/titleParsing.ts`'s `SEASON_NO_ALIASES`/`normalizeSeasonNo`:
- The original spec's "various" (episodes from multiple seasons at random on one disc, e.g. a cartoon compilation) is renamed **"Assorted"** going forward - the user prefers this wording. Existing "various" rows were migrated.
- **"All"** - a new, distinct value for a disc/box-set containing every season the show has (a complete-series collection), as opposed to a genuinely random cross-season mix. Kept as its own literal value rather than an explicit season list.
- **"Specials"** - a new, distinct value for unnumbered special episodes not tied to any numbered season at all (e.g. clip-show specials) - not the same as "Assorted" (a random mix of regular, numbered-season episodes).
- Multiple specific seasons are listed comma-separated (e.g. "2,4"), same as the original spec - ad hoc phrasing like "2 and 4" or "6-7" found in the live data was normalized to this format. The bare word "Multiple"/"multiple" (which doesn't say which seasons at all) isn't auto-normalized - it needs the title's own wording read for context.
- **Recognized exception**: an old syndicated-TV box set sold as numbered volumes/discs that don't respect season boundaries (e.g. a 79-disc Star Trek: The Original Series set) may use `part_of_season_no` to mean "this disc's volume number in the set" rather than "part of *a* season" - `season_no` on such a disc reflects whichever season(s) that particular volume's episodes actually belong to (and can itself be a comma-list, if a volume spans a season boundary). This is a deliberate, documented exception for this kind of release, not the general rule.

**Running Time for TV**: refined 2026-09-18 (same day, follow-up) after the user reviewed a full audit of every TV-typed row with a runtime already set (the "TV Runtime Review" artifact) and gave a per-category ruling, rather than one blanket rule:
- **TV Series** - n/a by default. A real value is the exception, only for a disc genuinely bounded enough to function like one "watch it in one sitting" program rather than a variable, open-ended run of a season's episodes - confirmed case-by-case (e.g. `Batman and Robin`, `Flash Gordon Conquers the Universe`, `Zorro Rides Again` keep a real total precisely because they're classic serials, not ordinary seasons - see the SERIALS note below).
- **TV Mini-Series** - real value is the norm, decided per-title rather than always-on: the user reviewed every Mini-Series row with a runtime and kept nearly all of them, dropping only two whose per-disc runtime didn't hold up on reflection (`The Day of the Triffids`, `The Nazis: A Warning from History`) plus a themed set of five (`The Agatha Christie Hour: ...`) where the per-episode-pair packaging didn't warrant one either. Not a fixed rule either way - ask/decide per title as new ones come in, same as these were.
- **TV Movie** - always keeps a real runtime, same as an ordinary Movie. No exceptions.
- **TV Special** - always keeps a real runtime, same treatment as TV Movie, going forward.
- **TV Episode** - always keeps a real runtime, same treatment as TV Movie/TV Special, going forward.
- Movies always keep a real running time regardless of format/collection status (unchanged).

**SERIALS** (rule given 2026-09-18, same day, follow-up): `Zorro Rides Again`/`Zorro Rides Again Episodes 7-12`, `Batman and Robin`, `Dick Tracy`, and `Flash Gordon Conquers the Universe` were flagged by the user as looking like classic theatrical serials (Republic/Columbia/Universal chapter-plays from the 1930s-40s), not ordinary TV seasons - confirmed via live OMDb lookups before anything was changed: all four are real serials, and three (`Batman and Robin`: 263 min/15 episodes, `Flash Gordon Conquers the Universe`: 195 min/12 episodes, `Zorro Rides Again`: OMDb's own total 212 min) already stored OMDb's own full-serial runtime total exactly.

A serial gets its own `movie_or_tv` value, **"Serial"** - not a subtype of TV Series/TV Movie. Rules:
- **`season_no` is always "1"** - a serial doesn't have multiple seasons.
- **`episode_count`** is counted the same way TV Series counts it - the number of episodes/chapters on this specific disc, not the serial's real total chapter count if the disc only holds part of it.
- **Always keeps a real `running_time_mins`**, unlike TV Series (which defaults to n/a) - the reasoning being that online databases (OMDb included) present a serial in "movie" shape with no episode breakdown of its own, and a serial's story definitively concludes across its chapters rather than running open-ended the way an ordinary TV show can.
- OMDb's own `Type` for a serial's imdbID is "movie" (confirmed against all four) - identical to an ordinary Movie, so auto-detection can never guess "Serial" on its own the way it can guess "TV Series"/"TV Episode" from OMDb's Type. The Confirm screen's Movie/TV field being always-editable (not hidden-until-no-match) already covers this - the user just picks it manually, same as TV Movie already has to be.
- **Deferred, rare complexity** (the user's own words): a serial can sometimes be nested inside a TV show - a season containing multiple serials, or a serial spanning multiple episodes within a season - most notably with Doctor Who, "a very complicated beast with multiple shows, series, serials, specials, and episodes all being part of the same continuity and entangling with one another." The user tends to ignore this nested case when it comes up and will give more specific logic for it later if it's ever actually needed - not built or designed yet.

**Two real bugs found and fixed while applying this rule** (both worth remembering for future free-text-field work):
1. `MOVIE_OR_TV_ALIASES` (`packages/shared/src/titleParsing.ts`) used to fold `"tv serial"` into `"TV Series"` - the user had *already* typed "TV Serial" in the Sheet for `Dick Tracy` and the two `Zorro Rides Again` rows, and every single sync was silently collapsing that distinction away without them ever knowing. Fixed: `"tv serial"`/`"serial tv"`/`"tv-serial"`/`"serial"`/`"serials"` all now map to `"Serial"`.
2. The first reclassification pass matched rows by title text (`"Batman and Robin"`, `"Dick Tracy"`) and wrongly caught two *unrelated* films that happen to share those exact titles - the 1997 Joel Schumacher `Batman and Robin` feature (tt0118688) and the 1945 RKO `Dick Tracy` feature (tt0037642), both briefly mislabeled "Serial"/season_no "1" before being caught (by checking for exactly this - DEFINITIONS.md's own "Remakes" note already warns two same-named titles aren't necessarily related) and reverted by `unique_id`, never title text. Every other title-text edit made in this same session was individually re-checked afterward for the same collision risk and came back clean - **lesson for any future batch edit targeting titles by name: check for a same-titled-but-unrelated row first, and prefer matching by `unique_id` once real candidates are identified, exactly like the Star Trek TOS volume-numbering exception above already does.**

`Dick Tracy` (1937, tt0028785)'s `episode_count` is still unset - unlike the other three serials, this disc has no season/episode data at all, just a single 70-minute entry matching OMDb's own Runtime exactly, suggesting it may be a condensed "feature" re-edit rather than a full multi-chapter set - needs the user to check the physical case/disc for the real chapter count before this can be filled in confidently.

**Director for TV**: for a TV entry that represents a specific single serial/episode (the classic-show convention - one row per serial, each with its own real director), the Director field keeps meaning exactly what it says. For a whole-season/show-level TV entry, the field is understood to hold the show's creator/head-writer instead, since creative authorship in ongoing TV is driven by them rather than by individual episode directors.

**Release Date for TV**: always the release date of the first episode of the first season of the show, even when the specific title/row being catalogued is for a later season or part - never the premiere date of that particular season. (Noted by the user as the current approach, subject to revisiting if a reliable per-season air-date source becomes available - TMDb's per-season endpoint is a candidate for this later.)

**IMDb page for TV**: always links to the show's own overall IMDb page, never a specific season - IMDb doesn't have separate pages per season, only per series and per episode, so a match against a specific episode needs to be resolved back to its parent series' id first.

IMDB/OMDB:
IMDB is biggest movie database on the internet and should contain all the possible details that the program might need about a movie (but not necessarily about it's physical media release) this information would be most important for web app specifically given the design that I plan to implement for it. However one of the drawbacks of IMDB is that it does not have a public API so it can't be scraped as easily. OMDB is a very similar Database to IMDB except for it doesn't quite have as much information, but it does have a public API which should make it easier to wield for this application. I would prioritize OMDB first due to ease, however if the details are not available there, I would instead grab the information from IMDB.
