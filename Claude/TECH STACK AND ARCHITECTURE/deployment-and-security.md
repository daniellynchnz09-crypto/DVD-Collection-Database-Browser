**PUBLIC VS PRIVATE BUILD PIPELINE**

The private repo/project is the actual working codebase. A script in scripts/ generates the sanitized public repo before each GitHub push described in Claude.md:
- Points environment config at the public Supabase project instead of the private one.
- Excludes any Letterboxd integration code (Claude.md: the public build disincludes potential Letterboxd features).
- Confirms taste-profile names in the public dataset are placeholders, not real names.

This keeps the "public build = subset + anonymized" rule enforced by tooling rather than by memory.



**HOSTING / KEEP-ALIVE**

Both Supabase projects are on the free tier, which auto-pauses a project after 7 days with no activity (confirmed by an actual pause-warning email Supabase sent for the public project in September 2026, since it's a demo dataset that doesn't get real day-to-day traffic the way the private project does from personal scanning/testing). A pause is recoverable within 90 days from the dashboard, but the goal is to just not let it happen.

Fix: scripts/src/keep-alive.ts does a trivial read (select unique_id from titles limit 1) against each project it has credentials for, and .github/workflows/keep-alive.yml runs it on a schedule (originally every 3 days; **changed to daily on 2026-10-04**, together with heavier pings - an exact row count plus a 50-row read, the Auth health endpoint and a Storage list - after the public project got Supabase's "scheduled to be paused" email even though the Actions logs showed every 3-day `limit(1)` ping succeeding, most recently 2026-10-01; Supabase doesn't document what counts as "sufficient activity". Original plan kept here for history) via GitHub Actions - so it keeps running even if no one's local machine is on. Credentials are GitHub Actions repo secrets: SUPABASE_URL/SUPABASE_ANON_KEY for the private project, PUBLIC_SUPABASE_URL/PUBLIC_SUPABASE_ANON_KEY for the public one. Both use the anon key rather than the service-role key the other scripts in this folder need - titles' RLS already permits a public select, so there's no reason to hand a more powerful key to a scheduled CI job than the task requires. Either target is skipped rather than failed if its secrets aren't set, so this doubles as a runnable-by-hand single-project check (npm run keep-alive from the repo root) when only one side is configured locally. A failed ping exits non-zero, which shows as a red Action run and (per GitHub's default notification settings) emails the repo owner - a free early-warning signal if a project's URL/key ever goes stale, separate from the inactivity-pause problem this was built to solve.

A second scheduled workflow, .github/workflows/resolve-scans.yml (added 2026-09-29), runs every 5 minutes as a backstop for resolving `pending_scans` rows - see barcode-scanning-pipeline.md's "Resolving pending scans" entry for the full reasoning (why GitHub Actions was chosen over Vercel Cron while the app isn't deployed to Vercel yet). Unlike keep-alive.yml, this one needs the private project's service-role key (`SUPABASE_SERVICE_ROLE_KEY`), since resolving writes rows rather than just reading them - plus `OMDB_API_KEY` and `GEMINI_API_KEY`. Only targets the private project; there's no scanning workflow to resolve on the public demo dataset.



**SECURITY & SECRETS**

- All API keys/secrets live in .env.local (gitignored) and Vercel/EAS project environment settings — never committed, per Claude.md's stability/security section.
- Supabase Row Level Security is the actual access boundary for reads/writes, not just conditional UI rendering.
- Public-facing API routes get basic rate limiting to prevent the spam/DoS concern Claude.md raises.
- If case images or any private data go through Supabase Storage, private buckets use signed URLs rather than public links.
- Because Rotten Tomatoes/Letterboxd/Blu-ray.com have no public API, any scraping must be low-volume and respectful of robots.txt/ToS — this is a legal/ethical constraint worth re-checking at implementation time, not just a technical one.
- Schema changes (migrations) run against both live Supabase projects via the Management API (`api.supabase.com`), using a short-lived personal access token the user provides in-chat when needed — direct Postgres access (port 5432) is blocked from this environment's sandbox, only HTTPS is reachable. The token is used only for the immediate API calls it was given for and is never written to a file, committed, or persisted anywhere for reuse - a fresh one is requested each time a migration needs to be applied this way.

**PUBLIC (ANON) KEY READ ACCESS LOCKED DOWN (2026-10-06)** - found while building the public-by-link website: the anon key (embedded in the scanner app bundle, and the key the website reads with) could SELECT every column of `titles` - including who a disc is lent to (a real third party's name), personal ratings, condition notes, barcodes and Estimated Value - plus every `pending_scans` row (whose `resolved_candidates.existingMatch` copies a full title row) and the Estimated Value tables. The website itself never selected those, but the key could. Fix, in two migrations: `0044_restrict_anon_title_columns.sql` (both projects) replaces anon's table-level SELECT on `titles` with a column-level grant of every column except `rented_by_who`, `date_rented`, `personal_rating`, `case_notes`, `disc_condition`, `barcode_id` (built from information_schema because the two projects' columns differ; re-run it after adding any column that should be public), and removes anon's read on `pending_scans`; `0045_restrict_anon_estimated_value.sql` (private only, excluded from the public build) revokes the Estimated Value columns and tables. The scanner app was moved off direct anon reads first: Pending Scans and SuccessScreen's count now use the scan-secret-gated `/api/scan/pending`, and the Rented By suggestions use `/api/scan/rented-by-options`. **Applied 2026-10-06**: 0044 on both projects and 0045 on the private one; verified anon can no longer select the private columns or `pending_scans`.

**SECURITY PASS (2026-10-07)** - before the public Vercel deploy. Fixed in code: the scan secret is compared in constant time (`scanAuth.ts`); `case-image-preview` and the confirm route's `case_image_url` fetch go through `packages/backend/src/remoteImageFetch.ts` (public hosts only, every redirect re-checked, raster images only, 20MB cap, timeout), closing an SSRF that also let the preview route serve attacker HTML from the site's origin; both image routes send nosniff + a sandbox CSP; cover-photo uploads validate `sessionId`, cap size and allow only photo content types; `session-finish` only keeps staged paths in the shape cover-photo writes; `/api/scan/resolve` clamps `limit` to 1-50; TMDb lookups refuse a non-`tt…` IMDb id; the Gemini key moved from the URL to the `x-goog-api-key` header; site-wide nosniff / X-Frame-Options DENY / Referrer-Policy headers in `next.config.ts`; the public-repo sanitizer also skips `scan-log`, `.playwright-mcp`, `screenshots` and `.temp`. **Written, not yet applied**: `0053_revoke_authenticated_writes.sql` (both projects) and `0054_revoke_authenticated_writes_estimated_value.sql` (private only) - the `*_owner_write` policies allowed any `authenticated` user, and anyone can become one by signing up with the public anon key, so they could edit/delete every title and read the private columns. Also turn off sign-ups and anonymous sign-ins in both projects' Auth settings. Still open (owner decisions): the scan secret is an `EXPO_PUBLIC_` value inside the app bundle and appears in the two image routes' query strings (so in request logs); no per-IP rate limiting on public routes yet (Vercel Firewall rules are the simplest place); `Claude/Prompt Journal.md` names real borrowers and is copied into the public build.

## Before going live: Vercel deploy or a real scanner APK (added 2026-10-09)
The user asked to be reminded of these before publishing:
1. **Rotate the scanner secret.** It's an `EXPO_PUBLIC_` value baked into the app bundle, which Expo Go serves to anyone on the LAN. Set the new value in `apps/web/.env.local`, the mobile env and Vercel's environment variables.
2. **Turn off Supabase sign-ups and anonymous sign-ins** in both projects (Authentication settings). Migrations 0053/0054 already removed the signed-in role's access, but switching these off stops the accounts being created at all.
3. **Set up rate limiting** (Vercel Firewall). See the rate-limits report.
4. **Set OWNER_PASSCODE, MDBLIST_API_KEY** and the other keys in Vercel.
5. **Replace the in-process background pollers** (`instrumentation.ts`), which won't run on serverless. See the rate-limits report.
