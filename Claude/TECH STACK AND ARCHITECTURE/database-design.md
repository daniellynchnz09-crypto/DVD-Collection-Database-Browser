**DATABASE DESIGN (Supabase / Postgres)**

Supabase was chosen over a self-hosted SQL database because it gives a managed Postgres instance, auth, file storage (for DVD case images), an auto-generated REST/JS client, and Row Level Security, all on a free tier sufficient for a personal collection database. This satisfies STEP BY STEP PROCESS AND AUTOMATION.md step 1 ("copy the Google Sheet data into a high-performance SQL database that takes priority over the Sheet for processing time").

Two separate Supabase projects, not one project with filtered views:
- A private project holding the entire real collection and real taste-profile names.
- A public project holding only the Friends TV show, X-Men, Star Wars, and the Film Noir boxset, with anonymized taste-profile names, matching Claude.md's public-build description exactly.

Keeping these as two physically separate databases (rather than a filter flag on one database) means the public build can never accidentally expose private rows through a bug in a query filter.

Schema: one core table modeled directly on the "All DVDs and Specs" Google Sheet columns from RESOURCES.md (Title, Movie or TV, Season No., Part of a Season No., Episode Count, Release Date, Running Time, Genre, Director, Franchise, Sub-franchise, Rating, Format, Disc Count, Special Features, Special Features Disk Count, Special Features Disk Format, Animation/Live Action, Documentary, Collection, Name of Collection, Title in a Collection, Number of Titles in a Collection, Rotten Tomatoes Page, IMDB Page, Studio, Disk Region), plus the new columns STEP BY STEP PROCESS AND AUTOMATION.md already calls for (Franchise and Sub-franchise as originally listed here have since been merged into one multi-value `franchise` column - see the Franchise/sub_franchise merge note below):
- unique_id (primary key used for barcode re-scans and future column backfills)
- barcode_id (so re-scanning a title later doesn't require re-scanning the physical barcode)
- case_image_url (points at Supabase Storage)
- genre_location (the single genre the title actually sits under on the shelf, separate from the possibly-multiple Genre column, used for the shelf-location suggestion in Aim Five)
- last_updated (timestamp, needed for the Sheet sync - see `google-sheet-sync.md`)
- steelbook (boolean, added migration 0003 - some items have a steel case with better artwork instead of a plastic one; see Claude/DEFINITIONS.md). Previously this was just a word typed into Format ("DVD Steelbook") - `scripts/src/backfill-steelbook.ts` (one-time, already run) stripped that word back out of Format for the 13 existing rows that had it and set this column instead, since packaging attributes deserve their own column rather than being buried in free text that's supposed to just say the disc format.
- release_name (text, nullable, added migration 0004 - the verbatim edition/packaging title as printed on the disc, e.g. "Gladiator Special Edition", when it differs from the canonical `title` used for OMDB matching and cataloguing, e.g. "Gladiator". Left null/"n/a" when they match. Manual-only in ConfirmScreen - unlike title/format, there's no reliable text signal for which words in a UPC listing are "part of the release name" vs. ordinary packaging noise, so no auto-fill guess is attempted.)

**Rental tracking, personal_rating, and original_language (2026-09-14, `0021_add_rental_and_language_fields.sql`)**: `is_currently_rented_out` (boolean, default false)/`rented_by_who` (text, nullable)/`date_rented` (date, nullable) track a disc currently out on physical loan - see `barcode-review-screen-fields.md` for the ConfirmScreen UI and `scripts/src/backfill-commando-rental.ts` for the one-time real backfill. `personal_rating` (integer, nullable) is the user's own Letterboxd star rating doubled onto a 10-point scale, populated automatically by `scripts/src/import-letterboxd.ts` - see `backfill-rescan-and-letterboxd.md`. `original_language` (text, nullable) is a manual autocomplete field, same pattern as Studio/Rating. All four ship to both Supabase projects/repos - generic collection-management fields, same tier as `disc_condition`/`case_notes`.

**Franchise/sub_franchise merge (2026-09-14, `0020_merge_franchise_columns.sql`)**: `franchise` was originally a single scalar column with a separate `sub_franchise` column for one level of nesting (e.g. franchise "Marvel", sub_franchise "Iron Man") - the user pointed out this doesn't actually generalize, since a film can belong to several franchises at once at different specificities (Captain Marvel (2019) is Marvel, Marvel Cinematic Universe, *and* the Captain Marvel character franchise itself - three memberships, not two nested levels), and separately that Sub-franchise had no input field anywhere in `ConfirmScreen` at all despite `franchise` always being editable. Merged into one `franchise: text[]` column (GIN-indexed, same shape as `genre`) - existing rows combined as `[franchise, sub_franchise]` in that order (verified against the real data first: of 3065 rows, 179 had both set, 1461 only `franchise`, 5 only `sub_franchise`, the rest neither - every real combination accounted for), and the live Sheet's separate "Franchise"/"Sub-Franchise" columns merged into one "Franchise" column (comma-joined) with Sub-Franchise deleted, the same day. `ConfirmScreen`'s Franchise field changed from a single-value `AutocompleteInput` to plain comma-separated text (matching Genre/Director) - `AutocompleteInput`'s "replace the whole field with the tapped suggestion" behavior doesn't work for a multi-value field, and the option-suggestion list was removed rather than reworked, same tradeoff already accepted for Genre/Director. Franchise's `/api/scan/confirm`-side dedup (`canonicalizeValue`'s case-insensitive lookup, "casper" vs "Casper") was dropped for the same reason - it's a single-value SQL `ilike` check that doesn't apply cleanly to an array column - left as a cosmetic gap for a future backfill pass rather than building a new `unnest`-based RPC just to preserve it. Wikidata's franchise prefill (`lookupFranchiseFromWikidata`, `packages/backend/src/wikidata.ts`) was upgraded at the same time to return *every* P179 ("part of the series") claim instead of just the first, since Wikidata already supports multiple per film and the column can now actually hold them all.

**Scanner-entered text normalization**: after the Format-spelling cleanup below kept resurfacing the same underlying risk for other free-text fields, `/api/scan/confirm` now normalizes every scanner-originated field before insert, so random capitalization/spacing typed on a phone keyboard never creates a near-duplicate category:
- `format` and `special_features_disc_format` go through `normalizeFormat` (packages/shared - the same fixed `FORMAT_ALIASES` table used for the Format backfill).
- `disk_region` and `genre_location` go through `apps/web/src/lib/canonicalizeValue.ts` - these have no fixed enum (unlike Format), so it does a live case-insensitive (`ilike`) lookup against whatever's already in `titles` and reuses that exact existing spelling/casing if found, falling back to the trimmed input only when nothing matches yet.
- `title` and `release_name` only get whitespace trimmed/collapsed (`cleanFreeText`, packages/shared) - never case-folded, since they're proper nouns/verbatim packaging text where casing is intentional (e.g. it would be wrong to silently rewrite "THX 1138" or a colon-suffixed collection name).
Verified end-to-end against the real database: a value differing only by leading/trailing whitespace and case correctly resolved to the exact existing genre_location's casing rather than creating a new entry.

**The 1000-row PostgREST cap is a recurring gotcha, not a one-off (2026-09-14)**: found for the second time when a genuine duplicate row ("Thor Ragnarok", a pre-barcode-pipeline legacy row) went completely undetected by `/api/scan/find-existing`'s similar-entry check when "Thor: Ragnarok" was rescanned - both shared the same IMDb id and normalized to an identical title, so the matching logic itself was correct, but the route's own `titles` query had no `.range()`/pagination at all. PostgREST silently caps a single unbounded response at 1000 rows, and with 3066 real rows, a plain `.select()` only ever returns a fixed (effectively arbitrary, since `unique_id` is a random UUID) subset - confirmed live that the legacy row's id genuinely wasn't in that returned set. The exact same class of bug (and the same fix - loop with `.range()` in 1000-row pages until a short page signals the end) had already been found and fixed once before in `apps/mobile/src/lib/fieldOptions.ts`; it just hadn't been applied to this route too. Fixed in `find-existing/route.ts` the same way. Any future `.from("titles").select(...)` with no `.eq`/narrowing filter and no explicit `.limit()` should be treated as suspect for the same reason - the collection is well past 1000 rows now and only grows. The one real duplicate this let through was cleaned up by hand: the new (barcode-scanned, correctly-spelled, TMDb-linked) row was kept as canonical, its Rotten Tomatoes link backfilled from the old row (the one field only the legacy row had), and the legacy row deleted from both Supabase and the Sheet.

Row Level Security: public read access for anything the browse/search UI needs; all writes require the authenticated owner (Supabase Auth, single account — see `web-app-and-auth.md`'s AUTH section). This is the actual security boundary, not just hiding UI elements.

**Format normalization**: the real Sheet had accumulated ~19 distinct spellings of Format for really 7 physical formats (casing drift like "BLu-Ray"/"Blu Ray", double spaces, "4k" vs "4K") - noticed via the Confirm screen's Format autocomplete showing several near-duplicate suggestions for the same thing. `packages/shared/src/titleParsing.ts`'s `FORMAT_ALIASES`/`normalizeFormat` is the single canonical mapping (DVD, DVD (Custom Burn), DVD 3D, Blu-Ray, Blu-Ray 3D, 4K UHD Blu-Ray, CD Movie - Custom Burn and the 3D variants are deliberately kept as their own distinct formats, not folded into plain DVD/Blu-Ray, since they're genuinely different physical media, not spelling variants), applied automatically to every Sheet sync from here on and also used to keep `extractFormatHint`'s scan-time guesses (`packages/shared/src/formatHints.ts`) spelled identically. `scripts/src/backfill-format-normalization.ts` (one-time, already run) cleaned up the 132 existing rows that predated this - verified end to end (Sheet edited, re-synced, and the resulting Supabase distinct-value counts checked against the predicted merge) down to exactly the canonical set with no strays.

**Sheet append bug (found via "Paper Planes," the first real scan-confirmed entry)**: `appendRowToSheet` used to call the Sheets API's `values.append` with an unbounded range (just the tab name), trusting its own "find the table, append after it" auto-detection. Against this Sheet's fixed 4000-row grid, that auto-detection was unreliable and consistently landed new rows at row 4000 regardless of where the real data actually ended (row 3064 at the time) - it silently misplaced every scan-confirmed append this way, leaving ~935 blank rows in between. Fixed by computing the target row explicitly: reading the Title column (`NOT NULL`, so always non-blank on a real row) via `values.get`, then writing with `values.update` at `data.values.length + 1` - sidesteps the ambiguous auto-detection entirely rather than trying to out-guess it. Verified live: a fresh append landed at the correct next row immediately after the fix.

**Running Time's Sheet format**: the real Sheet's existing convention is the unit typed directly after the number with no space (e.g. "154mins"), which a plain numeric write from the confirm route didn't match. `formatRunningTimeForSheet` in `packages/shared/src/titleParsing.ts` (registered in `SHEET_FIELD_FORMATTERS`) fixes this going forward; `toInt()` on the read side already tolerated the suffix fine (parseInt stops at the first non-digit character), so only the write path needed a formatter.

**Boolean Sheet formatting isn't actually uniform across columns**: `formatValueForSheet`'s blanket `boolean -> "y"/"n"` was silently wrong for Special Features specifically - noticed once a scan-confirmed row (Paper Planes) got written with "y" while every other row in the real Sheet uses full "Yes"/"No" for that column (confirmed: 1587 "no"/1429 "yes" vs. a single stray "y"). The distinction is real, not arbitrary: Collection and Title in a Collection's headers literally say "(y/n)" and their data genuinely favors that abbreviation, while Special Features' header has no such qualifier and its data favors the full word. `formatYesNoForSheet` (registered in `SHEET_FIELD_FORMATTERS` for `special_features` and `steelbook` - the latter this project's own new column, given the same convention for consistency with its similarly-unqualified header) fixes this; `toBoolean()`'s `YES_VALUES` set already accepted both spellings on the read side, so only the write path needed fixing. `scripts/src/backfill-yesno-normalization.ts` (one-time, already run) corrected the 15 existing mismatched cells (Paper Planes' Special Features + every Steelbook `y`/`n` from the earlier backfill) - deliberately left Collection/Title in a Collection untouched, since abbreviated `y`/`n` is genuinely their own established convention, not a bug.

**TMDb Title Index storage trim (2026-09-16)**: `tmdb_title_index`/`tmdb_tv_title_index` (`0006_tmdb_title_index.sql`/`0009_tmdb_tv_title_index.sql`, backing the manual title-search route's fuzzy-typo fallback - see `barcode-scanning-pipeline.md`) had grown to 1.24M movie rows + 231K TV rows, 304MB combined, which alone was 96% of the private Supabase project's 318MB total database size - discovered while investigating the user's "we're at 300 of 500MB, what happens at the cap" question. Considered and ruled out three alternatives before landing on the fix actually applied:
- Splitting the collection across two Supabase projects to double the effective storage cap - rejected outright, since Supabase projects are fully isolated Postgres instances with no built-in cross-project data sharing; this would mean building and maintaining a custom sync layer for zero real benefit, on top of the existing public/private split (which exists for a completely different reason - sanitized demo data vs. real collection data - and would only get more confusing with a third storage-driven split layered on top).
- A dedicated hosted search service (Typesense Cloud / Meilisearch Cloud) - investigated live pricing rather than assuming: neither has an ongoing free tier at this row count (Typesense Cloud: one-time 720 free cluster-hours, then ~$21.60/mo; Meilisearch Cloud: $20-30/mo) - both cost roughly the same as just upgrading Supabase to Pro outright, which would solve storage for the *whole* database, not just this one feature. Self-hosting either for free (e.g. a free-tier VPS) was also considered and rejected for now: it trades a one-time trim for a new always-on service the user has to keep alive, for a feature that's only ever a rare, tier-3 fallback when a manually-typed title has a typo neither OMDB's nor TMDb's own search catches.
- Algolia's free plan (verified live via its actual pricing page, since secondary sources disagreed with each other on the current record limit) is genuinely free forever - 50K records, 10K searches/month, no card required - but still would have needed the catalog trimmed to fit under 50K records, at which point moving to a new external service added no benefit over just trimming the existing Supabase table directly.
- A dynamic/session-aware cache (e.g. loading a genre's titles into a hot set while scanning that shelf, evicting it afterward) - proposed by the user, but doesn't actually fit this feature's real trigger condition: TMDb's bulk export has no genre field at all (`{adult, id, original_title, popularity, video}` only - tagging 1.24M rows by genre would need a per-title `/movie/{id}` detail call, the same rate-limited endpoint already a bottleneck elsewhere), and more fundamentally this fallback only ever fires *after* a manually-typed title has already failed to match anywhere else - meaning the mistyped title's identity (and therefore its genre) isn't known yet at the moment a cache would need to decide what to have preloaded. Left as a real idea to revisit if a different, non-genre-based signal comes up.

Landed on a flat popularity trim instead, applied directly to the existing tables: `delete ... where popularity < 1` (TMDb's own popularity score, factoring in vote counts/watchlist adds/etc. - near-zero indicates essentially no real-world engagement, exactly the titles least likely to ever need correcting a typo against) followed by `vacuum full` to actually reclaim the freed disk pages (a plain `delete` only marks space reusable within Postgres, it doesn't shrink the on-disk file - `vacuum full` rewrites the table and its indexes into a smaller file). Cut movies from 1.24M rows/246MB to 380K rows/70MB, TV from 231K rows/58MB to 125K rows/31MB - private project total database size dropped from 318MB to 116MB, comfortably back under the 500MB free-plan cap with real headroom for the collection's own ongoing growth. `MIN_POPULARITY = 1` was also added to both `scripts/src/refresh-tmdb-title-index.ts` and `refresh-tmdb-tv-title-index.ts`'s import filters, so a future re-run of either doesn't quietly re-import the full unfiltered catalog and undo this. Note: the refresh scripts only ever `upsert` newly-qualifying rows - they don't prune a previously-imported row whose popularity later drifts back below 1, so very minor size drift over a long time horizon is possible and considered an acceptable rounding error against the ~860K/106K rows this trim actually removed.

Also worth recording for context: Supabase's actual free-plan behavior at the 500MB cap (verified live, not assumed) is **read-only mode**, not deletion or a hard cutoff - writes get rejected once exceeded, reads keep working, and an email warning arrives at 80% usage beforehand. Getting out of read-only mode means either upgrading to Pro (8GB included) or shrinking back under the limit, same as what this trim did.
