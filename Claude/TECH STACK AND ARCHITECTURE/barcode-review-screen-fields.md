**REVIEW-SCREEN AUTO-FILL AND CANDIDATE NARROWING**

This is point 4 of the pipeline in `barcode-scanning-pipeline.md` (mobile Confirm screen), split out on its own because it's the single largest and most-iterated part of the barcode-scanning feature. See also `backfill-rescan-and-letterboxd.md` for the full-collection backfill rescan (physical-only fields, canonical-id requirement) and the Letterboxd watched-status import built alongside it - those were originally a sub-bullet of this section but are big enough to warrant their own file. **Collection scanning** (built 2026-09-20) is its own separate flow within `ConfirmScreen.tsx`, entirely bypassing the auto-fill/candidate-narrowing machinery described below (a collection member is searched one at a time via the new standalone `apps/mobile/src/components/TitleSearchPicker.tsx` instead) - see `barcode-scanning-pipeline.md`'s own Collections point for the full design.

The review screen never presents a bare barcode; several fields start pre-filled as editable guesses, and the OMDB candidate list itself is narrowed before the user ever sees it:

- `title` starts pre-filled with the UPC listing's own title, cleaned the same way the OMDB search query is (packaging/format words, marketplace-resale noise, and packaging-edition qualifiers like "Special Edition"/"Collector's Edition" stripped — those are marketing fluff, not a content distinction, unlike a genuinely different cut like "Final Cut" which the user does keep in a title). Always editable, never presented as confirmed.
- `format` starts pre-filled from a text-pattern match on the listing (`extractFormatHint` in `packages/shared/src/formatHints.ts` — checks for 4K/UHD before Blu-ray so a "4K UHD Blu-ray" combo isn't miscategorized as plain Blu-ray). This can only work with words actually present in the listing text — if a listing just says "Blu-ray" with no "4K"/"UHD" mention at all even though the physical disc is a 4K combo pack, there's no text signal to catch that; the field stays user-editable specifically because this guess can be wrong.
- The OMDB candidate list is narrowed using the listing's own year as a chronological upper bound (`extractProductYear` + `filterCandidatesByMaxYear`): a listing's year is the disc's *home-video release* year, not necessarily the film's, but home video always follows theatrical release, so any OMDB candidate whose Year is *after* the listing's year is eliminated outright — a disc can't exist for a film that hasn't been released yet. Never eliminates every candidate (falls back to the unfiltered list) since the extracted year is itself just best-effort text parsing.
- **"|"-delimited listings get their title and cast-list halves split apart, and the cast half narrows ambiguous candidates by who's credited.** Found live via a real "Captain Marvel" scan whose UPC listing title was `Captain Marvel | Brie Larson, Samuel L J Blu-Ray Expertly Referubished Product` - the trailing half isn't stripped by the ordinary noise-word regexes (they only know specific marketplace/packaging words, not arbitrary cast names), so it was reaching the OMDB search query verbatim and returning zero results even though "Captain Marvel" alone finds it instantly. `cleanProductTitleForSearch` (`packages/shared/src/omdb.ts`) now cuts at the first `|` before doing anything else, fixing the search itself. Separately, `extractListingMetaText` recovers that discarded half specifically to help disambiguate when the cleaned title search still returns more than one same-titled OMDB candidate (up to 10 - `enrichAndNarrowCandidates` in `packages/backend/src/scanResolver.ts`, runs only when there's real ambiguity to resolve): each candidate gets one OMDB detail fetch for its `Actors` field, scored against the metadata text by word overlap (`scoreCandidateByCastHint`) rather than by first trying to classify which part of the text "is a name" - a listing's cast mention is often abbreviated (this real example shortened "Samuel L. Jackson" to "Samuel L J", which wouldn't substring-match at all) and mixed with genuine noise with no delimiter of its own ("Samuel L J Blu-Ray Expertly Referubished Product" is one comma-segment). Word overlap tolerates both: real cast words contribute matching points, and noise words simply never appear in any actor's name and contribute nothing - never a wrong exclusion, only ever a (possibly zero) positive signal. Only narrows to a single candidate when there's a genuine, unambiguous winner (score > 0 and strictly ahead of every runner-up); a tie or an all-zero result leaves the full candidate list untouched, same fallback-safety pattern as the year filter above. Deliberately silent per the user's own request - no separate UI step or "matched via cast" indicator, unlike the cover-photo auto-match below which does show its reasoning; this only ever narrows what candidate list the existing screen already shows.
  - **Real near-duplicate candidates that cast overlap can't distinguish get a Runtime shown instead, as a physical, human-checkable signal** - found live: two separate OMDB entries for "Captain Marvel" (2019), same year, same poster, and (being an alternate cut of the same film) the same billed cast too, so cast-hint scoring alone can't tell them apart. `findDuplicateTitleYearIds` (`packages/shared/src/omdb.ts` - groups candidates by normalized title + Year, same title-matching normalization used elsewhere) flags any candidate sharing an identical key with another; `enrichAndNarrowCandidates` fetches Runtime for those specific candidates (reusing the same OMDB detail fetch already made for cast scoring when both apply, never fetching a candidate's detail twice for two different reasons) and attaches it to the candidate object sent to the review screen, which shows it next to Year (`"2019 · 133 min"`) whenever present. Deliberately **not** used to auto-narrow anything - unlike cast/year, nothing in the listing text says which cut is actually in the box, so this is purely something for the user to check against the disc's own case, same spirit as the cover-photo comparison.
  - **The candidate title text was also getting cut off** (`numberOfLines={2}` on the poster-card title, found live once a near-duplicate pair's titles ran long enough to need it) - removed entirely rather than raised to a higher fixed number, so a card's title always shows in full and the card just grows to fit it instead of risking truncation again on some future longer title.
- When UPCitemdb's own listing has a product photo, it's shown on the review screen captioned as "your scanned item" specifically because it's a photo of the actual listing, not a generic poster — the most useful single signal for telling apart releases of the same film that share a title and year (special editions, different regions, different bonus-features packaging) but look different on the shelf. Candidates without their own photo still show OMDB's poster in the horizontal candidate list, but that's a generic per-*film* image, not a per-*edition* one.
- **Auto-matching by cover photo**: when the listing has its own photo, it's automatically compared against every OMDB candidate's poster using perceptual image hashing (`matchPosterToCandidates` in `packages/backend/src/posterMatch.ts` — Jimp's pHash/compareHashes, a DCT-based hash compared by Hamming distance, normalized 0..1 where 0 is identical). Deliberately conservative: only reports a confident match when the best result is both close in absolute terms *and* clearly ahead of the runner-up, since a resale-listing photo of a plastic case often looks quite different from OMDB's stylized theatrical poster even for the objectively correct film (different framing, cropping, an added disc-shaped overlay, background) — thresholds were verified against synthetic identical/unrelated-image pairs (0 vs. ~0.375), not yet against a real photo-vs-poster pair from an actual scan, since no scan so far has had both a UPC photo and needed disambiguation. When confident, the review screen shows just that one matched candidate with a "Not this item" escape hatch that reveals the full poster list (everything it was compared against) to pick from manually instead; when not confident (or there's no listing photo at all), the full list shows as before with nothing pre-selected. Skipped entirely for collections, since a box-set's own cover doesn't correspond to any single film's poster.
- This poster-matching code lives in a separate `packages/backend` workspace, not `packages/shared` — image decoding (Jimp, for the perceptual hash) pulls in Node-core modules (`fs`, `util`, `stream`) that Metro (the mobile app's bundler) can't resolve, and `packages/shared` is the one package the mobile app also depends on. `packages/backend` depends on `packages/shared` and is itself only imported by `apps/web`'s API routes and `scripts/`, never by `apps/mobile`.
- **Making-of/behind-the-scenes/special-screening results get collapsed into a tap-to-reveal "Extras" section, never removed (2026-09-14)** - found live: searching a well-known film's title on OMDB also surfaces genuinely real IMDb entries for that film's making-of documentary, convention/special-screening footage, and featurettes, which the user correctly pointed out are "highly unlikely to be the actual physical disc being scanned" but shouldn't be discarded outright, since a false positive here would mean a real classification mistake hiding an actual candidate. `looksLikeExtraContent` (`packages/shared/src/omdb.ts`, next to `looksLikeCollection`) is a keyword heuristic ("making of", "behind the scenes", "featurette", "special screening", "world premiere", "red carpet", "press conference"/"junket", "q&a", "fan event", "gag reel"/"bloopers", "deleted scenes", "table read"/"roundtable", "panel discussion") checked against each candidate's title; `ConfirmScreen` partitions `candidates` into `mainCandidates`/`extraCandidates` at render time only (every piece of actual state - `selected`, auto-select-when-only-one-candidate, the title-text used for the similar-entry check - still operates on the full unpartitioned list, so an extra is fully selectable/confirmable like any other candidate, just visually tucked under a collapsed "Extras (N)" toggle below the main horizontal row instead of cluttering it). Deliberately more willing to over-classify than the cast-hint/duplicate-runtime logic elsewhere on this screen, since being wrong here only costs one extra tap, not a hidden result.
- **Special Features Disc Count defaults to 1 the moment it becomes relevant (2026-09-14)** - a multi-disc release with special features switched on is overwhelmingly likely to have exactly one dedicated bonus-features disc, so asking the user to type "1" every single time was pure friction; a `useEffect` keyed on `showSpecialFeaturesDiscFields` sets it to `"1"` only while the field is still blank (same "only while blank, never stomp a real value" pattern already used for the 4K-UHD-defaults-Disk-Region-to-"All" effect above), so a genuine 2+-dedicated-discs release just gets typed over it as before.
- Explicitly **not implemented**, and moved to the backlog rather than built: listing alternate physical releases/editions of a film once it's been identified (e.g. "here are the other known DVD/Blu-ray releases of this film"). This hits a hard data-availability wall rather than an effort one — OMDB holds exactly one entry per film with no per-edition/per-pressing data at all, and no API in this stack tracks that (Blu-ray.com, which would have it, has no API and is already excluded entirely — see `barcode-scanning-pipeline.md`). The user's plan is to invent spreadsheet categories/manual workarounds for this instead, to be specified later (see Claude/To Do list.md's BACKLOG).
- **Format / Disk Region / Genre Location are autocomplete fields, not free-typed with no help**: `apps/mobile/src/lib/fieldOptions.ts` loads every distinct existing value for these three columns from `titles` (public-read RLS, so the anon key can query it directly), and `AutocompleteInput` (`apps/mobile/src/components/AutocompleteInput.tsx`) filters that list as the user types, offering a tap-to-fill suggestion while still accepting anything typed as free text. There's no fixed enum in the schema for any of these three columns - typing a genuinely new value once just makes it appear as a suggestion for every future scan, since the option list is nothing more than "whatever's already in the collection."
- **Disk Region narrows by Format** (`getDiskRegionOptions` in `packages/shared/src/formatHints.ts`, verified against current region-code references rather than assumed): DVD offers 1/2/3/4/5/6/All (region 7 is reserved/never used on retail product and region 8 is airline/cruise-only, both excluded as unrealistic for a physical collection), Blu-ray offers A/B/C/All, and 4K UHD Blu-ray - which carries no region coding at all - defaults straight to "All" (auto-filled the moment Format is recognized as 4K, but only while the field is still blank, so it never overwrites a deliberate manual entry). An unrecognized format (VHS, CD, ...) falls back to the full unfiltered list of existing Disk Region values instead of a hardcoded scheme, since none applies. **Disk Region is a fixed multi-select, not free text** (`MultiSelectChips` in `apps/mobile/src/components/MultiSelectChips.tsx`) - unlike Format/Genre Location/Rating/Studio, region codes are a genuinely closed set that can't gain new members over time, and some discs are legitimately coded for more than one region at once, so the field is a toggleable set of chips rather than a single autocomplete value; the selected codes are joined into one string ("2, 4") at submit time, matching the existing plain-`text` column rather than needing an array column. Selecting "All" clears every other selection and vice versa, since being region-free is contradictory to being coded for specific individual regions. No `canonicalizeValue` normalization is needed for this field anymore - the option set is fully closed client-side, so there's no free-typed casing/spacing to drift. **"Not Listed"** (`NOT_LISTED_REGION` in `formatHints.ts`, appended to every format's option list) covers a disc that simply prints no region information anywhere on its packaging - distinct from "All", which means the packaging affirmatively states region-free (or the format's own scheme has no regions at all, like UHD). Added after the user found a real disc with no region info printed at all, rather than the app just assuming one. `MultiSelectChips` now takes a generic `exclusiveOptions` prop (default `["All"]`) so both "All" and "Not Listed" are mutually exclusive with every other option and with each other, instead of "All" being hardcoded as the only special case. Since "Not Listed" is now always appended, the old 4K-auto-defaults-to-"All" effect could no longer key off "the option list has exactly one entry" (that's now 2 for UHD) - it uses the new `isRegionFreeFormat` helper instead, which checks the format text directly.
- **Steelbook** is a plain boolean switch next to Special Features (see the steelbook/release_name column notes in `database-design.md`).
- **Special Features Disc Count / Format of Special Features Discs** only appear once Special Features is switched on *and* disc count is more than 1 - there's nothing to count when there are no special features, and a single-disc release can't have a separate bonus-features disc. Confirmed with the user this AND condition (rather than disc-count alone) matches their intent; these two fields aren't exclusive to collections - any multi-disc release, box set or not, can have one of its discs be a dedicated bonus-features disc.
- **Release Name** is manual-only (see `database-design.md`) - it sits right under Title/before Format in the review screen, shared across every member title for a collection scan exactly like Format/Disc Count/Steelbook already are, since a box set's release name describes the one physical object, not any single film inside it.
- **Rating and Studio only appear as manual fields when TMDb can't provide them** - since TMDb now auto-fills both (see below), asking the user to type in something TMDb is about to supply anyway would be redundant. `/api/scan/tmdb-preview` (a read-only, purely informational lookup - the actual authoritative one that gets stored still happens independently inside `/api/scan/confirm`) is called from `ConfirmScreen` the moment a single candidate is selected; the manual Rating/Studio fields stay hidden while that check is in flight and only reveal individually if TMDb genuinely came up empty for that specific field. With no candidate selected at all (pure manual entry, no `imdbId` to look up), the fields show immediately, since TMDb can never be tried in that case. **Unlike every other manual field, these are NOT shared across a multi-title collection** - a box set's cover only ever shows one rating/studio for the entire set, which isn't necessarily any individual film's own rating, so manual Rating/Studio entry is hidden entirely for a multi-title selection (and independently nulled out server-side in `/api/scan/confirm`, as a safety net beyond just hiding the UI); each member title instead gets its own from TMDb once confirmed.
- **Rating normalization**: like Format, the real Sheet had casing drift ("pg", "m") and a couple of stray typos ("R\`16", "Rr16") on top of the real NZ classification scheme (G/PG/M/R12/R13/R15/R16/R18). `RATING_ALIASES`/`normalizeRating` in `packages/shared/src/titleParsing.ts` is the canonical mapping, applied on every Sheet sync and in `/api/scan/confirm`'s manual Rating field - `rating` stays free text overall (OMDB's own US-style `Rated` value also flows through this column and isn't forced into the NZ table). `scripts/src/backfill-rating-normalization.ts` (one-time, already run) cleaned up the 4 existing rows that predated this.
- Explicitly **not implemented**: an automated online lookup for Rating/Studio (e.g. from IMDb's parental-guide/company-credits pages) for the collection-member case where there's no single physical case to read from. IMDb's own robots.txt states outright that "any device, tool, or process designed to data mine or scrape the content using automated means is prohibited without prior written permission" - confirmed by fetching it directly - so building that against IMDb isn't something this project does; OMDB's own `Rated`/`Production` fields were checked as a possible substitute and don't reliably solve this either (confirmed live against Paper Planes: `Rated` was the US-style "Not Rated" rather than any NZ/Oceania certificate, and `Production` was blank). TMDb (themoviedb.org) has a genuine free public API that tracks per-country release certifications and production companies and was raised as a real candidate worth pursuing, pending the user obtaining a free API key.
- **Rotten Tomatoes IS automated** (`lookupRottenTomatoesPage` in `packages/backend/src/rottenTomatoes.ts`), since RT's robots.txt is far more permissive (only a few specific paths disallowed - plain `/m/<slug>` movie pages aren't). OMDB's own `Ratings` array already reports whether a title has a critics score at all (a `"Rotten Tomatoes"` source entry, e.g. `"85%"`) with zero RT requests needed; only once that's confirmed does the function fetch one guessed slug (`https://www.rottentomatoes.com/m/<slugified-title>`) and cross-check the page's own schema.org JSON-LD block - both the film name and the Tomatometer score must match what OMDB already reported, or it returns null rather than a guessed link. Deliberately never overrides a link the user already typed in manually. Verified live: correctly resolved and saved Paper Planes' real page, and independently confirmed the guard rejects both a mismatched score and a nonexistent title rather than false-positiving.
  - **The name-match check was too strict, found live via a real miss (2026-09-14)**: rescanning Thor: Ragnarok never got an RT link even though OMDB reported a real Tomatometer score. Root cause: RT's own JSON-LD `name` field is `"<Title> (<Year>)"`, not the bare title (confirmed by fetching the real page - `"Thor: Ragnarok (2017)"`), so the exact-match comparison against OMDB's bare `"Thor: Ragnarok"` always failed once a page actually had this shape - silently, for any film whose RT page follows this common convention, not just this one title. Fixed by stripping a trailing `" (YYYY)"` before comparing. Also switched the returned URL from the guessed pre-redirect slug to `res.url` (the fetch's actual final URL) - RT itself 302s a same-titled/no-year slug to its real disambiguated one (`/m/thor_ragnarok` -> `/m/thor_ragnarok_2017`), and storing the guessed slug just meant every future click paid for an extra redirect it didn't need to.
- **Manual title-search fallback for a barcode that returned nothing at all** (`apps/web/src/app/api/scan/title-search/route.ts`, `searchTitleOnOmdb` in `apps/mobile/src/lib/scanApi.ts`): sometimes UPCitemdb has no listing whatsoever for a barcode, meaning the resolver never had any title text to search OMDB with in the first place - the old behaviour dumped the user straight into a blank manual-entry form with no candidate list at all. `ConfirmScreen` now detects this specific case (`candidates.length === 0 && !upcProduct && !hasSearchedOrSkipped` - deliberately narrower than "OMDB found no match," since a listing with its own product photo/description still gives the user something to manually fill in from) and shows a single "what's the title?" text field first. Submitting it calls the new route, which hands results back into the exact same candidate list state the automatic pipeline populates - so poster selection, cover-photo auto-matching, the TMDb Rating/Studio preview, and Confirm all work completely unchanged from that point on, with no separate code path to maintain. A "Skip - enter manually instead" link bypasses the search entirely (for a title OMDB likely won't have, e.g. an obscure regional release) and prefills the ordinary manual Title field with whatever was typed. Both the typed query and any search results survive navigating away and back, via the same `confirmDrafts.ts` cache every other in-progress field on this screen already uses. **A single candidate (from either the automatic resolver or a manual search) is auto-selected** rather than making the user tap it - nothing to disambiguate when there's only one option, and it's still fully reversible (tapping it again deselects it like any other candidate). This is also what makes the cast-hint narrowing above "bring up the best match" automatically with no extra code - once it narrows the candidate list down to one, this same generic single-candidate auto-select fires on it.
- **A genuinely manual entry (Skip - enter manually instead, `selected.size === 0`) also asks for Genre, Running Time, and Director** - added per the user's own request, since a title with no OMDB/TMDb candidate at all has no id for any future refresh job to backfill these from later (unlike every other scan, where they're filled in automatically from OMDB/TMDb detail once a real candidate is confirmed - see the confirm route's `manual.genre ?? omdbFields.genre` -style fallback). Genre is comma-separated text matching RESOURCES.md's own Sheet convention, and (since 2026-09-14, see below) a `TagAutocompleteInput` rather than plain free text; Director stays plain free text, since names don't repeat across the collection densely enough to be worth suggesting from. Deliberately **not** asking for Rotten Tomatoes/IMDb/TMDb links or ids here - `showTmdbOverrideField` is already gated on a real candidate being selected (`singleSelectedImdbId`), so a fully manual entry is already exempt from that requirement per the canonical-id rule in `backfill-rescan-and-letterboxd.md` - a page almost certainly doesn't exist for a title neither database could find in the first place. These three fields are only ever sent to `/api/scan/confirm` when `selected.size === 0` (omitted entirely otherwise, not sent as `null`/`[]`), so they can never clobber a real OMDB-derived value for an ordinary candidate-backed scan. (A fourth field, Sub-franchise, was briefly added here the same session before being merged straight into the always-visible Franchise field instead - see `database-design.md`'s Franchise/sub_franchise merge note - so it never actually shipped as a separate field.)
- **Typo correction for the manual title-search route** - built after empirically disproving the original assumption behind it. It was first assumed TMDb's own search API would be meaningfully more typo-tolerant than OMDB's literal substring search, and built as a second parallel search pass on that basis; live testing then showed this was wrong - TMDb's search returned zero results for realistic typos ("Jurrasic Park", "Lord of the Rngs", "The Shawshenk Redemption" all returned nothing from both OMDB and TMDb). That TMDb-search pass was kept anyway (it's still a genuinely different index that occasionally has a title OMDB lacks, and is now re-run with the corrected query too - see below), but doesn't solve typos on its own. Real typo tolerance is now three layered passes in the route, each merged into the final candidate list by imdbID (never replacing the previous pass's results, only adding to them - per the user's own explicit design that a spelling correction should never hide "results from what the user actually input"):
  1. OMDB + TMDb search using the user's exact typed text (unchanged).
  2. The same two searches again using a spelling-corrected version of the text (`correctSpelling` in `packages/backend/src/spellcheck.ts`) - an `nspell`/`dictionary-en` Hunspell-style English dictionary corrector, run only on individual words the dictionary both flags as misspelled and has a suggestion for (skips words already correct, and words 2 characters or shorter, e.g. "Ex" in "Ex Machina"). Verified live: fixes "Jurrasic" -> "Jurassic" and "Gladiaor" -> "Gladiator" correctly, but is also verified to sometimes guess wrong ("Titanik" -> "Titania", "Rngs" -> "Rags") and to return no correction at all for a name that isn't a real English word in the first place ("Shawshenk" - since "Shawshank" itself isn't a dictionary word either). A wrong guess is a low-risk failure mode specifically because pass 1's literal results are always present alongside it - it just adds an irrelevant extra candidate rather than replacing the correct one.
  2b. `dictionary-en` is ESM-only (a top-level `await` inside its own module) and is loaded via a **dynamic** `import()` inside `spellcheck.ts` rather than a static one - a static import broke every script in `scripts/` that transitively imports anything from `@danflix/backend`'s barrel export (confirmed live: `npm run refresh:tmdb` failed under `tsx`, which transforms scripts to CommonJS by default, and esbuild can't transform an ESM top-level-await module into CJS). A dynamic `import()` is left alone by that transform and Node natively supports loading an ESM module this way regardless of the caller's own module format, fixing it without changing any consumer's module settings.
  3. Only when passes 1 and 2 together found nothing at all: a fuzzy match against `tmdb_title_index` (`supabase/migrations/0006_tmdb_title_index.sql`, `0007_tmdb_fuzzy_rank_by_popularity_band.sql`) - a local copy of every real TMDb movie title (imported from TMDb's public daily bulk export, `https://files.tmdb.org/p/exports/movie_ids_MM_DD_YYYY.json.gz` - URL pattern and per-line schema `{adult, id, original_title, popularity, video}` confirmed live by downloading and inspecting a real file rather than trusting the docs summary alone, which didn't fully list the fields), matched via Postgres's `pg_trgm` trigram similarity extension through a `fuzzy_search_tmdb_titles` RPC function (PostgREST can't express the `%` trigram operator through its normal filter syntax). This is the pass that actually catches an invented/proper name a generic English dictionary never could ("Shawshenk" -> "The Shawshank Redemption", "Rngs" -> "The Lord of the Rings", "Titanik" -> "Titanic") - verified live against all three. Ranks by similarity first, but rounds it to one decimal place before ranking so near-identical matches fall into the same band and popularity breaks the tie within it (fixed live after an obscure foreign title with marginally higher raw similarity - "Bife 'Titanik'", popularity 1.9 - initially outranked the real "Titanic", popularity 45.5, on a 0.015 similarity difference alone). Bulk-imported via `scripts/src/refresh-tmdb-title-index.ts` (`npm run refresh:tmdb-title-index` - ~1.24 million non-adult titles, batched upserts of 2000; run by hand for now, weekly is plenty since TMDb regenerates the export daily and new titles are the only thing that changes). Resolving a fuzzy hit's IMDb id/poster/year still costs one `/movie/{id}` TMDb call per hit (same as the search-pass candidates), so this stays a last-resort fallback rather than always-on. **A separate `tmdb_tv_title_index`** (`0009_tmdb_tv_title_index.sql`, `scripts/src/refresh-tmdb-tv-title-index.ts` - ~231k rows from TMDb's daily `tv_series_ids_MM_DD_YYYY.json.gz` export, schema `{id, original_name, popularity}`, no `adult` field at all unlike the movie export) exists purely to support auditing the existing collection's TV/documentary titles for misspellings the same way (see BACKLOG note in `../TECH STACK AND ARCHITECTURE.md`'s INDEX) - the manual title-search route itself is movie-only (`omdbSearch`/`searchTmdbMovies` search movies), so this second index isn't wired into that live route, only used ad hoc via `fuzzy_search_tmdb_tv_titles`. Both index-building migrations bake in the exact-match-priority fix from the start (0008's lesson learned on the movie index). (See `INDEX.md`'s BACKLOG for other superseded/deferred decisions.)
- **"Custom/homemade disc" toggle skips spelling correction entirely** - the collection's `format = "DVD (Custom Burn)"` discs (32 rows) are the concrete real-world case the typo-correction passes above can actively hurt: many are non-English/obscure franchises with genuinely unusual-looking names, and a few are the user's own creations never listed on IMDb/OMDB/TMDb at all - "correcting" toward the nearest English word or nearest real TMDb title is more likely to produce a wrong, confusing suggestion than to catch an actual typo for these. Since Format itself isn't chosen yet at the point the manual title-search step runs (title comes before format in the flow), the user instead flags this manually with a checkbox right in that step; checking it sends `skipCorrections: true` to `/api/scan/title-search`, which then skips both the dictionary-spellcheck pass and the fuzzy-title-index fallback and runs only the literal OMDB+TMDb search. Verified live: searching a real typo ("Jurrasic Park") normally returns 11 corrected candidates, but returns none at all with `skipCorrections` set - confirming the toggle genuinely disables correction rather than just hiding it.
- **The Pending Scans "+" button creates a barcode-less manual entry** for discs that were never going to have anything to scan in the first place (the user's own custom-burned creations). `pending_scans.barcode` is nullable (`0010_pending_scans_barcode_nullable.sql`) specifically for this - a manual entry is inserted directly with `status: "needs_manual"` and empty `resolved_candidates`, bypassing `"pending"` entirely so `resolvePendingScansBatch`'s poller never touches it (there's nothing to look up: no barcode, no UPC listing). Since `resolved_candidates` is empty and `barcode` is null, `ConfirmScreen`'s existing `needsTitleSearch` check (`candidates.length === 0 && !upcProduct`) is already true immediately - a manual entry lands on the same manual title-search step as a barcode that scanned but returned nothing, with zero additional branching needed there. Every other `scan.barcode`-dependent code path (the confirm route's `barcodeId`, the backfill-match "attach to existing entry" flow, the scan-cooldown forget-on-discard callback) treats a null barcode as "nothing to attach/forget" rather than erroring - genuinely correct behavior, not a workaround, since there never was a barcode for these to begin with.
- **Rating and Studio ARE now automated too, via TMDb** (`themoviedb.org`) rather than IMDb - `lookupTmdbFields`/`fetchTmdbFieldsById`/`refreshTmdbFields` in `packages/backend/src/tmdb.ts`. TMDb has a genuine free public API (unlike IMDb), so this is what the "automated pipeline for Rating/Studio in a collection" idea became once the IMDb-scraping option was ruled out. Per-entry, keyed by `entry.imdbId` via TMDb's `/find` endpoint (external-id lookup, no title-text search needed) - genuinely per-film data, so unlike the manual Rating/Studio fields it applies to every member of a collection scan, which is exactly what solves the original "the box only has one rating, not each film's own" problem. Priority order at confirm time: a manual entry (single-title scans only, same restriction as before) > TMDb's NZ/Oceania certification + primary production company > OMDB's `Rated`/nothing. Verified live against the real Paper Planes IMDb id: TMDb's NZ certification was "G" (exactly matching the physical case) and its first-listed production company was "Arenamedia" (exactly matching the earlier manual research) - both independent confirmations that TMDb's data is accurate for this collection.
- **Franchise and Animation/Live Action are now scan-form fields too** - added after the user scanned Casper's Haunted Christmas and found it logged with no Franchise at all and the wrong Animation/Live Action value. The root cause wasn't a bad automated guess: neither field had ever been asked for anywhere in the mobile scan form, so every barcode-scanned title silently got Franchise blank and (per `/api/scan/confirm`'s own code) Animation/Live Action hardcoded to the literal string `"Live Action"` regardless of the truth - this had been happening to every scanned title, not just this one. Franchise stays a plain, always-visible field on `ConfirmScreen` (prefilled but always editable, never hidden - unlike Rating/Studio; comma-separated, and since 2026-09-14 a `TagAutocompleteInput` rather than free text or single-value `AutocompleteInput` - see below). Animation/Live Action, after a follow-up question, works more like Rating/Studio instead:
  - **TMDb has no "Live Action" genre at all** - its genre list (Action, Adventure, Animation, Comedy, Crime, Documentary, Drama, Family, Fantasy, History, Horror, Music, Mystery, Romance, Science Fiction, TV Movie, Thriller, War, Western) either tags "Animation" or doesn't; "Live Action" is purely this collection's own inference from that absence. So once TMDb has actually answered for a title, the two cases are handled asymmetrically rather than both getting the same free-text field: **confirmed live action** (no "Animation" genre) hides the field entirely and locks the value to `"Live Action"`, same as Rating/Studio hiding once TMDb has an answer - there's genuinely nothing for the user to pick. **Confirmed animated** keeps the field visible as a real style dropdown (`fieldOptions.animationOrLiveAction` with `"Live Action"` filtered out of the options list, since it's not a valid answer once TMDb has confirmed Animation), for the *specific* style (2D/3D/Puppet/Claymation/Stop-Motion/Anime/hybrid - this collection's own existing data already uses all of these, TMDb has no such field at all) which stays a manual choice.
  - **`isAnimated` is three-valued** (`true`/`false`/`null`), not a plain boolean, in `fetchTmdbFieldsById`/`lookupTmdbFields` (`packages/backend/src/tmdb.ts`) and `TmdbPreview` (`apps/mobile/src/lib/scanApi.ts`): `false` is a confirmed "TMDb has genre data and Animation isn't in it", but `null` covers both "no TMDb match for this IMDb id at all" and "the detail fetch itself failed" - genuinely unknown, not a confirmed live-action answer. Conflating `null` into `false` (the original implementation, fixed after being asked directly what TMDb's actual categories were) would have hidden the field and silently forced `"Live Action"` on a title TMDb was never actually able to answer for. `null` behaves like "no candidate selected at all" - field stays visible, full option list, no forced value.
  - **A blank confirmed-animated field can't be allowed to fall through to the server's default.** `/api/scan/confirm` still defaults a blank `animation_or_live_action` to `"Live Action"` (the right call when there's truly no signal - a multi-title collection scan, or no candidate selected). But if TMDb has confirmed Animation and the user leaves the now-visible style dropdown untouched, the mobile client sends `"Animation"` instead of `null` in that one specific case, so the server's blanket default can never mislabel a title TMDb already confirmed isn't live action.
  - **Franchise prefill via Wikidata** (`packages/backend/src/wikidata.ts`) - verified before writing any code that TMDb's own `belongs_to_collection` field doesn't reliably capture franchise membership (it's `null` for Casper's Haunted Christmas despite obviously being a Casper film - no free "franchise database" exists at all), and separately verified that Wikidata's own documentation (`wikidata.org/wiki/Wikidata:Data_access`) explicitly permits bot/API access to its SPARQL query service - unlike IMDb's outright ban, the `Disallow: /sparql`/`Disallow: /w/` lines in its robots.txt are there to stop search-engine crawlers from indexing those endpoints, not a ban on the deliberate queries Wikidata's own docs teach people to make (followed their etiquette requirements regardless: a descriptive User-Agent, treating a 429 as "back off"). Queries Wikidata's P179 ("part of the series") property, keyed by IMDb id (P345). **P674 ("characters") was tried too as a fallback and dropped after live testing exposed real false positives** - Gladiator (a standalone film, pre-2024 sequel) returned "Marcus Aurelius" as its "featured character", a real historical figure who appears as a dramatized character across many unrelated productions about Rome, not evidence of an actual franchise; a follow-up query confirmed there was no way to algorithmically prefer the "right" character among several plausible candidates either. P179 alone is far more precise (Wikidata editors only set it when a genuine series exists) at a real cost in recall - Casper's Haunted Christmas itself has no P179 claim, so its own Franchise field still needs manual entry even now; that's the honest trade-off, not a bug.
  - **Manual entry for Animation/Live Action** uses the exact same `AutocompleteInput`/`fieldOptions.ts` pattern as Genre Location - typing the first few letters offers existing values to pick from (the "dropdown of pre-existing entries" the user asked for), backed by a proper alias table (`ANIMATION_ALIASES`/`normalizeAnimationOrLiveAction` in `packages/shared/src/titleParsing.ts`, same pattern as `RATING_ALIASES`) since the real Sheet already had 20 distinct typo'd casings of "Live Action" alone by the time this was investigated (some needing an explicit alias entry beyond simple case-folding, e.g. "Live Aciton"/"Live Acrion"/"Lice Action" - genuine letter-level typos, not just casing) - all backfilled in the Sheet + Supabase (`scripts/src/backfill-animation-normalization.ts`, one-time/already run), deliberately leaving genuine hybrid descriptions ("Live Action/Animation Hybrid", "2D Animation and 3D Animation", ...) untouched since those are real combination values, not typos.
  - **Genre and Franchise are `TagAutocompleteInput` fields (2026-09-14)** (`apps/mobile/src/components/TagAutocompleteInput.tsx`), replacing plain free text (Genre) and the brief single-value-`AutocompleteInput`-then-plain-text history Franchise went through right after the Sub-franchise merge above. Built after the user pointed out that a whole-field-replacing autocomplete (the original `AutocompleteInput`) can't work for a comma-separated multi-value field at all - tapping a suggestion would clobber every tag already typed before it - but a plain text field with no suggestions loses the "dropdown of pre-existing entries" every other free-text-with-known-values field on this screen already has. `TagAutocompleteInput` splits the field's current text on commas and only matches/filters against the segment after the last comma (the tag currently being typed), leaving every earlier tag untouched; tapping a suggestion appends it plus `", "` to the prior tags and leaves the field focused, so the next thing typed is matched fresh against the full option list rather than filtered by whatever came before - the "reset independent of the previous entry" the user asked for. A tag with no matching option is simply kept as free text, exactly like every other field's known-value list ("no fixed enum, typing something new just becomes a future suggestion"); `fieldOptions.ts` now also loads `genre`/`franchise` (flattened distinct tags from the `text[]` columns via `distinctSortedFlat`, not distinct whole-array values, which is what makes segment-level suggestions possible at all), and `ConfirmScreen` calls `loadFieldOptions(true)` right after a successful confirm so a genuinely new tag is already suggestible on the very next scan in the same session, not just after an app restart (previously true of every autocomplete field on this screen, but never actually wired up until now). The `canonicalizeValue` case/whitespace dedup mentioned in earlier versions of this doc still doesn't apply here - it's a single-value SQL `ilike` check, not applicable to an array column - left as the same cosmetic gap noted in `database-design.md`'s Franchise/sub_franchise merge note rather than being rebuilt as a per-tag RPC. **Franchise renders 3 lines tall** (`TagAutocompleteInput`'s `numberOfLines` prop, multiline `TextInput` with `textAlignVertical: "top"` on Android) since it regularly holds several comma-separated tags at once (per the Captain Marvel example above: Marvel, Marvel Cinematic Universe, Captain Marvel) and a single line kept truncating; Genre stays single-line since it rarely holds more than one or two tags.
- **In-progress form state survives leaving the screen**: `apps/mobile/src/lib/confirmDrafts.ts` is a module-level cache, keyed by pending scan id, holding everything the user has typed/selected on this screen. ConfirmScreen restores from it on mount instead of recomputing fresh defaults, and saves to it on every change - needed because ConfirmScreen fully unmounts every time the user navigates to Pending Scans and back (same reason the scan-cooldown map lives in App.tsx, not ScannerScreen), which was previously silently discarding anything entered on an incomplete scan. Cleared only once the scan reaches a terminal state (confirmed, dismissed, discarded, or attached to an existing entry) - a still-incomplete scan keeps its draft indefinitely.
- **Rental tracking and Original Language (added 2026-09-14, `0022_add_rental_and_language_fields.sql`)** - three new fields for a real, specific need: a physical disc can be out on loan to someone at any time, independent of any scan/rescan event (see `scripts/src/backfill-commando-rental.ts`, the one-time backfill for the real "Commando" row currently out on loan). `isCurrentlyRentedOut` is a plain checkbox (same visual as the Watched/Watched Disc checkboxes, in the Checkboxes group) which reveals `rentedByWho` (`AutocompleteInput`, `fieldOptions.rentedByWho`) and `dateRented` (a real native date picker, `@react-native-community/datetimepicker` - the first date field on this screen backed by one rather than free text) directly beneath it when checked. Unticking the checkbox clears both fields immediately in the UI *and* forces them to `null` again at submit time in `manualFields` (same "hide + clear, don't just hide" precedent already established for Special Features Disc Count/Format) - this matters specifically for the Overwrite path: without the clear, unticking the box on a rescan wouldn't actually un-rent the row. All three are sent unconditionally on every scan, shared across a multi-title collection exactly like Disc Condition/Case Notes - they describe the one physical object, not any single film inside it. `original_language` was originally a plain always-visible `AutocompleteInput` field (`fieldOptions.originalLanguage`), manual-only, in the Classification group right after Franchise - **superseded 2026-09-15**, following the same Rating/Studio precedent, once the ISO-code-to-name blocker below got a real fix: `packages/backend/src/iso639.ts` is a static ISO 639-1 -> English-name table (e.g. "en" -> "English"), so `fetchTmdbFieldsById` (already called for Rating/Studio/isAnimated on the same `/movie/{id}` response, genuinely free) now also returns a mapped `originalLanguage`. The field moved out of the Classification group into the same conditional block as Rating/Studio, right after Studio: `showOriginalLanguageField` (`ConfirmScreen.tsx`) hides it whenever `tmdbPreview.originalLanguage` resolves a value, and shows it only when TMDb has no match at all for the title (or, for a multi-title collection, never shows it - each member resolves its own language individually via `resolvedTmdb[i]`, same as Rating/Studio). `original_language_is_manual` (`0023_add_original_language_is_manual.sql`, defaulting `true` on every existing row) is the same protective flag as `rating_is_manual`/`studio_is_manual`: `refreshTmdbFields` only ever overwrites `original_language` on a row where that flag is false. The original blocking reasoning is kept below for context, since it explains why this took a real migration/table rather than a one-line change:
  - TMDb returns a bare ISO 639-1 code ("en", "ja", ...), not a human-readable name, and this field's `AutocompleteInput` suggestions are meant to be whatever the user has already typed in full (per the user's own convention elsewhere on this screen - "English", "Japanese", ...); auto-filling raw codes would either need a full ISO-code-to-name table or produce a mixed vocabulary of codes and names that undermines the autocomplete's own usefulness - `iso639.ts` is that table.
  - Unlike Rating/Studio (genuinely annoying to look up externally per-film), the film's original language is usually obvious and quick to type once, so the auto-fill upside was judged smaller - still worth doing once the table existed, since it's the same free API response either way and removes one more manual field from the common case.
  - **`fieldOptions.ts`'s `rentedByWho`/`originalLanguage` use the plain `distinctSorted` pattern**, not `distinctSortedFlat` - both are scalar single-value columns, not comma-separated multi-value lists like Genre/Franchise, so plain `AutocompleteInput` (whole-field-replace on tap) is the correct component, not `TagAutocompleteInput`.
  - **Date Rented's local-date handling deliberately avoids the ISO-string/UTC round-trip** (`new Date("2026-02-01")`/`.toISOString()` both operate in UTC, which can silently shift the displayed calendar day depending on the device's timezone) - `parseDateOnly`/`formatDateOnly` (local helpers in `ConfirmScreen.tsx`) construct/read the `Date` object via its individual year/month/day components instead, operating entirely in local calendar terms since a date picker's "which calendar day" has no timezone component to begin with.
- **Keyboard avoidance on this screen went through five attempts before settling**: `KeyboardAvoidingView`'s own `"height"` behavior on Android left a blank gap above the keyboard (it double-adjusts on top of Android's native window resize); removing that behavior fixed the gap but let the keyboard cover fields again; `react-native-keyboard-aware-scroll-view` (a dedicated library, meant to fix exactly this) then proved inconsistent in its own right during real testing - sometimes still blocked a field, other times over-corrected and pushed the Confirm button half outside the safe area; a fourth attempt added a static extra bottom padding (`KEYBOARD_SAFETY_PADDING`) as a manual safety margin, but a static value doesn't know the keyboard closed - the user found that scrolling to the bottom with the keyboard open and then closing it left that same dead space permanently, cutting content off or leaving a gap depending on scroll position. Landed on a plain `ScrollView` wrapped in `KeyboardAvoidingView` with `behavior` only set on iOS (`"padding"`) and Android relying entirely on its own native window resize (`app.json`'s `softwareKeyboardLayoutMode`) - explicitly accepting, as a known tradeoff, that the focused field wouldn't automatically snap into view.
  - **That tradeoff turned out not to be acceptable in practice** - the user reported the keyboard blocking lower fields and AutocompleteInput's dropdown results again once they'd used the screen more (reserving room for the keyboard was never the missing piece; nothing ever *moved the scroll position* to bring a field that was already below the fold into that reserved room). Fifth attempt, and the one that actually closes the gap: manual scroll-to-focused-field built directly on RN's own public `UIManager.measureInWindow` (`apps/mobile/src/lib/scrollIntoView.ts`) - deliberately not another third-party library, having already been burned once by `react-native-keyboard-aware-scroll-view`'s own internal inconsistency. A `Keyboard.addListener` pair tracks the live keyboard height (reset to 0 on hide, so it can never go stale the way the static-padding attempt did); every plain `TextInput` on the screen gets a ref and calls `scrollFieldIntoView(findNodeHandle(ref.current))` `onFocus`; `AutocompleteInput` (`apps/mobile/src/components/AutocompleteInput.tsx`) does the same internally via its own wrapping-`View` ref and an `onFocusScroll` prop, called twice (immediately on focus, and again ~120ms later) so the second measurement includes the dropdown's own height once it's actually rendered - the first pass alone would only account for the bare input. The handler measures the focused node's position in the window, compares it against `screen height - keyboard height`, and only scrolls (via a tracked `onScroll` content-offset ref, never React state, to avoid a re-render on every scroll tick) when the node would genuinely be covered - never fights a field that's already visible.

**TV SCANNING**

Designed 2026-09-18. Before this, the scan pipeline was movie-shaped end to end: OMDb's `Type` field (movie/series/episode) was the only live TV signal (translated once in `scan/confirm/route.ts`'s `omdbTypeToMovieOrTv`), TMDb's live lookup (`packages/backend/src/tmdb.ts`) only ever called `/find`'s `movie_results` and `/search/movie`, and `ConfirmScreen.tsx` had a `showTvFields` boolean wired to nothing but one static disclaimer sentence - `season_no`/`part_of_season_no`/`episode_count` were never written by a live scan at all, always landing `null`. The DB columns themselves (`movie_or_tv text`, `season_no text`, `part_of_season_no text`, `episode_count integer`) have existed unchanged since `0001_init.sql` and are already the right shape for everything below.

- **`movie_or_tv` dropdown is always visible on the Confirm screen, pre-filled by best guess but always editable** - not hidden-until-no-match like Rating/Studio. Checked whether IMDb's own site could supply a finer classification than OMDb's coarse movie/series/episode `Type` (which can't distinguish TV Series from TV Mini-Series/TV Special/TV Movie) by reading IMDb's `robots.txt` directly: it disallows the wildcard user-agent site-wide (`Disallow: /*`, with `Allow: /` only granted to specific named bots like Googlebot) with no per-title-page carve-out, so scraping it would violate the same "never scrape against a site's own robots.txt" rule this project already holds itself to for Rotten Tomatoes (see `barcode-scanning-pipeline.md`'s ROTTEN TOMATOES LINK GAPS note) - ruled out. Given that, and given how often the guess will need correcting anyway, the dropdown stays in view rather than hidden.
- **Refined 2026-09-19, three changes at once per the user's own feedback after trying it live**: (1) the whole "Type" section (the dropdown plus Season No./Part of a Season No./Episode Count) moved from near the bottom of the form to right after the best-match/candidate picker, and right before the Title field - so the type is settled early, and the Title suggestion below it (see TV TITLE + SEASON/PART COMPOSITION in `barcode-scanning-pipeline.md`) can already account for it. (2) The guess itself is now reactive to whichever candidate is the *current* best match, not just a one-time guess frozen at mount - a new `useEffect` keyed on `singleSelectedImdbId` re-guesses every time the selected candidate changes (e.g. the user picks a different candidate than the one auto-selected), backing off the moment the field no longer holds the tool's own last suggestion verbatim, same guard pattern as the Title composition effects; never runs at all when a draft or a rescan's already-catalogued value exists, since those are authoritative. (3) The actual input control changed from `SingleSelectChips` (every option shown at once as a row of tappable buttons) to a new `SelectDropdown.tsx` (tap the field, a modal list opens, tap one option, it closes) - the user clarified a row of chips wasn't what they meant by "dropdown box with no text entry." `SingleSelectChips` itself is untouched and still used for Disc Condition, which is a genuinely different shape of control (a small, always-useful-to-see-all-at-once severity scale).
- **Dropdown vocabulary is the real, live distinct values already in the collection**, not just RESOURCES.md's example list - audited via `scripts/src/audit-movie-or-tv-values.ts` (a reusable, read-only script, kept for future re-runs) before trusting the list, per the user's own instruction to normalize first. The audit came back completely clean (0 stale values needing a fix, 0 suspicious near-duplicate clusters) - the existing `MOVIE_OR_TV_ALIASES` normalization already applied on every Sheet sync had kept the column genuinely clean. The real 14-value vocabulary: `Movie`, `TV Series`, `TV Movie`, `TV Mini-Series`, `Documentary`, `Short`, `TV Episode`, `TV Special`, `Live Performance`, `Video`, `Music`, `Sport`, `Sports Recording`, `Live Concert`.
- **`season_no`/`part_of_season_no`/`episode_count` semantics** - see `Claude/RESOURCES.md`'s "TV field semantics refined 2026-09-18" note for the full spec (the "Assorted"/"All"/"Specials" values, the comma-list format, and the syndicated-box-set `part_of_season_no`-as-volume-number exception) - all now enforced going forward via `SEASON_NO_ALIASES`/`normalizeSeasonNo` in `packages/shared/src/titleParsing.ts`, applied on every Sheet sync exactly like `normalizeMovieOrTv`/`normalizeRating`. `episode_count` is disc-scoped (the count on this specific disc/row), never the season's own total.
- **One-time data cleanup that predated this feature**: `scripts/src/backfill-season-no-normalization.ts` (already run) fixed the live Sheet's `season_no` column - migrated "various"/"Various" to "Assorted", normalized "all"/"Specials" casing, converted mis-punctuated multi-season lists ("1 and 2" -> "1,2", "6-7" -> "6,7") via a narrow regex, and hand-resolved three rows that just said the bare word "Multiple" (which doesn't say which seasons at all) by reading each title's own wording - none mentioned covering every season, so all three became "Assorted". The same script also reclassified "Miss Marple: The Blue Geranium"/"Miss Marples: The Pale Horse" from `movie_or_tv="Movie"` (with a stray `season_no="Unknown"`) to `"TV Movie"` with `season_no` cleared - both are BBC TV productions IMDb nests inside a nominal "series" with an "Unknown" season for exactly this kind of entry, which is what made them look wrong in the Sheet; the wider question of whether they should really be modeled as a 2-disc collection of 2 TV movies is flagged in `Claude/To Do list.md`'s BACKLOG for when Collection support is built. Separately, the same audit surfaced that the "long IG" legacy `running_time_mins` value (which the user asked to clear) wasn't TV-specific at all - it appears on ~280 rows across both TV season box sets and plain movie collections, evidently a general personal placeholder for "no single runtime applies to this multi-item disc." Cleared to `"n/a"` everywhere it appeared (both DB effect is a no-op either way - `toInt("long IG")` already parsed to `null`, same as `toInt("n/a")` does now - this was purely a Sheet-readability fix).
- **Running time**: TV entries default to n/a, but the user gives a real value when the disc is genuinely bounded and would play like a single "one-sitting" program (confirmed against 162 real existing TV-typed rows with a runtime already set, audited and reviewed by the user via a one-off Artifact table before this design was finalized - almost all were single/few-episode TV Movies/Specials/Mini-Series with a real meaningful length; the only genuinely ambiguous cluster was 9 `TV Series`-typed rows summing several episodes' runtime, e.g. *Batman and Robin*: 15 episodes -> 263 min). The rule is scope-based, not type-based - a whole open-ended season doesn't get a runtime, a bounded program does, regardless of what `movie_or_tv` value it's filed under.
- **Director vs. Creator/Head-Writer**: the auto-fill source and on-screen label switch based on scope, not simply on `movie_or_tv` being TV-typed. A single-serial/episode-disc entry (the classic-show convention - one row per serial, its own real director, e.g. Doctor Who's individual serials) keeps using Director exactly as today (353 of 469 real TV rows with a `season_no` already have a real per-serial director set this way - switching wholesale would have overwritten a meaningful, intentional existing data pattern). Only a whole-season/show-level entry switches to Creator/Head-Writer, sourced from OMDb's `Writer` field or TMDb's "created by" field rather than OMDb's `Director` (which for a TV series is often blank or just the pilot episode's own director - rarely useful here).
- **Release date for TV**: always the show's own overall first-air date (first episode, first season), regardless of which season/part the specific disc being catalogued actually holds - never that season's own premiere date. In practice this falls out for free as long as `release_date` is sourced from the same full-show OMDb/TMDb lookup the `imdb_page` rule below already requires, since OMDb's series-level entry only ever carries the show's original premiere date, not a per-season one. Noted by the user as the current approach, explicitly subject to revisiting if a reliable per-season air-date source becomes available later - TMDb's `/tv/{id}/season/{n}` endpoint (already used for the Doctor Who season-completeness check in `scripts/src/import-letterboxd.ts`, see `backfill-rescan-and-letterboxd.md`) is a real candidate for that fast-follow.
- **IMDb page for TV**: always the show's own overall IMDb page, never a specific season - IMDb has no separate per-season pages, only per-series and per-episode. A confirmed candidate whose OMDb `Type` is `"episode"` needs its `seriesID` field resolved back to the parent series first, rather than using the episode's own `imdbID` directly - the same resolution point that also has to feed the release-date rule above.
- **TMDb TV lookup, built same day (turned out to be a blocker, not a fast-follow)**: the confirm route has always had a hard requirement that any OMDb-matched entry must resolve to a real TMDb id (so ratings/cast/etc. can be backfilled later without re-touching the disc) - but `lookupTmdbFields`/`findTmdbIdByImdbId` only ever checked `movie_results`, meaning every TV confirmation would have failed this check outright and forced a manual TMDb link on every single TV scan. Fixed properly rather than deferred: `findTmdbIdByImdbId` now also checks `tv_results`, and `fetchTmdbFieldsById` branches to the real TV-shaped endpoints (`/tv/{id}`, `/tv/{id}/content_ratings` - a differently-shaped endpoint from a movie's `/release_dates`, not an oversight). Needed its own schema decision: `tmdb_media_type` (`0028_add_tmdb_media_type.sql`) records "movie"/"tv" explicitly per row, since TMDb's movie and TV id spaces are separate number spaces and the ~5-month `refreshTmdbFields` job needs to know which endpoint a stored id belongs to - backfilled to "movie" for every pre-existing row (the only kind this project could confirm before this). Still not built: using TMDb's own `type` field (Miniseries/Scripted/Documentary/etc.) to refine the `movie_or_tv` *guess* itself beyond OMDb's coarser Type - a real but smaller fast-follow, not a blocker, since the dropdown is always editable regardless.
- **"Serial" category, added 2026-09-18 (same day, follow-up)**: a classic theatrical chapter-play (Republic/Columbia/Universal-style, 1930s-40s) is its own `movie_or_tv` value, not a TV Series subtype - always `season_no` "1", `episode_count` counted the same way TV Series counts it (chapters on this specific disc), and always keeps a real `running_time_mins` (unlike TV Series's n/a default), since a serial's story definitively concludes and online databases present it in "movie" shape with no episode breakdown of its own. Full rule, the rare Doctor-Who-shaped nested-serial case the user's deliberately deferring, and two real bugs found while applying this (an alias-table bug that had been silently erasing the user's own "TV Serial" tagging, and a title-text-matching bug that briefly mislabeled two unrelated same-titled films) are all in `Claude/RESOURCES.md`'s SERIALS note. `SEASON_FIELDS_MOVIE_OR_TV_VALUES` (ConfirmScreen.tsx) includes "Serial" alongside the TV-ish types so the season/episode fields show for it, and a small effect auto-fills `season_no` to "1" the moment "Serial" is picked (same "only if not already typed" guard the disk-region default uses) - matches how OMDb's own `Type` for a serial's imdbID is "movie" (confirmed live against all four titles), same as an ordinary Movie, so auto-detection can never guess "Serial" on its own; the user picks it manually, same as TV Movie already required.
- **Four bugs and two UI reworks found/built 2026-09-19, from the user's first real live TV scan (Doctor Who Season 21)**:
  - **Running Time was being auto-filled for TV Series, contradicting its own documented default.** `/api/scan/confirm/route.ts` set `omdbFields.running_time_mins` unconditionally from OMDb's `Runtime` field regardless of `movie_or_tv` - the n/a-by-default rule above was only ever enforced for the fields ConfirmScreen exposes on a genuinely manual entry (`selected.size === 0`), never for a real OMDb-matched candidate, since the mobile client deliberately never sends `running_time_mins` in that case at all (letting the server's OMDb-derived value win). Fixed by resolving the final `movie_or_tv` classification (`manual.movie_or_tv` if the user picked one, else OMDb's own Type-based guess - same precedence the stored `title.movie_or_tv` already resolves with) before deciding whether to keep the OMDb runtime, and nulling it out specifically when that resolves to `"TV Series"`. Every other category (TV Movie/TV Special/TV Episode/TV Mini-Series/Serial, plain Movie) is unaffected. Note this only fixes it going forward - an already-confirmed row with a wrongly-set TV Series runtime (like the live Doctor Who Season 21 scan that surfaced this) needs a manual fix or a rescan/Overwrite, not a retroactive backfill.

**REQUIRED-FIELD VALIDATION (added 2026-09-20)** - the user asked directly whether anything actually warned about, or blocked confirming, a field that's presented as non-optional (no "(optional)" label) but left blank - there wasn't. Every "required" field previously just fell through to a placeholder-ish server-side default instead (`manual.title ?? omdbFields.title ?? "Unknown Title"` and its siblings in `scan/confirm/route.ts` - "Unknown Title"/"Movie"/"DVD" are never genuinely correct data, just what kept the DB's own `NOT NULL` constraints on `title`/`movie_or_tv`/`format` satisfied). `getMissingRequiredFields()` (`ConfirmScreen.tsx`), checked at the very top of `handleConfirmPressed` - the single choke point every Confirm-button path already funnels through, including the collection and existing-match branches - blocks submission outright and shows a clear message (`error` state, same as the existing TMDb-required check) naming every currently-blank required field at once, rather than the user discovering them one at a time.

- **The required set**: Title (only when it's actually shown - see the Title-visibility note above), Movie or TV, Format, Genre Location, Disk Region, Disc Condition, and (when their own conditional sections are showing) Number/Format of Special Features Discs and Depicted Era. Every check is gated on the field's own real render condition, never a field that's currently hidden - a hidden Title field is never checked at all, since the season-composition effect already guarantees it's synced to the real OMDb title even while unseen.
