**BARCODE SCANNING PIPELINE (Aim One)**

See also: `barcode-review-screen-fields.md` (the review/confirm screen's auto-fill, candidate narrowing, and every per-field design decision) and `backfill-rescan-and-letterboxd.md` (the full-collection backfill rescan and the Letterboxd watched-status import built alongside it).

Blu-ray.com is confirmed to have no API or sanctioned query path at all (their own forum: "Does blu-ray.com provide an API for developers? No" — asked repeatedly since 2018, never changed), and their per-IP scraping tolerance is undocumented and unprotected, so it's excluded entirely as a data source, not just deprioritized.

The user also clarified this isn't just steady-state logging of new purchases — the entire existing collection needs its barcode/case-image data backfilled too, which is a bulk operation, not a trickle. That reshapes the pipeline: **scanning and lookup are decoupled**, so a free API's daily rate limit never gates how fast the user can physically scan their shelves.

**Testing this on a real device requires BOTH dev servers running at once, not just Expo.** `ScannerScreen.tsx` posts to `EXPO_PUBLIC_SCAN_API_URL` (`apps/mobile/.env`), which points at `apps/web`'s own local `next dev` server over the LAN (`http://192.168.1.71:3001` - `npm run dev` defaults to port 3000, so `apps/web` needs to be started as `npx next dev -p 3001` to actually match this, confirmed live 2026-09-18 after the default port left the two dev servers unable to reach each other despite both running) — every scan endpoint (`/api/scan/queue`, `/api/scan/confirm`, `/api/scan/find-existing`, etc.) lives there, not in the Expo/mobile process. Restarting or starting only `apps/mobile` (`npx expo start`) leaves `apps/web` (`npm run dev` from `apps/web`) not running, and the failure this produces is easy to mistake for an app bug rather than a missing process: the countdown and camera UI all work (purely client-side), but the barcode is never actually queued, so the screen never shows "Scanned ... queued for lookup" or any error message either (this exact confusion happened once already — 2026-09-14, testing "Paper Planes"/"Casper's Haunted Christmas" after only the Expo server had been restarted). Before testing any scan, confirm both are up: `npx expo start` in `apps/mobile` AND `npm run dev` in `apps/web`. This is on top of (not instead of) the existing 15-second `[auto-resolve]` poller note below, which is the *other* half of this same "forgot a required background process" failure mode — that one governs how long it takes a queued scan to resolve, this one governs whether it gets queued at all.

1. Expo camera screen (`expo-camera`'s `CameraView`, `barcodeScannerSettings.barcodeTypes: ['ean13','upc_a','upc_e']`, `onBarcodeScanned`, permission via `useCameraPermissions()` — confirmed current for SDK 57; the older `expo-barcode-scanner` package is deprecated/removed since SDK 51) reads the barcode and, once actually committed (see the hold-steady countdown below), writes `{ barcode, scanned_at }` to a new `pending_scans` Supabase table via a secret-gated endpoint, then returns straight to the camera. No network wait, no per-scan lookup — the user can scan hundreds of discs in one sitting.
   - **A 3-second hold-steady countdown gates every scan** (`COUNTDOWN_MS` in `ScannerScreen.tsx`, per the user's own request): the very first sighting of a barcode no longer queues it instantly - `pendingBarcodeRef` tracks `firstSeenAt` for the current hold, and only once the same code has been continuously in frame for the full 3 seconds does it actually queue, showing "Barcode detected - hold steady... N" in the meantime. This exists specifically to avoid queueing a barcode glimpsed only briefly while lining up the shot (a neighbouring disc's code passing through frame, a shaky first attempt at aiming) - only a barcode the user is deliberately holding still counts. `queued` on the same ref then prevents re-firing on every subsequent frame once that hold has already been committed, exactly like before.
   - **A real bug found live (2026-09-14): the countdown froze on its last number if the user moved away from the barcode mid-countdown.** `onBarcodeScanned` only fires while a barcode is actually detected in frame - moving away doesn't fire any "lost sight of it" event, it just stops firing at all - so `pendingBarcodeRef`/the on-screen countdown, both only ever updated reactively from a sighting, had nothing to reset them once sightings stopped. Fixed with an independent `setInterval` (250ms) that polls `pendingBarcodeRef` regardless of whether new sightings are coming in, clearing it and hiding the countdown once the gap since `lastSeenAt` reaches `SIGHTING_GAP_MS` - deliberately reusing that same constant rather than a second, different "gave up" threshold that could disagree with the existing "is this still the same hold" one used the other direction.
   - Two independent debounce layers still prevent duplicate queueing on top of the countdown: `SIGHTING_GAP_MS` (2s, local state inside `ScannerScreen.tsx`) decides whether a new sighting is "still the same hold" (a brief gap between frames) or "you looked away and came back" (resets the countdown for a fresh hold), and `RECENT_QUEUE_COOLDOWN_MS` (5 minutes, per the user's own suggestion) separately remembers every barcode's last-queued time so pointing back at the same case a few seconds or minutes later doesn't create a second `pending_scans` row for it. Both are keyed on the literal barcode value, so two different physical releases of the same film — which necessarily have different barcodes — are never affected by either debounce. The 5-minute map lives in `App.tsx`, not `ScannerScreen.tsx` itself, since `ScannerScreen` unmounts every time the user navigates to Pending Scans and back (App.tsx's screen switch is plain conditional rendering, not a navigator that keeps screens mounted) — local state there would silently reset the cooldown on every trip to review scans. Deleting a pending scan (either the Pending Scans list's bulk delete, or Confirm screen's single discard) also forgets that barcode's cooldown entry immediately, per the user's own request: having just discarded it, they clearly want to rescan it right away rather than wait out the rest of the 5 minutes.
2. A **resolver** (reusable function, called from a manual script, an auto-poller, and, later, a scheduled job) works through `pending_scans` at a safe rate: looks the barcode up against UPCitemdb (chosen UPC/EAN lookup service — free tier, no signup/card, 100 requests/day; the only other options found either have no free tier at all or an undocumented one, and buying UPCitemdb's cheapest paid tier is $99/mo, which is only worth it as a one-time month if the free-tier backfill drain feels too slow later — not decided now), then cross-references OMDB for movie metadata (OMDB prioritized over IMDB per RESOURCES.md, since OMDB has a public API and IMDB doesn't) using OMDB's own `Type` field (`movie`/`series`/`episode`) to know whether TV-only fields even apply. Marks each pending scan `resolved` (found confident candidates) or `needs_manual` (nothing confident found).
   - **Auto-polling in `apps/web`**: `instrumentation.ts`'s `register()` hook (a stable Next.js server-boot hook, not a route) starts a 15-second `setInterval` that calls the resolver on whatever's pending (batch limit 20) for as long as `next dev`/the deployed server process is running — this replaced repeatedly running `npm run resolve-scans` by hand during real-device testing, which was mistaken for a bug ("I scanned it but it's not showing up") more than once before this existed. Deliberately still a poll rather than resolving on every `/api/scan/queue` call, so scanning and lookup stay decoupled and a bulk shelf-scanning burst can't blow through UPCitemdb's 100/day cap just by scanning fast — a big backlog drains gradually over many ticks instead of firing one lookup per scan back-to-back. The manual script and `/api/scan/resolve` route both still exist (the route is what a Vercel Cron job will call once deployed, superseding this poller then).
3. A pending-scans review screen (mobile) lists resolved/needs-manual entries; the user confirms the suggested match, edits fields, or fills in manually — mirroring Claude's own clarifying-question style per STEP BY STEP PROCESS AND AUTOMATION.md (skipping fields that don't apply, e.g. never asking for a season number on a movie).
4. **Review-screen auto-fill and candidate narrowing** — see `barcode-review-screen-fields.md` for the full design (title/format pre-fill, year-based candidate narrowing, cover-photo auto-matching, every autocomplete/normalized field, TMDb-sourced Rating/Studio/Franchise/Animation, the manual title-search + typo-correction fallback, and the full-collection backfill rescan + Letterboxd import built alongside it).
5. **Collections** (built 2026-09-20, replacing the franchise-name-search design originally described here - see below for that superseded idea): since individual titles inside a box set have no barcode of their own, `ConfirmScreen` has an entirely separate flow for a collection scan rather than trying to auto-search OMDB for the box set as a whole:
   - **A manual toggle** ("This is a collection / box set"), defaulting from `looksLikeCollection`'s own keyword-heuristic guess (`packages/shared/src/omdb.ts` - checks the UPC listing's own title text for "collection"/"box set"/"trilogy"/"N-film"/etc.) but always overridable - the heuristic can misfire both ways (a standalone film whose own title contains "Trilogy"; a real box set whose listing text uses none of the trigger words). `scanResolver.ts` skips the OMDB search entirely once `looksLikeCollection` is true (searching a box set's own listing text against OMDB almost never matches a real film, and poster auto-matching was already skipped for a collection scan before this) - `status` stays `needs_manual` for a real collection scan, since ConfirmScreen drives the whole flow from its own UI state rather than resolved candidates.
   - **A shared physical-fields step, filled in once**: Genre Location, Disk Region, Release Variant Note, Disc Condition, Case Notes, Steelbook, and rental tracking apply identically to the header row and every member - per the user's own reasoning, a physical box set is one object that can't sit in two shelf locations at once. Genre Location in particular is a **hard-shared** field (not just a default), for the same reason - it's also filtered by media type (see below). **Release Name moved OUT of this shared bucket (2026-09-20)** - the header keeps its own (the box's own edition name), but each member now gets its own independent Release Name field in `TitleSearchPicker`, since the user pointed out a definitive/remastered cut of one specific film can be bundled into an otherwise-ordinary box set.
   - **Genre Location is filtered by media type in the dropdown (added 2026-09-20)** - the user started prefixing shelf-location names to disambiguate ambiguous shelf sections that share a genre name across formats: "TV " in front of every TV-only location (e.g. "TV Sci-Fi", distinct from the movie "Sci-Fi" shelf), "COLLECTION " in front of every collection-only location (e.g. "COLLECTION Person" - box sets grouped by the actor/director they're about), no prefix for a plain movie location. `filterGenreLocationOptions` (ConfirmScreen.tsx) filters the dropdown to only the locations that apply to whatever's currently being catalogued (a collection scan only ever sees `COLLECTION `-prefixed options; an ordinary scan sees `TV `-prefixed or unprefixed depending on `movie_or_tv`) - applies to both the collection flow and the ordinary single-title flow.
   - **A title in a collection shares the box's own barcode (added 2026-09-20)** - individual titles inside a box set have no barcode of their own, so per the user's explicit request, `performCreateCollection` sets every member's own `barcodeId` to the same barcode the box itself was scanned with, alongside the header. Lets a future rescan of any single disc from the set resolve back to it via the existing barcode fast-path.
   - **Format, Disc Count, and Special Features exist at BOTH the collection level and the per-title level (revised 2026-09-20, the day after first shipping)** - originally hard-shared like the fields above, corrected once the user was actually mid-scan on a real box set where every title had its own separate 4K UHD disc plus its own Blu-ray special-features disc: a box set is one physical *case*, but the discs inside routinely belong to individual titles, not the box as a whole, so a single shared value for these three couldn't represent that at all. The header's own `format` still describes the box in general (a plain manual field), and its own Special Features (+ sub-fields) describe a bonus disc belonging to the *collection itself*, separate from any title's own - per the user directly, "a collection can have a special features disk for the whole set and a title can have a special features disk for that particular title." The header's own `disc_count` is no longer manually typed at all - it's computed live as the true total of every physical disc in the box (every title's own Disc Count, summed, plus the collection's own bonus disc(s) if it has one). Each title's own Format/Disc Count/Special Features are asked in `TitleSearchPicker` when it's added, seeded from the previously-added title's own values (or the header's shared-step values for the very first title) as a starting guess - still fully editable per title, which is what actually lets titles with a genuinely different disc pattern coexist in the same box.
   - **Name of Collection** (moved to the very top of the form, above Shared Details, 2026-09-20): a plain, always-editable free-text field, pre-filled from the box's own cleaned listing title - not the franchise-search idea below. The Collection Type dropdown and the Watched Collection/Watched Collection Disc checkboxes sit right below it, so the whole "what is this collection" decision happens in one place before the shared physical fields or the per-title loop, both of which read this state. **The colon-suffix disambiguation convention (below) is now generated automatically at submit time (fixed 2026-09-18, found live via the real Hitchcock collection), not typed in by hand** - `performCreateCollection` appends `": " + <every current member's own title, comma-separated>` onto whatever the user typed here, for both the header's `title` and `name_of_collection` (which must match exactly across the header and every member, since it's the join key the collection-header fuzzy match and the Sheet aggregation both group by). The duplicate-check search itself (`handleConfirmCollectionPressed`) still searches on the plain typed name alone - the member-title-overlap signal already covers the rest, so including it twice would double-count.
   - **A per-title "add a title" loop**: `TitleSearchPicker` (`apps/mobile/src/components/TitleSearchPicker.tsx`) is a small standalone search UI (deliberately not a reuse of ConfirmScreen's own single-title search block, which is entangled with logic - the TMDb-override requirement, season/title auto-composition - that doesn't apply to a collection member) invoked once per title: search OMDB/TMDb, pick a candidate or fall through to manual entry, set Movie/TV type + season fields if TV-ish, then straight to "Add to set" - no duplicate check happens here (see below). Each member keeps its own real, verbatim `title` (confirmed against the live data - e.g. "The 39 Steps", "Sabotage") and its own `imdb_page`/`tmdb_id` resolved independently, exactly as a normal single scan would.
   - **Watched Collection / Watched Collection Disc**: no new columns - the header row's own `watched`/`watched_disc` (the same columns every title row has) are relabeled in this context, per the user's exact spec: checking either one by hand cascades that value onto every current member's own Watched/Watched Disc; separately, each one auto-derives back to checked only once every member's own value agrees (added/removed/toggled members recompute this live), and back to unchecked the moment any member no longer agrees. **Once either is already checked, a newly-added title's own Watched/Watched Disc checkboxes don't even show up in `TitleSearchPicker` any more (added 2026-09-20)** - they default to matching instead of asking again for something already declared true for the whole set. Watched Collection Disc implies both fields for the new title; Watched Collection alone only implies Watched (watching the film doesn't necessarily mean via this specific disc, so Watched Disc is still a real, visible question in that case). Either checkbox can still be overridden per-title afterward from the running member list, in case one title genuinely differs.
   - **Duplicate detection, scoped to collections only, resolved as ONE decision for the whole collection (redesigned twice, both 2026-09-20)** - first moved from per-title (inside `TitleSearchPicker` at add time) to Confirm time as a queue of one Overwrite/New-Entry question per matched entry; the user then pointed out even that was one question too many - "as if done correctly all the titles that the system asks to overwrite or leave are part of collections anyway." Final design: `handleConfirmCollectionPressed` runs a single collection-scoped `findExistingTitle` check for the HEADER only, passing the collection's own current member titles as `collectionMemberTitles`. `/api/scan/find-existing` matches a collection header very differently from an ordinary title (see its own doc comment) - not exact text equality, but a fuzzy score combining name similarity (`textSimilarity`, a Dice coefficient over normalized word tokens, format-noise-words stripped), a format-match bonus, and - the strongest signal - how many of the new collection's own member titles exactly match an existing member already catalogued under a candidate's own `name_of_collection`. This exists specifically because a real box set was found to fail exact-title matching once already (see the BACKFILL note below). A "none" result skips straight to submission with no overwrite decisions. A real match shows ONE screen ("Matches an existing collection") with an Overwrite/Is-a-new-entry choice for the WHOLE collection: choosing Overwrite resolves the header to the chosen candidate, then independently matches each of the new collection's own members against that candidate's own already-catalogued members (`existingMemberTitles`, returned alongside the match) by exact normalized title - a match becomes that member's own overwrite target, no match means it's a genuinely new addition to the collection (adding a title a partially-catalogued box set didn't have yet, never blocked). `scopeToCollections: true` still filters candidates to `is_collection || title_in_a_collection` rows generally, so a collection/member is only ever compared against other collections/collection members, never a standalone title. `/api/scan/confirm`'s `overwriteUniqueId` moved from a single request-level field to a per-entry one (`ConfirmEntry.overwriteUniqueId`) to support this - a collection submission can mix fresh-insert entries with overwrite-in-place ones in one request.
   - **Collection header aggregation (added 2026-09-20)** - `/api/scan/confirm` computes several of the header row's own fields from its members' final resolved values, right before writing (the confirm route's per-entry loop first builds every entry's own row in memory without writing anything, then aggregates the header, then writes everything - so the header can read values the write loop hasn't touched the database with yet): **Genre** and **Franchise** are the union of every member's own values (order-preserving dedup, not an intersection - a collection is worth finding under any genre/franchise any of its titles belong to). **Director** is the single most-common value across every member (a tie or no repeated value leaves it empty - never guesses). **Studio** is the most-common value among every member's own TMDb-resolved studio; if there's no single most-common one, falls back to the header's own manual "Distributor" field (the box's real-world publisher, e.g. Universal - confirmed directly with the user this is a genuinely different fact from any one film's own original production company, which is what "most common among members" actually measures); if neither, "n/a". **Special Features** becomes `true` the moment ANY member has its own special features disc (in addition to the header's own toggle, which describes a bonus disc belonging to the collection itself, never overridden back to false by this). **Disc Count** is the real total of every member's own disc count, summed, plus the header's own bonus-disc count if it has one - no longer a value the user types in at all. **Personal Rating** is the average of every member's own (only when every single member is both watched AND already has a real personal_rating - a partial set doesn't produce a meaningful average). **Last Watched Date** is the latest among every member's own real date. The last two read from the EXISTING row being overwritten when a member's own duplicate resolved to Overwrite (a fresh insert has neither yet) - see the Overwrite-protection note below for why this data survives an Overwrite at all. **Rating** is NOT aggregated - always a plain manual field on the header (there's no TMDb id for a header to auto-fill it from), required before Confirm.
   - **Overwrite can never erase Letterboxd-derived watched status, on ANY scan (added 2026-09-20, universal - not just Collections)** - found live: `watched`/`watched_disc` are explicitly sent on every scan submission (unlike `personal_rating`/`last_watched_date`, which are never part of the write payload at all and were therefore always already safe - Supabase's `.update()` only touches keys actually present), so an Overwrite whose own current form state doesn't happen to have them checked would otherwise silently blank out real Letterboxd history. Fixed in `/api/scan/confirm`: before building an Overwrite's own row, the existing row's current `watched`/`watched_disc` are fetched and OR'd into the final value - an Overwrite can only ever ADD watched status, never remove it, matching the user's own words: "the letterboxd data takes priority."
   - **TMDb's NZ rating certification is now validated, not trusted blindly (added 2026-09-20)** - found live: real rows for Psycho and The Birds had "R"/"PG-13" written from TMDb's own `iso_3166_1 === "NZ"` certification slot, neither a real NZ classification (this collection's real scheme is G/PG/M/R12/R13/R15/R16/R18) - TMDb's NZ data is itself crowdsourced and can carry a mistagged non-NZ code. `packages/backend/src/tmdb.ts` now checks the certification against the real NZ scheme before accepting it; an invalid code is treated the same as "no NZ certification at all" (returns null), which already correctly reveals ConfirmScreen's manual Rating field instead of silently writing a wrong classification.
   - `name_of_collection`'s disambiguation convention (when a box set's own name is too vague to be unique on its own, e.g. "Hugh Grant Collection 4 Favourites" — there could be more than one box set with that same base name over time) is now applied unconditionally to every collection, not just an ambiguous one - see the automatic-generation note above.
   - **A collection member's Estimated Value Sheet cell now shows "n/a" instead of sitting blank forever (fixed 2026-09-18)** - found live: these rows are deliberately never priced (ELIGIBILITY in estimated-value.md), and the only thing that normally writes that Sheet cell is the async pricing job's own push, which explicitly skips `title_in_a_collection` rows - so a member's cell simply never got touched by anything, ever. `/api/scan/confirm` now writes `formatEstimatedValueCell(null, false)` ("n/a") to it directly, synchronously, right after each member's own insert/update, since that value is already fully known and never depends on the async job the way a priced title's real value does. Only ever writes to the Sheet, never Supabase (`estimated_value` there was already correctly `null`). A one-time follow-up (`scripts/src/backfill-collection-followup-fixes.ts --header-only`) fixed the real Hitchcock header's own name/special_features (see the BACKFILL note below) but deliberately did NOT mass-backfill the ~948 pre-existing collection-member rows across the whole collection also missing this - per the user's own explicit choice, that's left for each of those collections' own future rescans instead.
   - **Deferred, disclosed rather than silently skipped**: per-MEMBER studio selection still uses TMDb's own single "first-listed production company" per film, unchanged - the user separately asked for each member's own studio to instead prefer whichever company is most common across *every* member's own full TMDb production-company list (not just each film's own first-listed one), falling back to the current per-film logic when no cross-member consensus exists. Building this needs `TmdbFields`/`fetchTmdbFieldsById` extended to return each film's *entire* company list (currently only the first is kept at all), plus a second cross-referencing pass once every member's own list is known - a real, scoped follow-up, not attempted this pass given everything else already changing in the same session.
   - **BACKFILL (2026-09-20)**: the real "Alfred Hitchcock Classics" box set scanned before several of the fixes above existed needed a one-time repair script (`scripts/src/backfill-hitchcock-collection-fix.ts`, already run) - the header's aggregated fields (computed by hand, matching what the fixed algorithm now produces automatically), each member's barcode/number_of_titles_in_collection/release_name, Psycho and The Birds' real NZ ratings (R13 and M respectively, confirmed directly by the user against their own physical discs - an initial lookup against the NZ Film & Video Labelling Body's public register suggested R13 wasn't needed and returned PG/M instead for a same-day Blu-ray batch, but the user's own copies are the authoritative source and said otherwise), and deleting a pre-barcode legacy stub row for the exact same physical box that the collection-matching algorithm couldn't find at scan time (no shared barcode, and its own exact title text didn't match what was typed for the new scan) - exactly the gap the new fuzzy header-matching above now closes for future scans.
   - **BACKFILL ROUND 2 (2026-09-18, same evening)**: testing the already-fixed real Hitchcock row surfaced that it still didn't reflect three more gaps found and fixed later the same session - `scripts/src/backfill-collection-followup-fixes.ts --apply --header-only` (already run) corrected just that one header's `title`/`name_of_collection` (now the full colon+comma-list form) and `special_features` (now `true`, matching all 4 real members). Confirmed via direct query that this was purely a backfill-timing gap, not a live-algorithm bug - the confirm route's own aggregation already handled `special_features` correctly for any collection scanned through the real flow; this one row simply predated that code, having been hand-written by round 1's own repair script before round 1 itself even existed in its final form.
   - **Nothing is written to Supabase/the Sheet until Confirm is pressed and every duplicate in the queue (if any) is resolved** - per the user's own explicit requirement, the collection header and every one of its titles are pushed to the database in one single request (`performCreateCollection`), never incrementally as titles are added. This was already true even before the requirement was stated explicitly (adding a title only ever updated local component state), and remains true now that the per-title duplicate check - the only network activity that used to happen during the add loop - has moved to Confirm time too.
   - Deliberately **not** built this pass, disclosed as a scope cut rather than an oversight: a collection scan is online-only (not wired into `offlineQueue.ts` - that queue's resync logic is built around a single title-text match/single overwrite target, which doesn't fit a submission whose per-entry overwrite decisions are already resolved live before submission); and a real merge-into-an-already-catalogued-row write path for a *pre-existing* member found by the duplicate check (today it's Overwrite-the-whole-row or a plain new insert, same as the single-title flow already offers, not a scoped 3-column patch).
   - **Superseded idea, kept for context**: the original plan here was to strip filler words from the collection's product title to extract a likely franchise/director/actor name, search OMDB for that, and present the results as an auto-populated checklist. The user explicitly dropped this in favor of the manual per-title loop above - the auto-search idea's candidate list would often be either empty or unmanageably large (e.g. searching "Marvel") with no reliable way to know which, and never actually shipped as functional (the "checklist" ConfirmScreen had before this date read from the same weak box-listing OMDB search this point now skips entirely, so it was effectively always empty in practice).
6. **Documentary chronology**: the user's physical shelf splits documentaries into a contemporary/alphabetical section and a "History Documentary" section ordered by the era each one *depicts* (often explicit in the title/synopsis — "The Spanish Civil War", "1936-1939"). A nullable `depicted_era_start` (integer year) column on `titles` is prefilled by a regex pass over the title+synopsis looking for a year/decade/range, falling back to a manual field when nothing is found — no LLM/AI inference call added for this, the regex-plus-manual-fallback approach covers what the user described.
7. On confirm, the completed entry (and every checked title in a collection) is written to Supabase, then to the Sheet.
8. **Similar/matching-entry check** (single-title scans only, not yet extended to collections) - see `backfill-rescan-and-letterboxd.md` for the full current design (this replaced the original narrower "backfill matching/attach" design: exact-title-only, un-barcoded rows only, a conservative field-by-field refresh). The current version matches by base title text OR a shared `imdb_id`, across every row (barcoded or not), shows a poster + key-field comparison against the matched existing entry, and offers three explicit choices: Overwrite (replace every field of the existing row with this scan's data), Is a new entry (a genuine second copy - proceeds to create a new row as normal), or Reject (discard this scan, touch nothing).
9. Shelf-location suggestion: alphabetical order within `genre_location`, except when `genre_location` is the History Documentary bucket, which orders by `depicted_era_start` instead.
10. The scanner returns to the camera view, ready for the next disc.

Note: neither Rotten Tomatoes nor Letterboxd exposes a public API. Their scores are needed for search/sort (WEB APP DESIGN.md's Advanced Search filters) but not for identifying a disc, so fetching those can happen asynchronously after the entry is created rather than blocking the scan flow.

**ROTTEN TOMATOES LINK GAPS - A KNOWN, RECURRING LIMITATION (found 2026-09-18)** - the user scanned "The Day the Earth Stood Still" and found it had no `rotten_tomatoes_page` saved despite RT genuinely having a page and score for it. Investigated directly rather than guessing: `packages/backend/src/rottenTomatoes.ts`'s `lookupRottenTomatoesPage` (called from `scan/confirm/route.ts` right after OMDB's own `Ratings` array confirms a critics score exists) has no real RT search to fall back on - Rotten Tomatoes' own robots.txt explicitly disallows `/search`, and this project has consistently respected every site's robots.txt throughout the whole barcode/Estimated Value pipeline, so scraping RT's search results the way a plain `/m/<slug>` page can be fetched isn't an option here. Instead it guesses a slug from the title text (`the_day_the_earth_stood_still`) and only accepts the guess if the resulting page's own JSON-LD both names the same film and reports the same score - "wrong link is worse than no link," the same convention every scraper in this codebase follows.

For this specific film, RT's real slug is `1005371-day_the_earth_stood_still` (a numeric-ID prefix, confirmed live via `curl` - the guessed slug returns a flat 404, and two much older Sheet-imported rows for the same 1951 film already carry the correct link, almost certainly typed in by hand well before this automation existed). This isn't a one-off bug in the code - the lookup behaved exactly as designed and correctly returned `null` rather than a wrong link - it's a genuine, structural limitation of guessing-from-title-text that will keep recurring for any film whose real RT slug is irregular (a numeric prefix, a dropped article, non-standard punctuation handling, etc.), and there's no better automated fix available within this project's own scraping-ethics constraints (no `/search` scraping, no headless browser).

**NON-MEDIA BARCODE WARNING (added 2026-09-19)** - `upcLookup` (`packages/shared/src/upc.ts`) previously discarded UPCitemdb's own `category` field entirely, so nothing in the pipeline could tell a genuine DVD/Blu-ray listing apart from a barcode that just happens to belong to some unrelated product (scanned by accident, or a coincidental UPC collision). Now kept, and checked by `looksLikeNonMediaCategory` - a deliberately soft, **warn-don't-block** signal, not a hard rejection: tested live against a real DVD already in this collection ("Blade Runner The Final Cut") and found UPCitemdb had it filed under `"Electronics > Video > Video Players & Recorders > DVD & Blu-ray Players"` - hardware, not "Movies" - which is exactly the kind of inconsistent crowdsourced categorization that would make a hard block actively harmful (it would have rejected a real, correct scan). The check is therefore an **allowlist of media keywords** (movie/film/TV/DVD/Blu-ray/VHS/video/media/CD) rather than a denylist of "known bad" categories, and treats a *missing* category (the common case - most listings this project scans don't have one at all) as "unknown," never "suspicious." When it does trigger, `ConfirmScreen.tsx` shows an amber warning banner (same style as `OfflineBanner.tsx`) naming the real category UPCitemdb returned, and leaves the decision to the user - Confirm is never disabled by this.

**TV TITLE + SEASON/PART COMPOSITION (added 2026-09-19)** - OMDb only ever has one entry per whole show, never one per season, so before this, matching (or manually searching for) a real TV candidate left the catalogued `title` as just the bare show name ("Breaking Bad") with no way to tell two season discs of the same show apart - found by the user immediately after their first live TV scan test. `ConfirmScreen.tsx`'s Title field (previously only shown for a fully-manual entry with no candidate at all) is now shown whenever there's zero or exactly one real candidate selected, and auto-suggests `"<Show> Season <N>"` (plus `" Part <N>"` when Part of a Season No. is set) the moment a single TV-ish candidate is picked and Season No. is filled in - always fully editable, never enforced, since this collection's own real titles already use several different phrasings for the same idea ("Season N", "Series N", "the Complete Nth Season", a bare number with no word at all for old syndicated box sets). Two effects handle this: a hard reset the moment the selected candidate itself changes (so it always starts from a fresh, correct suggestion), and a soft update as Season No./Part of a Season No. change afterward that backs off the instant the field no longer matches the tool's own last suggestion verbatim - so it never fights a further manual edit.

Running the new audit script the same day surfaced this is a **broader, ongoing gap, not an isolated case** - `scripts/src/find-missing-rotten-tomatoes.ts` (read-only, `npm run find-missing-rotten-tomatoes --workspace=scripts`) found on the order of dozens of titles across the collection with a real Rotten Tomatoes score OMDB already confirms, but no link saved, spanning old Sheet-import-era rows and freshly-scanned ones alike. Since there's no way to close this gap automatically without violating the project's own robots.txt discipline, the fix is procedural rather than code: **run this script occasionally, manually search Rotten Tomatoes for each title it lists, and paste the real URL into that title's cell in the Sheet** (which flows back into Supabase through the existing webhook - no separate write path needed). This is the same "surface an automation gap for human review instead of leaving it silently wrong" pattern already established for Estimated Value's AUTO-ESTIMATED NOTE (`estimated-value.md`).

**UPC LISTING TEXT PARSING - ONGOING, ITERATIVE (2026-09-19)** - the user's own framing: UPCitemdb's listing text has "inconsistent formatting and different types of information every time," so this is treated as an ongoing effort to notice more extractable signal in real listings over time, not a one-shot fix - the user explicitly said they'll give hints from future scans if something still isn't picked up. First real case: a scan of "Resident Evil: Extinction" came back with **zero OMDB candidates at all** (not even a wrong one) and none of the extractable listing detail got auto-filled - investigated by pulling the actual stuck `pending_scans` row directly from Supabase rather than guessing, which had UPCitemdb's real listing title: `"Resident Evil: Extinction [regions 2,5] - Dvd - - Free Shipping."`.

- **Root cause, confirmed live via direct OMDB queries**: `cleanProductTitleForSearch` (`packages/shared/src/omdb.ts`) left `"[regions 2,5]"` completely untouched - its region-stripping pattern only ever matched the literal singular word "region " followed by one alnum token (`region [a-z0-9]+`), never the plural "regions", never a comma-separated list, and square-bracketed listing metadata was never stripped at all (only round-bracketed `(...)` was, via a separate step). The resulting search query - `"Resident Evil: Extinction [regions 2 5] - - - ."` after the surviving noise-words were stripped from around it - returned "Movie not found!" from OMDB outright, confirmed by querying OMDB directly with both the garbled and a properly-cleaned version side by side. Fixed by broadening the region pattern to a comma/slash/ampersand/hyphen-separated list after "region(s)", stripping `[...]` alongside `(...)`, and cleaning up the stray standalone `" - "` separators and trailing punctuation left behind once the words between them are gone.
- **A real regression trap avoided while fixing this**: an early version of the broadened region pattern would have also swallowed an unrelated adjacent digit (e.g. "region 4, 2015 edition" capturing both "4" and "2" as if both were region codes) - caught by testing multiple real and synthetic listings side by side before committing to the final regex shape, not just the one example that prompted the fix.
- **New auto-fill, not just a bug fix**: per the user's actual ask ("find what information can be taken from that string and used to auto fill the form"), the bracketed region text itself is a genuine, previously-wasted signal - `extractDiskRegionHint` (`packages/shared/src/formatHints.ts`) now pulls real region code(s) directly out of a listing's own text (`"[regions 2,5]"` -> `"2, 5"`, `"(Region A)"` -> `"A"`, `"Region Free"` -> `"All"`) and pre-fills `ConfirmScreen.tsx`'s Disk Region field, same draft/existingMatch precedence and same "still fully editable" convention as every other auto-filled field. Deliberately conservative rather than a single greedy capture: only matches genuinely standalone single-character codes (`\b[1-6]\b` for DVD, `\b[A-C]\b` for Blu-ray - word-bounded on both sides, so a digit embedded in a longer number like "2015" can never match) within a short window right after the word "region"/"regions", and only for whichever scheme is actually valid for the disc's own resolved `format` (mirrors `getDiskRegionOptions`) - never for UHD, which has no per-title region scheme of its own to extract (`isRegionFreeFormat` already covers that case separately).
- **A live end-to-end verification trap, worth remembering**: after fixing the code, re-triggering `/api/scan/resolve` against the running `next dev` server still returned zero candidates for a first retry - not because the fix was wrong (confirmed correct by importing and running the real, unmodified `cleanProductTitleForSearch`/`omdbSearch` functions directly via `tsx`, outside Next.js entirely, which produced the correct 4 real candidates), but because the already-running dev server process hadn't picked up the change to `packages/shared` - a workspace package outside `apps/web`'s own directory - even though it compiles from source with no separate build step. Restarting the dev server (stop, confirm the port is actually free - the same orphaned-process gotcha noted earlier in this file, `taskkill` was needed again - then start fresh) picked up the fix immediately, and re-resolving the same stuck scan then returned the correct 4 real OMDB candidates for real. Worth checking first next time a fix that touches `packages/shared`/`packages/backend` doesn't seem to take effect against a long-running dev server, before assuming the code itself is wrong.
