**BARCODE SCANNING PIPELINE (Aim One)**

See also: `barcode-review-screen-fields.md` (the review/confirm screen's auto-fill, candidate narrowing, and every per-field design decision) and `backfill-rescan-and-letterboxd.md` (the full-collection backfill rescan and the Letterboxd watched-status import built alongside it).

Blu-ray.com is confirmed to have no API or sanctioned query path at all (their own forum: "Does blu-ray.com provide an API for developers? No" — asked repeatedly since 2018, never changed), and their per-IP scraping tolerance is undocumented and unprotected, so it's excluded entirely as a data source, not just deprioritized.

The user also clarified this isn't just steady-state logging of new purchases — the entire existing collection needs its barcode/case-image data backfilled too, which is a bulk operation, not a trickle. That reshapes the pipeline: **scanning and lookup are decoupled**, so a free API's daily rate limit never gates how fast the user can physically scan their shelves.

**Testing this on a real device requires BOTH dev servers running at once, not just Expo.** `ScannerScreen.tsx` posts to `EXPO_PUBLIC_SCAN_API_URL` (`apps/mobile/.env`), which points at `apps/web`'s own local `next dev` server over the LAN (`http://192.168.1.71:3001` - `npm run dev` defaults to port 3000, so `apps/web` needs to be started as `npx next dev -p 3001` to actually match this, confirmed live 2026-09-18 after the default port left the two dev servers unable to reach each other despite both running) — every scan endpoint (`/api/scan/queue`, `/api/scan/confirm`, `/api/scan/find-existing`, etc.) lives there, not in the Expo/mobile process. Restarting or starting only `apps/mobile` (`npx expo start`) leaves `apps/web` (`npm run dev` from `apps/web`) not running, and the failure this produces is easy to mistake for an app bug rather than a missing process: the countdown and camera UI all work (purely client-side), but the barcode is never actually queued, so the screen never shows "Scanned ... queued for lookup" or any error message either (this exact confusion happened once already — 2026-09-14, testing "Paper Planes"/"Casper's Haunted Christmas" after only the Expo server had been restarted). Before testing any scan, confirm both are up: `npx expo start` in `apps/mobile` AND `npm run dev` in `apps/web`. This is on top of (not instead of) the existing 15-second `[auto-resolve]` poller note below, which is the *other* half of this same "forgot a required background process" failure mode — that one governs how long it takes a queued scan to resolve, this one governs whether it gets queued at all.

1. Expo camera screen (`expo-camera`'s `CameraView`, `barcodeScannerSettings.barcodeTypes: ['ean13','upc_a','upc_e']`, `onBarcodeScanned`, permission via `useCameraPermissions()` — confirmed current for SDK 57; the older `expo-barcode-scanner` package is deprecated/removed since SDK 51) reads the barcode and, once actually committed (see the hold-steady countdown below), writes `{ barcode, scanned_at }` to a new `pending_scans` Supabase table via a secret-gated endpoint, then returns straight to the camera. No network wait, no per-scan lookup — the user can scan hundreds of discs in one sitting.
   - **A 3-second hold-steady countdown gates every scan** (`COUNTDOWN_MS` in `ScannerScreen.tsx`, per the user's own request): the very first sighting of a barcode no longer queues it instantly - `pendingBarcodeRef` tracks `firstSeenAt` for the current hold, and only once the same code has been continuously in frame for the full 3 seconds does it actually queue, showing "Barcode detected - hold steady... N" in the meantime. This exists specifically to avoid queueing a barcode glimpsed only briefly while lining up the shot (a neighbouring disc's code passing through frame, a shaky first attempt at aiming) - only a barcode the user is deliberately holding still counts. `queued` on the same ref then prevents re-firing on every subsequent frame once that hold has already been committed, exactly like before.
   - **A real bug found live (2026-09-14): the countdown froze on its last number if the user moved away from the barcode mid-countdown.** `onBarcodeScanned` only fires while a barcode is actually detected in frame - moving away doesn't fire any "lost sight of it" event, it just stops firing at all - so `pendingBarcodeRef`/the on-screen countdown, both only ever updated reactively from a sighting, had nothing to reset them once sightings stopped. Fixed with an independent `setInterval` (250ms) that polls `pendingBarcodeRef` regardless of whether new sightings are coming in, clearing it and hiding the countdown once the gap since `lastSeenAt` reaches `SIGHTING_GAP_MS` - deliberately reusing that same constant rather than a second, different "gave up" threshold that could disagree with the existing "is this still the same hold" one used the other direction.
   - Two independent debounce layers still prevent duplicate queueing on top of the countdown: `SIGHTING_GAP_MS` (2s, local state inside `ScannerScreen.tsx`) decides whether a new sighting is "still the same hold" (a brief gap between frames) or "you looked away and came back" (resets the countdown for a fresh hold), and `RECENT_QUEUE_COOLDOWN_MS` (5 minutes, per the user's own suggestion) separately remembers every barcode's last-queued time so pointing back at the same case a few seconds or minutes later doesn't create a second `pending_scans` row for it. Both are keyed on the literal barcode value, so two different physical releases of the same film — which necessarily have different barcodes — are never affected by either debounce. The 5-minute map lives in `App.tsx`, not `ScannerScreen.tsx` itself, since `ScannerScreen` unmounts every time the user navigates to Pending Scans and back (App.tsx's screen switch is plain conditional rendering, not a navigator that keeps screens mounted) — local state there would silently reset the cooldown on every trip to review scans. Deleting a pending scan (either the Pending Scans list's bulk delete, or Confirm screen's single discard) also forgets that barcode's cooldown entry immediately, per the user's own request: having just discarded it, they clearly want to rescan it right away rather than wait out the rest of the 5 minutes.
2. A **resolver** (reusable function, called from a manual script, an auto-poller, and, later, a scheduled job) works through `pending_scans` at a safe rate: looks the barcode up against UPCitemdb (chosen UPC/EAN lookup service — free tier, no signup/card, 100 requests/day; the only other options found either have no free tier at all or an undocumented one, and buying UPCitemdb's cheapest paid tier is $99/mo, which is only worth it as a one-time month if the free-tier backfill drain feels too slow later — not decided now), then cross-references OMDB for movie metadata (OMDB prioritized over IMDB per RESOURCES.md, since OMDB has a public API and IMDB doesn't) using OMDB's own `Type` field (`movie`/`series`/`episode`) to know whether TV-only fields even apply. Marks each pending scan `resolved` (found confident candidates) or `needs_manual` (nothing confident found).
   - **Auto-polling in `apps/web`**: `instrumentation.ts`'s `register()` hook (a stable Next.js server-boot hook, not a route) starts a 15-second `setInterval` that calls the resolver on whatever's pending (batch limit 20) for as long as `next dev`/the deployed server process is running — this replaced repeatedly running `npm run resolve-scans` by hand during real-device testing, which was mistaken for a bug ("I scanned it but it's not showing up") more than once before this existed. Deliberately still a poll rather than resolving on every `/api/scan/queue` call, so scanning and lookup stay decoupled and a bulk shelf-scanning burst can't blow through UPCitemdb's 100/day cap just by scanning fast — a big backlog drains gradually over many ticks instead of firing one lookup per scan back-to-back. The manual script and `/api/scan/resolve` route both still exist (the route is what a Vercel Cron job will call once deployed, superseding this poller then).
   - **SUPERSEDED 2026-10-09** (the poller above is kept for history): `instrumentation.ts` is gone. Scans now resolve in `after()` as soon as a session finishes (`/api/scan/session-finish`), and again whenever the Pending Scans list or the website is opened (`apps/web/src/lib/backgroundJobs.ts`). Each job claims a row in `background_job_runs` and each scan is claimed via `pending_scans.claimed_until` (migration 0055), so runs never overlap. UPCitemdb is still paced at 5/min, and a refused lookup (429/5xx) or a day with no lookups left leaves the scan pending instead of resolving it as "no listing". The GitHub `resolve-scans.yml` backstop is manual only. The "stale poller needs a restart" gotcha below no longer applies, since each resolve runs from a fresh request. See rate-limits.md section 5.
3. A pending-scans review screen (mobile) lists resolved/needs-manual entries; the user confirms the suggested match, edits fields, or fills in manually — mirroring Claude's own clarifying-question style per STEP BY STEP PROCESS AND AUTOMATION.md (skipping fields that don't apply, e.g. never asking for a season number on a movie).
4. **Review-screen auto-fill and candidate narrowing** — see `barcode-review-screen-fields.md` for the full design (title/format pre-fill, year-based candidate narrowing, cover-photo auto-matching, every autocomplete/normalized field, TMDb-sourced Rating/Studio/Franchise/Animation, the manual title-search + typo-correction fallback, and the full-collection backfill rescan + Letterboxd import built alongside it).

**UPC LISTING TEXT PARSING - ONGOING, ITERATIVE (2026-09-19)** - the user's own framing: UPCitemdb's listing text has "inconsistent formatting and different types of information every time," so this is treated as an ongoing effort to notice more extractable signal in real listings over time, not a one-shot fix - the user explicitly said they'll give hints from future scans if something still isn't picked up. Deliberately conservative rather than a single greedy capture: only matches genuinely standalone single-character codes (`\b[1-6]\b` for DVD, `\b[A-C]\b` for Blu-ray - word-bounded on both sides, so a digit embedded in a longer number like "2015" can never match) within a short window right after the word "region"/"regions", and only for whichever scheme is actually valid for the disc's own resolved `format` (mirrors `getDiskRegionOptions`) - never for UHD, which has no per-title region scheme of its own to extract (`isRegionFreeFormat` already covers that case separately).

**LLM FALLBACK FOR UNPARSEABLE LISTING TEXT (added 2026-09-22)** - the ongoing "UPC listing text parsing" effort above (2026-09-19) kept finding new *shapes* of junk UPCitemdb glues onto the real title with no consistent delimiter - a `|` separator, an appended barcode number, bracketed region text - each fixable with a new targeted regex once found. This one wasn't: a real scan of "Bride of the Monster" (1955) came back with **zero OMDB candidates**, root-caused to the listing title `"Bela Lugosi, Tor Johnson-bride Of The Monster (uk Import) Dvd"` - the actor names are glued directly onto the title with a bare hyphen and **no surrounding space** (`"Johnson-bride"`), which `cleanProductTitleForSearch`'s existing `" - "` (space-hyphen-space) splitting rule never touches, so the OMDB search query came out as `"Bela Lugosi Tor Johnson-bride Of The Monster"` and matched nothing.

The user asked directly whether to (a) keep extending the regex approach with per-field extraction (actors/format/year all parsed separately) or (b) bring in an LLM for this kind of judgment call. Recommended and built (b), specifically as a **fallback**, not a replacement: regex-cleaned search still runs first (free, instant, works for the large majority of listings), and the LLM (`packages/backend/src/listingTextExtract.ts`, `extractListingTextFields`) only gets called when that first search returns zero raw OMDB candidates - same "cheap first, escalate only on failure" shape as Estimated Value's Amazon auto-shorten-then-retry-once. Reasoning given to the user: recognizing "Bela Lugosi, Tor Johnson" as actor names isn't a closed-vocabulary pattern-matching problem the way format/region/edition words are - it requires actually knowing those are real names, which is exactly what an LLM brings that a hand-written regex can't, without needing a maintained actor-names database.

**COVER-PHOTO SCANNING (built 2026-09-28)** - the user's request: the scanner should also be able to photograph a disc case's front and/or back cover, use that photo as the title's stored product image, and read title/format/disc-count/movie-or-TV straight off it so the same best-match search a typed title uses can run without the user ever typing anything - none of barcode/front-cover/back-cover exclude each other, in any order, for one physical disc. This went through Plan Mode's full workflow (3 Explore agents mapping existing conventions, several rounds of `AskUserQuestion` to pin down the hard design calls) before any code was written - the key architecture-shaping decisions, none re-litigated during the build:

1. **No real corner/edge tracking.** The user's first instinct was true alignment detection, but that needs `react-native-vision-camera`-style native frame processors, which conflicts with staying on plain Expo Go (no EAS dev-client) - a direct contradiction in two consecutive answers that was surfaced back to the user explicitly rather than silently resolved either way. Final call: **the on-screen guide is a plain static rectangle** the user lines the case up with by eye - no live-feed analysis, no native module.
2. Because the guide's screen position is fixed and known, **it doubles as the crop boundary** - "it's just so that it makes it easier for the system to crop the image later" (the user's own words). A captured photo is cropped to the same proportional rectangle deterministically, client-side - content-blind, not a smart/AI crop.
3. The countdown still visually matches the barcode scanner's old one, but is **manually-triggered** (a "Capture" tap starts it) rather than an automatic hold-steady detector, since there's no "aligned" signal to key off any more.
4. **A captured front cover always becomes the title's stored product image** (`case_image_path`), overriding the UPC-listing-photo source whenever both exist.
5. **A captured back cover is never a stored product image** - both front and back stay in temporary Storage only until the pending scan reaches a terminal state (confirmed/dismissed/discarded/superseded), then get deleted.
6. **One continuous scan session per physical disc** - barcode, front cover, and back cover can be captured in any order/subset before an explicit "Done"; everything captured becomes one `pending_scans` row. This is a deliberate behavior change from the old "barcode instantly queues and you can walk away" model.
7. **Front/back classification happens automatically via vision analysis during async resolution, never by asking the user to label a photo at capture time.**
8. If a barcode re-scan resolves to an already-catalogued title (the "dismiss" outcome) but a fresh cover photo was also captured that session, the photo updates that title's stored product image rather than being discarded.

**Mid-implementation, one more simplification arrived**: "if there is now a manual capture button we may as well use that for the barcode as well and just remove the countdown entirely." The barcode side's whole hold-steady countdown subsystem (`COUNTDOWN_MS`/`SIGHTING_GAP_MS`/`pendingBarcodeRef`/the 250ms stale-poll effect - the same mechanism section 1's bullets above describe in detail) was removed outright: `onBarcodeScanned` is now just a live "Detected: `<code>`" readout, and a "Capture Barcode" button commits it instantly, no countdown - there's no motion-blur/exposure concern in reading an already-decoded value the way there is for a real photo. Cover capture's own countdown-after-tap is unaffected.

**Post-build fixes from the first real on-device test (same day, follow-up sessions):**
- `EXPO_PUBLIC_SCAN_API_URL` in `apps/mobile/.env` is a LAN IP that drifts across Wi-Fi reconnects - if cover/barcode scanning ever throws `fetch failed: java.net.ConnectException`, re-check it against `ipconfig`'s current IPv4 before assuming the dev server itself is down.
- Removed the countdown entirely from cover capture too (it had survived the barcode-side removal above since a real photo has a genuine motion-blur/exposure argument for one) - the user judged the pause not worth it in practice once a manual Capture tap already existed; `handleCaptureCoverPhoto` now fires immediately on tap. `shutterSound: false` was also added to `takePictureAsync` (the default shutter sound cut off early and sounded like a harsh click).
- **Cover photos came out blurry, and the fix needed reading `expo-camera`'s actual installed native source, not just its public docs (this library changes fast - see `apps/mobile/AGENTS.md`).** `CameraView`'s `autofocus` prop had never been set, defaulting to `"off"` - and on Android, `"off"` isn't a no-op, the native setter calls `cancelFocusAndMetering()`, freezing whatever focus distance the lens happened to have. Every session was silently running with focus locked the entire time.
- **First attempt over-corrected**: alongside the autofocus fix, `COVER_GUIDE.widthRatio` was shrunk from `0.72` to `0.5` on the theory that a bigger on-screen guide box forces standing closer to fill it (closer than typical phones' minimum macro-focus distance) - but the user's actual ask had been to make the box **bigger**, not smaller, because it felt too small to line a case up in comfortably. Shrinking it was substituting an unrequested physics-based guess for an explicit instruction, and got called out for it. Reverted the direction: `widthRatio` is now `0.85` (bigger than even the original `0.72`). The user then explained *why* they want to stand close: their own stated belief is that a closer shot is less affected by hand shake than a farther one, so being close to the case is a deliberate preference here, not a side effect to just tolerate - the blur risk that closeness raises for autofocus specifically is handled by the focus-then-lock pattern below instead.
- **`expo-camera` has no manual focus-distance/lens-position API on either platform** (confirmed by reading the installed Kotlin/Swift sources directly, not just the docs) - the user's first idea, pinning a fixed focal length to match the guide's known distance, isn't reachable without a native module, which conflicts with this feature's own decision 1 above (plain Expo Go, no native module). Landed on a **focus-then-lock** pattern instead, using only the on/off toggle the library does expose: `autofocus` stays `"on"` (continuous) while the user lines up the shot, then a new `focusLocked` state flips it to `"off"` for a 250ms pause right before `takePictureAsync` fires - locking focus just before the shutter instead of leaving continuous autofocus free to hunt at the exact moment of exposure - then resets back to `"on"` once the capture finishes. Still not confirmed against a real on-device test; report back if focus or framing distance still feels off.
