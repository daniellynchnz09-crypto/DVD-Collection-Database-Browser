**BACKFILL RESCAN AND LETTERBOXD IMPORT**

This was originally a sub-bullet of the review-screen section (`barcode-review-screen-fields.md`), split into its own file because it grew into a large, mostly-historical project arc of its own: the full-collection physical rescan (what data had to be captured while a disc is actually in hand vs. what can be backfilled later from an API) and the one-time Letterboxd watched-status import built alongside it.

Once the Franchise/Animation fixes (see `barcode-review-screen-fields.md`) were shipped and verified on a real re-added title, the user asked to re-scan their *entire* physical collection over the following weeks/months to backfill barcode/genre-location/etc. onto the ~3,063 legacy Sheet-only rows, and - since they only want to do that once - asked first for a deliberate brainstorm of what other planning-doc-described features (web browsing, Letterboxd integration, Advanced Search, ...) might need a data field captured *now*, before any of that full-collection rescan work started. Two research passes (one over every Claude/*.md planning doc, one over the existing scan pipeline's own duplicate-detection code) grounded that brainstorm in what was actually already written down and already built, rather than guessing. The key framing that came out of it, agreed with the user: almost everything in the planning docs (Rotten Tomatoes/IMDb/Metacritic/Letterboxd scores, cast/crew, synopsis, franchise/person bios and photos, popularity) is per-film metadata obtainable from an API keyed by a stable id - it can be backfilled by a script for the *whole* collection at any future point, without ever touching the shelf again, as long as every row ends up with a real canonical id. Only genuinely physical-only data (observable solely from the disc/case in hand) actually has to be captured during this one pass, or it's lost until a second rescan.

- **Canonical id is now a hard requirement, not best-effort**: `imdb_id` (clean, e.g. `tt0110912` - the same id OMDB/TMDb search already hands back, just not previously persisted) and `tmdb_page` (a clickable `themoviedb.org/movie/{id}` URL, alongside the pre-existing numeric `tmdb_id`) were added as new columns on `titles`, per the user's own request "so future lookups are easier" from the Sheet/web app. **`imdb_id` was later dropped again** (`0019_drop_imdb_id.sql`, 2026-09-14, applied to both Supabase projects via the Management API) once it became clear it was redundant with `imdb_page`, which already embeds the same id in a fixed URL shape (`https://www.imdb.com/title/<imdb_id>/`, always written that way by this app's own code) - `extractImdbIdFromPage` in `packages/shared/src/titleParsing.ts` recovers the bare id from `imdb_page` on the fly wherever the raw id is still needed (TMDb's `/find` lookup, the similar-entry title/id match), rather than keeping a second stored copy that could drift out of sync with it. `/api/scan/confirm` now refuses (400, before writing anything) to confirm any entry backed by a real OMDB/TMDb candidate (i.e. `entry.imdbId` is set - a fully manual custom-disc entry with no candidate at all is exempt, since there's nothing to look up) if TMDb's own `/find` lookup comes up empty and no manual override was given. `ConfirmScreen` shows a "TMDb Link or ID" field (parses either a bare numeric id or a pasted `themoviedb.org` URL) only when that lookup has actually failed, and disables the Confirm button until it's filled in - this is deliberately the one thing in the whole rescan that can genuinely block submission, since it's the one thing that can't be recovered later without re-touching the physical disc. For a multi-title collection scan, every member is validated *before* any of them are written (a pre-pass over all entries, resolved once and reused rather than looked up twice) so a later member's missing TMDb match can never leave earlier members already committed with a partial write - this same pre-pass is also where a manual override id gets a full `fetchTmdbFieldsById` detail fetch, so rating/studio/isAnimated still get populated even when the id had to be entered by hand.
- **Physical-only fields captured during this rescan** (the genuine "only observable from the disc itself" set, agreed after several rounds of clarifying questions): `disc_condition` (a closed severity scale the user defined explicitly - `None`/`Visual`/`Visual Unchecked`/`Minor Issues`/`Unplayable Scenes`/`Significant`/`Unwatchable`, exported as `DISC_CONDITION_VALUES` from `packages/shared/src/titleParsing.ts`, normalized via `normalizeDiscCondition` the same alias-table pattern as Rating/Animation; `Visual Unchecked` specifically covers a disc that looks scratched but has never actually been played, so its real playback impact is unknown - distinct from `Visual`, which has been played and is confirmed fine despite the visible marks), `case_notes` (free text, for the rarer "blank/mismatched case" scenario from `Claude/DEFINITIONS.md`/`STEP BY STEP PROCESS AND AUTOMATION.md`, kept as a separate column from `disc_condition` since it isn't a severity scale at all), `release_variant_note` (free text - the first concrete step toward the still-unsolved "alternate physical editions" feature flagged in `Claude/Prompt Journal.md`/`Claude/To Do list.md` as having no available data source; captured now as raw text so the information isn't lost even before the full feature around it exists), `watched` (a simple self-reported boolean, defaulting to unwatched/unchecked - deliberately independent of any future Letterboxd integration, since the user's own collection can hold multiple physical copies of the same film, e.g. a Blu-ray and a 4K UHD, and Letterboxd's diary has no way to say which specific copy was watched on a given date), and `depicted_era_label` (a new display-only worded era field, e.g. "Spanish Civil War"/"1980s", alongside the pre-existing `depicted_era_start` integer sort key from `0002_pending_scans.sql` - that column stays purely a sort key for `computeShelfLocation` and was never actually shown to a user; this is the human-readable text a browsing user would see, only asked for when `genre_location` matches the same `/history document/i` pattern the shelf-location code itself uses). All default to a "nothing wrong/known yet" state (`disc_condition` to `None`, `watched` to `false`) specifically so the rescan itself stays fast - the user's own explicit choice over requiring an active decision on every one of ~3,063 discs.
- **`date_added`** (new column) is a true "added to this database" timestamp, distinct from `last_updated` (which the existing `set_last_updated` trigger bumps on *every* write, including unrelated normalization-backfill scripts, so it could never reliably answer "recently added" on its own - a real gap `WEB APP DESIGN.md`'s "Recently added" browse row would have hit later). Deliberately **not** backfilled for the ~3,063 pre-existing rows (`0011_backfill_rescan_fields.sql` adds the column with no default, then sets a `now()` default afterward) - nobody actually knows when each of those was first added, and stamping them all with the migration's own run time would be actively misleading. Only rows inserted from this point on get a real value, via the column default the app code never overrides. The user separately declined a purchase-price/date field outright ("I don't remember when I bought them or how much they were exactly") and confirmed `date_added` can stand in as a rough "first-scan-date" proxy for that later if wanted.
- **Deferred, on purpose, as fully out of scope for the rescan itself**: a proper cast/crew/person/franchise-description database (many-to-many relational data - many cast members per title, the same actor across many titles - that doesn't fit as columns on the flat `titles` row at all). Fully backfillable later, independent of the physical rescan, once `tmdb_id`/`imdb_page` are reliably populated - it doesn't require the disc to ever be in hand again, which is exactly why it didn't need a decision now.
- **One-time Letterboxd import (built, not deferred - see below)**: the "heygoogoo" watched/reviewed/scored integration originally floated as a maybe-later idea became a real, scoped feature once the user actually confirmed it as a request and handed over their real Letterboxd data export (`Letterboxd/letterboxd-heygoogoo-.../` - gitignored, local-only, never committed to either repo; see the "Personal data leak near-miss" note further down). Letterboxd has no public API, so this is a one-time CSV import (`watched.csv`/`diary.csv`), not a live sync - re-run by hand later if wanted, not on any schedule.
  - **Two watched metrics, not one**: `watched` means "seen this film/season at some point, on any format or copy" - the broad claim; `watched_disc` means "watched this specific physical disc/title release" - the narrow claim. This is the reverse of the mapping originally built: `watched` (0011) started out meaning "played *this* physical disc", with a new `watched_title` column (`0013_add_watched_title.sql`) added for the broad "any format" claim, but the user later clarified their intent was the opposite of the initial reading - the plain word "watched" naturally reads as "have I seen this movie at all", not "did I play this exact disc". Corrected via `0017_swap_watched_semantics.sql` (a single `update titles set watched = watched_title, watched_title = watched` - safe in one statement, since Postgres evaluates every `SET` expression against the row's old values before writing any of them) followed by `0018_rename_watched_title_to_watched_disc.sql` (a plain column rename, no data change) so the column name matches its new meaning instead of being actively misleading. Applied to both Supabase projects, the Sheet (values swapped, then the "Watched Title" header cell renamed to "Watched Disc" in place), and every code reference across `packages/shared`, `apps/web`'s confirm route, and `apps/mobile`'s `ConfirmScreen` (including swapping which of the two on-screen checkboxes drives which state variable, so the checkbox still labeled "Watched this disc" now maps to `watchedDisc`/`watched_disc`). The import script's actual matching logic didn't need to change at all - only which field name each already-correct real-world fact gets written to.
  - **Exact tag vocabulary, confirmed against the real export rather than guessed** - the user tags each Letterboxd log/review with how they watched it, but several of the ~143 distinct real tags read as sarcastic commentary on the film itself ("so bad its good", "should have been a streaming movie", "oops all white people", ...) rather than an actual viewing-method signal, so the user asked to review the exact list before any of it got wired into matching logic. Confirmed disc-format tags: `blu-ray`->Blu-Ray, `dvd`->DVD, `4k uhd blu-ray` and `4k uhd blu-ray steelbook`->4K UHD Blu-Ray. Confirmed non-disc tags (set `watched` only, never `watched_disc`, since these mean the film wasn't watched on any owned physical copy at all): `cinema` (a theater screening), `docplay` (a documentary streaming platform), and the 🌐 emoji (confirmed by the user to mean "watched on the web" - not obvious from the tag text alone, since it carries no literal label). Every other tag (satirical or otherwise - `mst3k`, `w/father`, `serial`, `doctor who`, ...) is ignored entirely by the import; it has no bearing on watched/format matching.
  - **Built as a real script (`scripts/src/import-letterboxd.ts`, `npm run import-letterboxd --workspace=scripts -- [--apply]`)**, not just an analysis - dry run by default, only writes to Supabase/the Sheet with `--apply`. A first rough dry-run pass (done before the real script existed) had estimated 228 matched films; once actually built and run against the real export, exact-normalized-title matching found only ~89 distinct Letterboxd films/serials matching the physical collection by title (verified independently: 85 of 754 `watched.csv` entries match a `titles` row by `normalizeTitleForMatch` alone) - the earlier 228 figure came from a rougher, since-discarded analysis and was simply wrong; the real collection is a small subset of the user's full watch history (most of what's on Letterboxd - Morbius, RRR, Zardoz, ... - was never owned on disc at all). Of the real matches: single-copy titles resolve 29/74 via a confirmed tag, multi-copy resolve 7/15, and the Doctor Who season-completeness check (below) resolves 6/9. The ~56 unresolved items went to `letterboxd_review_queue` (`0014_letterboxd_review_queue.sql`, private project only) and a throwaway `/letterboxd-review` page (`apps/web`, gated by a `?secret=` query param matching `SCAN_API_SECRET` - a page a browser navigates to directly, unlike the mobile app's header-gated API routes).
  - **Completed and cleaned up**: every item was worked through (via the page's pick/skip buttons, and via free-text notes needing real judgment - collection-membership disambiguation, "seen elsewhere not on this disc", the 4K UHD companion-Blu-Ray case, and standalone-serial-vs-season-box cases for Doctor Who). The page and its API route were then deleted and the table dropped (`0016_drop_letterboxd_review_queue.sql`), per the original "throwaway, deleted after you finish" plan. `import-letterboxd.ts`/`letterboxdCsv.ts` themselves are kept (re-runnable by hand for a future export) - which surfaced two real gaps while doing the actual public/private sync afterward: the sanitizer's word-scan only walked `apps`/`packages`, so these two scripts (neither under those directories) would have been silently copied into the public checkout without ever tripping it; and the word-scan never covers `supabase/` at all, so `0014`-`0016` (which create/modify/drop `letterboxd_review_queue` - real feature infrastructure, not just a comment mentioning the word) would also have shipped unnoticed. Fixed both: `scripts` added to the scanned directories, and an explicit `EXCLUDE_FILENAMES` list (basename-matched, wherever a file lives) added for these two scripts, the sanitizer script itself (its job is generating the public repo *from* the private one, meaningless the other direction), and the three migration files - deliberately narrower than excluding all of `0011`-`0013` too, since those are ordinary `watched`/date columns that just happen to have a comment giving Letterboxd as context, not Letterboxd-specific infrastructure.
  - **A "Blu-Ray" tag is treated as a match for an owned "4K UHD Blu-Ray" copy**, not a format mismatch (`formatsAreCompatible` in `import-letterboxd.ts`) - the user confirmed most 4K UHD releases physically bundle a standard Blu-ray disc of the same film in the same case (for players without 4K support), and tags whichever disc they actually played. Deliberately one-directional and format-specific: a "Blu-Ray" tag against an owned plain DVD is a *different* situation (no DVD release bundles a Blu-ray) and correctly stays a real mismatch sent to manual review, as happened for Bride of Frankenstein - that one turned out to be a genuinely different physical disc entirely (see below), not this rule.
  - **A single physical copy can still be the wrong candidate** when the film is *also* part of a box set the collection catalogues separately - the "similar/matching entry" design already models this (a franchise film has its own standalone row *and* a separate `title_in_a_collection` row for the box-set copy, e.g. Pink Panther's "A Shot in the Dark" or the Coppola Masterpiece Collection's "American Graffiti"), but the Letterboxd import's per-title review only ever offered whichever copies matched by title, with no way for the user to say *which* of those matters. Real cases from the manual review pass: "A Shot in the Dark" and "American Graffiti" each had a standalone copy and a box-set copy, and the user specified they'd watched the box-set one specifically; "Bride of Frankenstein" was subtler still - the review item's only candidate was a standalone DVD, but the user had actually watched a *different* physical copy entirely (a Blu-Ray inside the "Universal Monsters The Essential Collection" set) that the review item never even offered as an option, since nothing in the import's matching connected them. No general fix was built for this (it would need the review UI to search the whole collection, not just its own candidate list) - resolved by hand via the free-text note instead, case by case.
  - **Never edit the review page/API or reset/replace `letterboxd_review_queue` while the user might have the page open** - both mistakes actually happened in the same session: a live code edit to add error handling reset the page's in-memory draft state (Next.js Fast Refresh remounts on a change), losing typed-but-unsaved notes; separately, deleting-and-reinserting the whole queue to fix the year-matching bug silently orphaned whatever review IDs the open tab still had in memory, so further clicks against those saved nothing while still claiming success (compounded by the page originally never checking the fetch response at all - fixed, see below). Coordinate with the user before touching either while they're actively using the page.
  - **The review page also has a free-text field per item** (`user_note` column, `0015_letterboxd_review_queue_user_note.sql`), separate from the import script's own machine-generated `note` - lets the user leave context for Claude to read afterward (e.g. "these 3 are different cuts, I watched the theatrical one") instead of that only being possible by typing it into chat. A "Save note" button persists it without resolving the item, for something the user isn't ready to decide yet; the resolve/skip buttons also carry along whatever's currently typed.
  - **The Doctor Who season-completeness check is deliberately restricted to Doctor Who itself**, not applied to every whole-season TV row - the collection actually has 334 such rows across dozens of ordinary shows (Breaking Bad, Friends, Game of Thrones, ...), and checked live that TMDb's own per-season episode lists for those are ordinary hour-long episodes that Letterboxd users essentially never log as individual "films" the way classic Who's serials are catalogued - running the same completeness check against them would have produced ~300 meaningless review-queue entries instead of a real signal. The restriction (`title` contains "doctor who", numeric `season_no`, no `part_of_season_no`, and the box-set suffix pattern actually matched and stripped from the title) also correctly excludes single-serial Doctor Who rows that happen to share a `season_no` (e.g. "Doctor Who Terror of the Zygons") - those fall through untouched by this pass rather than being wrongly checked against the whole season's completeness.
  - **Duplicate title rows are usually *not* a data error** - worth stating explicitly after the Iron Man 2 case (two "4K UHD" rows, confirmed by the user to be a genuine database mistake) got initially over-generalized during this analysis. The far more common real reason two rows share a title is a legitimate multi-disc collection membership (e.g. "Dawn of the Dead" appearing more than once because it's part of more than one box set the user owns) - `is_collection`/`name_of_collection`/`title_in_a_collection` already exist specifically to represent this. Any future automated duplicate-detection logic must check those collection fields before ever flagging a repeated title as a likely mistake; a genuine accidental duplicate (like Iron Man 2) is the case where none of those fields explain the repeat.
  - **A window of unreliable Letterboxd dates exists and must not be trusted at face value**: the user backfilled a batch of older reviews/logs from Facebook Stories and IMDb notes onto Letterboxd, and several of those genuinely predate Letterboxd itself but all landed on the same couple of days (whenever that backfill happened), not their real watch dates. Confirmed empirically in the real `diary.csv` rather than guessed at which days: 457 of 825 diary rows (~55%) carry `Watched Date` of either 2025-09-28 (250 rows) or 2025-09-29 (207 rows), and for every one of those rows `Date` (the day the log entry was created) is identical to `Watched Date` - the signature of a bulk backfill session where no real historical date was entered per-title, so Letterboxd defaulted the watched date to the log date. The import leaves `last_watched_date` blank for any diary row whose `Watched Date` falls on either of those two dates, rather than writing a confidently wrong date. **Backlog**: a future pass could recover the *real* dates by going back through the user's actual Facebook Stories archive for the original posted dates - not attempted now, no tooling for it exists yet.
  - **TV/season completeness, built in this same pass (not deferred to a follow-up)**: confirmed against the real data that the collection already models this exactly as expected - a DVD holding a single classic-series serial has that serial's own real title as its `title` (e.g. "Doctor Who: The Invasion of Time", `season_no` set, `episode_count` = that serial's episode count) and matches Letterboxd/import logic identically to a movie, no special-casing needed. A Blu-ray box set holding an *entire* season, however, is a single row (e.g. "Doctor Who the Collection Season 7", `episode_count` = the season's total across all its serials) with no list of the individual serial titles it contains - that list isn't derivable from anything already in this database. The import resolves it via TMDb's `episode_groups` endpoint for the show (classic Doctor Who's individual serials are captured there as a curated grouping) to get the real serial list for that `season_no`, then treats the season row as watched only if every one of those serials has its own matching Letterboxd log - exactly the all-or-nothing rule the user specified. A season TMDb has no such grouping for falls through to the manual-review bucket rather than guessing.
- **Sheet mirroring**: `imdb_page`/`tmdb_page`/`release_variant_note`/`disc_condition`/`case_notes`/`watched`/`depicted_era_label` were all added to `HEADER_ALIASES` and `AUTO_CREATE_COLUMNS` in `packages/shared/src/titleParsing.ts`, so `scripts/src/sync-sheet.ts` adds the matching header columns to the live Sheet itself the same way it already does for Genre Location/Steelbook/Release Name, rather than requiring the user to add them by hand first. `date_added` deliberately has no Sheet column at all (system-managed only, same as `last_updated`) - not something the user is expected to edit. The Sheet's own former "IMDb ID" column was manually deleted by the user on 2026-09-14 once `imdb_id` was dropped from the schema - see `google-sheet-sync.md` for why that needed no code changes.
- **The similar-entry check itself was broadened at the same time**, not just extended with a new screen: the original version (`/api/scan/find-existing`) only ever matched exact normalized title text among rows with no barcode yet, showed only a title/format/disc-count summary, and its "attach" action only refreshed a conservative subset of IMDb/OMDB-sourced fields. Per the user's own definition of "similar" ("same movie title, same IMDB entry, same format but maybe it has 2 disks instead of one... or a different region"), matching is now title-text-OR-`imdb_id`, across **every** row including already-barcoded ones - so a genuine second physical copy of a film you already own also surfaces here, letting you deliberately choose "Is a new entry" for it rather than that case simply never being checked. Each candidate now carries a resolved poster (`case_image_url` if the row has one, else a live OMDB poster fetch via `imdb_id` as a fallback for the many legacy rows that predate the barcode pipeline entirely) plus enough real fields (format, disc count, region, genre location, franchise, rating, studio, animation/live action, special features, steelbook, existing barcode) for a genuine side-by-side comparison, not just a name check. The three choices replace the old two-choice "attach/add as new": **Overwrite** replaces every field of the existing row with this scan's data - implemented as a plain Supabase `update` + a full `updateSheetFieldsByUniqueId` rewrite keyed on the *same* `unique_id` (not a delete-then-recreate), specifically so anything already referencing that id (e.g. a confirmed `pending_scans` row) never has to be repointed; **Is a new entry** is unchanged (creates a fresh row, for a genuine second copy); **Reject** discards the pending scan outright, same as the existing stray-scan discard path. The old `/api/scan/link-existing` route and `linkExistingTitle` client function were removed entirely rather than kept alongside Overwrite - Overwrite is a strict superset of what that route did (every field, not just the IMDb/OMDB-sourced subset), so keeping both would only have meant two parallel "merge into an existing row" code paths to maintain.
- **TMDb's actual API Terms of Use** (fetched directly and quoted verbatim, not assumed - the general Site Terms of Use the user first found is a different document covering website membership/user contributions, not API use) explicitly prohibit two things relevant here: caching any TMDb-sourced data for longer than 6 months, and displaying TMDb content without a specific attribution notice + logo ("This [product] uses TMDB and the TMDB APIs but is not endorsed, certified, or otherwise approved by TMDB", less prominent than the app's own branding). The caching limit directly conflicts with this project's "store once, keep forever" pattern used for every other field, so two new columns track it: `tmdb_id` (the TMDb movie id, found once via `/find`) and `tmdb_synced_at` (last successful refresh). `refreshTmdbFields` re-fetches anything overdue (never synced, or synced >~5 months ago - a safety buffer under the 6-month limit) on a 1-hour interval in `apps/web/instrumentation.ts` (checks are cheap since almost always nothing is due) and via `npm run refresh:tmdb` for manual/testing use. The user explicitly chose to build this refresh rather than skip TMDb or use it display-only, since ratings/studio names can genuinely change over time anyway (re-classifications, studio mergers/renames) independent of the compliance angle.
- **`rating_is_manual`/`studio_is_manual` columns protect anything a human actually typed in** (the physical case, or the original Sheet before this feature existed) from ever being silently overwritten by the refresh job - both default to `true` (so the existing ~3063-row collection was automatically protected the moment the migration ran, no separate backfill needed) and are only ever set to `false` by the scan-confirm route, and only when the corresponding field wasn't manually provided. Verified live: a manual override at confirm time correctly took priority over TMDb's values and set both flags true; a fully-manual row was correctly skipped entirely by the refresh job even when deliberately backdated past the cutoff, while a TMDb-sourced (non-manual) row deliberately backdated the same way was correctly picked up and its `tmdb_synced_at` renewed.
- **Attribution is still owed, not yet built**: the TMDb logo + required notice need to appear once the actual browsable web app (Phase 2+) displays this data publicly - noted here so it isn't forgotten, but not blocking this backend work, since the mobile Confirm screen is a private single-owner cataloguing tool, not the public-facing surface the attribution requirement is really aimed at.

Added `last_watched_date` to the select and the `TitleRow` interface; re-ran `--verbose` afterward and confirmed it now correctly reports "0 would actually change a value" once the collection is genuinely all caught up. `tsc --noEmit` clean on `scripts`.

**A COLLECTION HEADER'S `personal_rating` DOESN'T RETROACTIVELY RECOMPUTE AFTER A LATER BACKFILL (2026-09-27)** - once the Letterboxd backfill above gave every one of the 9 Universal Classic Monsters members a real `personal_rating` (and all 9 were already `watched`), the user asked where the box set's own header-row `personal_rating` was - it was still `null`. Not a bug: the confirm route's averaging logic (`apps/web/src/app/api/scan/confirm/route.ts`, "Personal Rating (#11)") only ever runs once, at the moment that specific collection is submitted through the app, using whatever `existingPersonalRating` each member had *at that instant*. **REAL STORAGE DUPLICATION FOUND AND FIXED THE SAME SESSION**: user asked why Universal Classic Monsters and Resident Evil: Welcome to Raccoon City appeared to have "multiple images." Investigated with real evidence rather than assuming: Raccoon City's "multiple images" turned out to be a case photo plus a separate poster (two legitimately different things, `case_image_path` vs `poster_image_path`/`movie_poster_path` - the latter two themselves a likely-redundant duplicate pair worth a future cleanup, not touched this session). Root cause: `confirm/route.ts`'s per-entry loop calls `uploadCaseImage` unconditionally against each entry's own `manual.case_image_url` - and every member of a Collection scan submits the *identical* URL (the box's own listing photo, since individual titles in a box set have no cover of their own to scan), so the loop was independently re-fetching and re-uploading that same external image once per member. Fixed going forward with a per-confirm-request `Map<url, path>` cache (`uploadedCaseImagePathByUrl`) declared above the loop: the first entry to use a given URL still gets its own upload as before, but every later entry sharing that URL reuses the already-uploaded path instead - a deliberate, documented exception to the usual "own uuid, own folder" convention. **Backfilled the same session, on request**: surveyed every collection rather than guessing scope - of 509 `is_collection` rows, only 18 title-rows across the whole database actually combine a collection role with a real `case_image_path` at all, narrowing to 3 candidate collections with 2+ image-bearing rows (Alfred Hitchcock Classics, Universal Classic Monsters, Resident Evil: Retribution). Checked each by real eTag comparison rather than assuming every multi-image collection was broken the same way: Resident Evil: Retribution's two members turned out to have **genuinely different** images (different eTags) - correctly left untouched, not a duplication case. The other two (5 and 10 image-bearing rows respectively) were confirmed byte-identical duplicates. Cleaned up in the safe order - repointed every duplicate member's `case_image_path` to its collection header's own path first, verified the repoint via a fresh read, *then* deleted the 13 now-orphaned files (4 Hitchcock + 9 Monsters, ~717KB freed) - never delete-then-repoint, which would leave a dangling reference if the repoint step failed partway. Verified both surviving canonical files still exist and are intact after the delete. `case_image_path` has no Sheet column (confirmed via `titleParsing.ts`'s own "Fields with no Sheet column" list), so no Sheet push was needed for this cleanup.
