**ESTIMATED VALUE**

A per-title resale/replacement value in NZD, computed against real NZ/international retail sites rather than guessed. Private-collection-only: excluded from both the public Supabase project and the public GitHub repo entirely (see PUBLIC EXCLUSION below), since real dollar values are financially sensitive per Claude.md's security section.

**TRIGGER (corrected 2026-09-15)** - a title is only ever priced for the first time immediately after it's scanned and confirmed, never by a backlog sweep across the collection. The original design had a single periodic job pull from the whole `titles` table (any row with `estimated_value_last_checked` null or stale) - the user explicitly corrected this: "the estimated value should only run on an item that I have just scanned, not the entire database." Two separate entry points now exist in `packages/backend/src/estimatedValue/refresh.ts`:
- `refreshEstimatedValueForTitleIds(supabase, titleIds)` - the real trigger. Called fire-and-forget from `apps/web/src/app/api/scan/confirm/route.ts` right after a scan's title row(s) are inserted (never blocks the confirm response - "work in the background" per the original spec means right here). Processes exactly the given ids, regardless of staleness.
- `refreshEstimatedValueBatch(supabase, limit)` - the periodic 6-month recheck sweep (still real, still part of the original spec: "the Estimated Value process will rerun on existing titles every 6 months and update the price"), but its own eligibility query now explicitly excludes `estimated_value_last_checked is null` - it only ever revisits a title that already has a real price that's gone stale. A never-priced title is never picked up here, only by the scan-time trigger above, so this sweep can never turn into a backlog run across the ~3000-title collection.

Known gap in the fire-and-forget trigger: it only reliably finishes on a long-running Node process (true of `next dev` and the current deployment target) - a true serverless deployment (Vercel's default Node runtime) can freeze the function once the response is sent, cutting the pricing work off mid-run. If this route ever moves to serverless, wrap the call in Vercel's `waitUntil` (or equivalent) instead.

**ELIGIBILITY**
- `titles.title_in_a_collection = true` rows (a film that's part of a box set, sharing `name_of_collection` with the box set's own row) are skipped entirely - only the `is_collection = true` row gets a value, representing the whole set's worth. Valuing both would double-count: N member values + 1 collection value for what's actually one physical item.
- Custom-burn discs (`format` normalizes to `"DVD (Custom Burn)"` per `FORMAT_ALIASES`) get `estimated_value = 0` immediately, no lookup.
- Every other row is eligible once it exists in `titles` - ConfirmScreen already enforces required fields before insert, so there's no separate "completeness" check.

**SEARCH TITLE** (`packages/backend/src/estimatedValue/searchTitle.ts`, `buildSearchTitle(title)`): `(release_name if set/not "n/a", else title)` + `" " + release year from release_date` (skipped when `is_collection`, since a box set has no single film year) + `" " + format` + `" Steelbook"` if `steelbook`. Example: "2001: A Space Odyssey" (1968, Blu-Ray, steelbook) -> `"2001: A Space Odyssey 1968 Blu-Ray Steelbook"`. A collection: `is_collection` row titled "Universal Monsters Collection", format Blu-Ray -> `"Universal Monsters Collection Blu-Ray"` (no year).

**API compliance review** (2026-09-14) - checked before wiring real credentials in, since this feature stores eBay-sourced data (price, product image, listing title) in `title_price_observations` and re-checks every ~6 months. `developer.ebay.com`'s actual API-docs pages (`buy/browse/overview.html`, `buy/buy-integration.html`, `buy/static/buy-requirements.html`) all return a flat 403 to fetch tools (repeatedly, across two separate research passes) - findings below come from search-indexed excerpts of eBay's own pages/community forum, not a direct read of the current license text, so treat this as a good-faith best effort rather than a verified legal reading:
- **Rate limit**: 5000 calls/day on a standard production keyset - not a concern at this personal, ~3000-title, 6-month-cycle scale.
- **Caching/retention duration**: no explicit Browse-API-specific caching-duration ceiling (e.g. "refresh within N days") was found. The API License Agreement does contain a data-destruction requirement - remove/destroy eBay Data within a reasonable time, described in a 30-day figure in secondary sources - but that reads as a post-termination/on-request purge obligation, not an active-use caching TTL; could not confirm which it actually is from primary text. Given that, this feature's existing 6-month refresh-and-replace design (each cycle deletes and re-inserts a title's price observations, so nothing accumulates indefinitely) is the safe default already in place - it's bounded retention, not indefinite storage - but should be re-confirmed once the user's eBay developer dashboard shows the actual accepted terms for their approved access level.
- **Copying/storing images**: the License Agreement's general "eBay Content" clause (content, data, images, and other material retrieved from eBay) prohibits selling, renting, distributing, copying, storing, or modifying it "other than for purposes allowed by the Terms" - no specific carve-out for a private image cache was found either way. This feature already treats eBay product images exactly like every other retail image in this feature: cached into the private `retail-product-images` Supabase Storage bucket, signed URLs only, never public (see IMAGES / STORAGE above) - the cautious default, not a change made because of this finding.
- **Attribution/branding**: found requirements for *public* displays (eBay Content in a Public Display must be visually isolated from non-eBay content) and for affiliate/EPN revenue-sharing flows (campaign ID headers, `itemAffiliateWebUrl` forwarding for commission) - neither applies here, since this feature is never shown publicly (private Supabase table, owner-only) and does no affiliate checkout/commission flow, only read-only Browse search. No explicit "zero attribution needed for private personal use" statement was found, but nothing found implies one is required either.
- **AI-training restriction**: the 2025-updated agreement explicitly bars using eBay Content/Personal Information to train AI models - not applicable, this feature does plain arithmetic averaging and display, no model training.
- **One new-to-this-pass finding worth flagging**: eBay's own `buy-requirements.html` (via search excerpt) frames "Buy APIs" production access generally as "Limited Release... intended for eBay partners only," applied for through the eBay Partner Network with an approved business model. Community-forum context suggests this framing is really about the checkout/order/commission-earning resources, not read-only `item_summary/search` - and the 5000/day figure is consistent with a standard (non-EPN) production keyset existing for Browse search specifically. Still unconfirmed from primary source text (blocked by the same 403), so worth a two-minute sanity check once the user's production approval actually comes through: confirm the granted access covers `buy/browse/v1/item_summary/search` under normal developer terms, not an EPN-gated tier this app doesn't participate in (no checkout, no `itemAffiliateWebUrl` usage, no commission).

**CONFIDENCE SCORING** (`confidence.ts`) - reuses the perceptual-hash machinery already built for OMDB poster-matching (`packages/backend/src/posterMatch.ts`, Jimp pHash + `compareHashes`) rather than inventing a new scheme:
1. Hard gate: a candidate whose own listing text implies the wrong format or a mismatched release year is discarded outright, never scored (the remake/re-release guard), reusing format-hint extraction from `packages/shared/src/formatHints.ts`.
2. Text score (0-1): Dice coefficient over normalized word tokens (`normalizeTitleForMatch`), a generalization of `scoreCandidateByCastHint`'s existing word-overlap approach in `packages/shared/src/omdb.ts`.
3. Image score (0-1, only when a poster is resolvable via `imdb_page`/`tmdb_id` AND the title is neither `is_collection` nor `steelbook` - retail art looks nothing like the poster for either): `1 - pHashDistance`. Reuses `posterMatch.ts`'s `CONFIDENT_MAX_DISTANCE = 0.2` / `CONFIDENT_MIN_GAP = 0.05` two-gate pattern for plain DVD, but a more lenient `LENIENT_MAX_DISTANCE = 0.32` for Blu-ray/4K UHD (non-steelbook) - their retail photos always carry an extra format-header band above the actual cover art that reduces raw similarity even for a genuinely correct match, so a stricter threshold there would just create false rejections.
4. Combine: with an image score, `confidence = 0.4 * textScore + 0.6 * imageScore` (a candidate that doesn't clear its own distance/gap gate contributes 0 to the blend, not partial credit). Without one (steelbook/collection), `confidence = textScore` if `textScore >= 0.85`, else `textScore * 0.7` - a concrete stricter bar to compensate for the missing second signal.
5. **No bands** (redesigned 2026-09-15 - see PENDING VALUE IS NOW ALWAYS-MANUAL below): `confidence` is purely a ranking/sort signal now, never a gate. There is no auto-accept threshold and no manual-review floor any more - every candidate that survives step 1's hard gate goes to Pending Value, sorted best-first.

**PENDING VALUE IS NOW ALWAYS-MANUAL** (redesigned 2026-09-15, replacing the original auto-accept/manual-review/drop design) - the user rejected the semi-automatic system after testing it against 5 real titles and finding only 1 of 5 (Captain Marvel) got a real scraped price, the other 4 silently falling through to the random fallback estimate. Their own words: "instead of automatically finding a product that fits and then averaging out the prices of those products, instead it will send the results of the products found to the pending value page and the user can choose to remove ones that don't fit." Confirmed directly with the user on three specific points:
- **No auto-accept tier at all**, not even for a near-certain match - every title with any surviving candidates goes to Pending Value, full stop. `refresh.ts` no longer ever calls `recordAcceptedPrices` itself; that only happens from the Pending Value response route once a human has actually chosen which candidates to keep (see MANUAL REVIEW below - unchanged).
- **A strict 0% floor, added the same day once real testing confirmed the score is trustworthy** - the original no-floor design (above) meant every candidate that survived the hard gate was shown, however low it scored. After using it for real, the user reported the confidence metric was accurate enough that a candidate scoring exactly 0% (no text overlap at all, and no passing image match either) was reliably junk, never a real match worth looking at - so `refresh.ts`'s `reviewCandidates` now filters to `confidence > 0` before capping at 15. This is a floor at zero, not a return of the old 30% band - anything above 0%, however marginal, is still shown. The fallback estimate's trigger condition widened to match: zero candidates survive the hard gate at all, OR everything that does still scores a flat zero.
- **Candidate cap raised from 7 to 15** (`MAX_REVIEW_CANDIDATES` in `refresh.ts`) - now that the user is the one filtering, the list should show more of what was actually found rather than hiding results beyond a small handful.
- **Search-source ordering changed twice the same day** - first kept as NZ-first/international-only-if-NZ-empty (unchanged from the pre-redesign behaviour, confirmed deliberately with the user at the time). Reversed once real testing showed why that was wrong: JB Hi-Fi/Real Groovy always returned *some* raw candidates for every one of 5 test titles (even when every one was the wrong movie), so `gatherCandidates`'s "skip international if NZ found anything at all" rule meant eBay was never queried even once. The user pushed back directly - NZ retail has few options for a lot of titles, and eBay in particular should have been turning up real secondhand Marvel-movie listings and wasn't. `gatherCandidates` now always queries every NZ source AND every international source, every time, no early exit - see NEVER-QUERIED-EBAY below for the second half of why eBay specifically still hadn't shown anything even before this fix.

**AVERAGING** (`averaging.ts`) - unchanged mechanically, but now only ever runs from the Pending Value response route (`pending/respond/route.ts`), never from `refresh.ts` directly, since there's no more auto-accept path: each Search Title accumulates a list of user-accepted prices from possibly multiple marketplaces in `title_price_observations` - deliberately not deduplicated to one, since varying prices across sites are the point. `estimated_value` = the average of whatever the user chose to keep. Every review resolution deletes and re-inserts a title's own price-observation rows rather than accumulating forever, so the average always reflects the latest accepted set, not an ever-growing historical blend.

**NON-DISC RESULT FILTERING** (added 2026-09-15, same day as PENDING VALUE IS NOW ALWAYS-MANUAL below) - removing the confidence floor made it obvious that JB Hi-Fi/Real Groovy/eBay's search endpoints return plenty of non-disc noise for a middling query (Sonos speakers, phone cases, CD box sets, apparel, funko pops) that used to be silently dropped below 30% before anyone saw it. Marbecks already filtered this via its own `DISC_FORMAT_HINT` (its listing description names the medium explicitly, e.g. "CD - released..."), but that same allow-list approach can't be copied to the other sources - live-checked first (2026-09-15) rather than assumed:
- **JB Hi-Fi / Real Groovy** (`shopifySearch.ts`'s `isLikelyDiscProduct`): the two storefronts' `product_type` field turned out to mean completely different things. Real Groovy's is literal disc-format text (a real "Casper" DVD's type is literally `"DVD"`), but JB Hi-Fi's is a generic department name (a real "Thor: Ragnarok" listing's type is `"MOVIES"`, with no DVD/Blu-ray/4K/UHD keyword anywhere in its title, type, or body at all). An allow-list-of-format-words filter would have wrongly dropped every genuine JB Hi-Fi match. So this checks two ways: a `type` that IS an explicit disc-format word is kept; a `type` that's a known non-media department (music/cd/lp/games/accessories/apparel/books/etc.) is dropped; anything else (an unrecognized generic department name) is kept by default.
- **eBay** (`ebay.ts`'s `isLikelyDiscListing`): no clean structured field to read (seller-written listings, not a retailer's own catalog, and the Browse API's `categories` taxonomy couldn't be verified live - same 403 issue as the rest of this file's API compliance notes). Checks title + `shortDescription` text for common movie-title-search cross-listing junk instead (funko pops, posters, soundtrack vinyl/CDs, apparel, video games) - exclude-only, same reasoning as JB Hi-Fi/Real Groovy's filter.
- **What this filter does NOT fix**: a search returning the *wrong movie* in the *right format* (e.g. searching "Avengers: Infinity War" and getting back genuine-but-irrelevant DVDs like "Purple Rain" or "Shaft") - those are real disc products, just bad search matches, which is exactly what the confidence score (for ranking) and the user's own reject button (for correctness) are there to handle, not something a disc/non-disc filter can or should touch. Verified live against the same 5 test titles from the redesign below: Casper's Haunted Christmas went from 12 to 10 candidates (a Sonos speaker and a phone case dropped), Paper Planes went from 10 to 7 (a CD box set, a book, and a t-shirt dropped) - the other 3 titles' candidate counts were unchanged, since their noise was entirely wrong-movie-right-format, not non-disc merch.

An accepted review candidate goes straight into `title_price_observations` via `recordAcceptedPrices` (the only place that function is called from at all now - see PENDING VALUE IS NOW ALWAYS-MANUAL above), no re-scoring; an all-rejected review falls back to the random estimate and sets `estimated_value_is_estimate = true`.
- API: `apps/web/src/app/api/estimated-value/pending/route.ts` (POST/list - matches `requireScanSecret`'s header-based auth convention, same reasoning as every other scan-secret-gated route being POST regardless of whether it mutates anything; resolves signed image URLs server-side before responding, same "resolve everything server-side" convention as `find-existing/route.ts`) and `.../pending/respond/route.ts` (POST, accept/reject decisions).

**GOOGLE SHEET SYNC** (added 2026-09-15, closing a gap in the first build) - the original spec calls this out as "a new column to the database/**spreadsheet**," but the first build only ever wrote `estimated_value` to Supabase; the Sheet's own copy of the collection never saw it. Now wired into `google-sheet-sync.md`'s existing bidirectional mechanism, full two-way (the user's explicit choice over a one-way push, consistent with how every other column already behaves - a manual correction typed into the Sheet does take effect, and yes, that means a hand-edit can get overwritten by the next 6-month recheck, same tradeoff every other column already accepts):
- **Setup**: add a column headed exactly `Estimated Value` to the real Sheet by hand (same one-time step Steelbook needed - `AUTO_CREATE_COLUMNS` deliberately wasn't extended for this one, since the value only means something once the estimator has actually run). Until that column exists, `pushEstimatedValuesToSheet` finds no matching column and simply does nothing - no error, no retry.
- **Supabase -> Sheet**: `apps/web/src/lib/estimatedValueSheetSync.ts`'s `pushEstimatedValuesToSheet(supabase, titleIds)` - reads `estimated_value`/`estimated_value_is_estimate` back out of Supabase for the given ids, formats each as `"$13.50"` / `"est. $45.00"` / `"n/a"` (`formatEstimatedValueCell` in `packages/shared/src/titleParsing.ts`), and writes it via the existing `updateSheetFieldsByUniqueId`. Called after all three places a title's price actually changes: the scan-time trigger (`scan/confirm/route.ts`, chained after `refreshEstimatedValueForTitleIds` resolves), the 6-month recheck sweep (both `instrumentation.ts`'s interval and the `estimated-value/refresh` route), and a resolved manual (Pending Value) review (`pending/respond/route.ts`). Best-effort throughout - a Sheets API failure is caught and logged, never allowed to sink a scan confirmation or a refresh batch. `RefreshBatchResult` (`packages/backend/src/estimatedValue/types.ts`) grew a `titleIds` field so callers know exactly which rows to push without re-deriving it.
- **Sheet -> Supabase**: needs no new plumbing - `packages/shared/src/titleParsing.ts`'s `HEADER_ALIASES` maps the `"Estimated Value"` header to a synthetic `estimated_value_display` field, and `parseSheetRowToTitle`'s `parseEstimatedValueCell` turns whatever text is typed into that cell (`"$13.50"`, `"est. $45.00"`, `"0.00"`, blank/`"n/a"`) back into the two real `estimated_value`/`estimated_value_is_estimate` columns. Reaches Supabase through the sheet-webhook route exactly like every other column already does - no estimated-value-specific code needed there.
- **Public exclusion**: `titleParsing.ts` is genuinely shared (every other column's Sheet<->DB mapping lives there too), so its estimated-value-specific lines are sentinel-wrapped (`ESTIMATED-VALUE-PUBLIC-EXCLUDE-START/END`) rather than the whole file excluded - added to `sanitize-public-repo.ts`'s `ESTIMATED_VALUE_MARKED_FILES`. `formatEstimatedValueCell` deliberately duplicates (rather than imports) the tiny `"$X.XX"`/`"est. $X.00"` formatting already in `fallbackEstimate.ts`, since that module is excluded from the public build outright and `titleParsing.ts` isn't - an import across that boundary would leave a dangling reference in the public copy the moment the marked block is stripped out from around it. `estimatedValueSheetSync.ts` itself is private-project-only code through and through (reads/writes columns that don't exist in the public schema), so it's excluded as a whole file via `EXCLUDE_FILENAMES`, same as `PendingValueScreen.tsx`.

**IMAGES / STORAGE**: both retail product photos and cached OMDB/TMDb posters (`titles.poster_image_path`, populated opportunistically the first time the job resolves a poster for confidence scoring) are stored in a single private Supabase Storage bucket, `retail-product-images`, created via the migration - the first real Storage integration in this codebase (`case_image_url` has only ever stored an external URL as-is, despite Storage being the originally-documented intent). Private bucket, signed URLs minted server-side on demand (`createSignedUrl`, ~1hr expiry) rather than a public bucket - the user's explicit choice, consistent with this project's generally cautious security posture even though these are just promotional/stock images with no personal content.

**FALLBACK ESTIMATE** (`fallbackEstimate.ts`) - used in two cases since the 2026-09-15 redesign: zero candidates survived `refresh.ts`'s hard format/year gate at all (nothing to send to Pending Value), or the user reviewed a Pending Value entry and rejected every candidate shown. Formatted as `"est. $X.00"` (vs. a real found price's plain `"$X.XX"`) - the `est.` prefix is display-only, derived at render time from `estimated_value` + `estimated_value_is_estimate`, never baked into the stored number. "Special edition" (for the SE-bumped ranges) means `release_name` is set and differs from the plain `title`, independent of whether the disc has bonus features - confirmed directly with the user via a concrete before/after example (plain "Gladiator" DVD vs. "Gladiator: Extended Edition" DVD).

**AUTO-ESTIMATED NOTE** (added 2026-09-15) - a fallback-estimated title used to be completely invisible anywhere in the app once `processTitle` wrote its random guess straight to `titles` - no Pending Value entry, no way to review or correct it short of editing Supabase or the Sheet directly. The user asked for a note in Pending Value for exactly this case: something that shows the process ran, and when tapped, shows the title + its guessed value + an option to change it.
- **Eligibility, defined purely by two existing columns** - `estimated_value_is_estimate = true AND estimated_value_is_manual = false` (the new column, see below). This naturally covers both ways a title ends up here without any path-specific code: zero candidates ever survived the hard gate, or the user reviewed a real candidate set and rejected everything - both just set the same two columns already, so no new state needed to distinguish them.
- **`estimated_value_is_manual`** (`0024_add_estimated_value_is_manual.sql`) - same `rating_is_manual`/`studio_is_manual`/`original_language_is_manual` precedent as `0005_add_tmdb_fields.sql`: protects a value a human has actually looked at and confirmed or edited from ever being silently overwritten by the 6-month recheck sweep (`refresh.ts`'s `fetchOverdueTitles` now excludes `estimated_value_is_manual = true`). Defaults `false` (the opposite default from `original_language_is_manual`, which defaults `true`) - deliberately, since every *existing* `estimated_value` came from this feature's own automation, never a human decision, so the migration should surface the whole existing backlog of guesses into this new queue immediately, not treat them as already-reviewed.
- **API**: `apps/web/src/app/api/estimated-value/auto-estimated/route.ts` (POST/list, same signed-URL-resolution convention as `pending/route.ts`) and `.../auto-estimated/confirm/route.ts` (POST, `{titleId, value}` - always sets `estimated_value_is_manual = true` and clears `estimated_value_is_estimate`, whether or not the number actually changed from the guess, then pushes the result to the Sheet via `pushEstimatedValuesToSheet`).
- **Mobile**: `PendingValueScreen.tsx` now merges two API calls into one flat list (`PendingValueRow`, a `"review" | "estimated"` union) rather than two separate screens/sections - both are "things sitting in Pending Value" from the user's perspective, differing only in row content and which detail screen they open. A new `AutoEstimatedDetailScreen.tsx` is deliberately much simpler than `PendingValueDetailScreen.tsx` - no candidates, no accept/reject, just the title, poster, and one editable value field pre-filled with the current guess. Tapping Confirm without editing it accepts the guess as-is; editing it first saves the new number instead - both cases hit the same `confirm` action, since there's no meaningful difference between "confirming an unedited value" and "retyping the same number." As of 2026-09-17, this same screen also carries the opt-in "Try Amazon Search" button and quota progress bar - see RESELLER-FIRST / AMAZON-AS-OPT-IN below for why this exact screen, rather than a new one, is where that lives.

**RECURRING JOB (the 6-month RECHECK sweep only - see TRIGGER above for how a title first gets priced)** - follows the `refresh-tmdb.ts` / `instrumentation.ts` precedent shape, but scoped down per the TRIGGER correction:
- `scripts/src/refresh-estimated-value.ts`, a standalone runner (small default `limit`, e.g. 3, since each title can mean several slow scrape calls across up to 4 sites - unlike TMDb's cheap single API call).
- A third interval block in `apps/web/instrumentation.ts` alongside the existing pending-scans poller and TMDb refresher, same Fast-Refresh double-registration guard. Long interval (30-60 min) with a small batch (2-3 titles) per tick - ordinary politeness toward the retail sites being re-checked, not a workaround for a large backlog (there isn't one - this sweep only ever touches titles that already have a real, now-stale price, a small and slowly-growing set, never a never-priced title).
- `apps/web/src/app/api/estimated-value/refresh/route.ts`, `requireScanSecret`-gated, the route a future Vercel Cron entry would target (no Cron config exists yet, same "run by hand until Cron exists" state the TMDb refresher is already in).

**PUBLIC EXCLUSION** - the first feature in this codebase where the public and private builds' *database schemas* diverge. Every migration before this one applied to both Supabase projects (`deployment-and-security.md`: "migrations run against both live Supabase projects via the Management API") - migration `0021_estimated_value.sql` is private-project-only.

Mechanism, extending `scripts/src/sanitize-public-repo.ts`:
- `0021_estimated_value.sql` and every estimated-value-specific file (`packages/backend/src/estimatedValue/`, `apps/web/src/app/api/estimated-value/`, `PendingValueScreen.tsx`, `PendingValueDetailScreen.tsx`, `apps/mobile/src/lib/estimatedValueApi.ts`, `scripts/src/refresh-estimated-value.ts`) are added to `EXCLUDE_FILENAMES`/`EXCLUDE_DIRS`, the same mechanism already used for the Letterboxd migrations/scripts.
- The real snag Letterboxd never hit: this feature also has to add a few lines to *shared* files that exist in both repos - the "Pending Value" button on `PendingScansScreen.tsx`, the third interval block in `instrumentation.ts`, two new `Screen` union members/render branches in `App.tsx`, barrel-export lines in `packages/backend/src/index.ts`, and the 4 new `Title` fields in `packages/shared/src/types.ts`. Left alone, the public repo's copies of the first four would reference code that no longer exists there and fail to build; `types.ts` is lower-stakes (a missing type declaration doesn't break a build the way a missing import does) but is stripped too for consistency, so the public repo doesn't even name these columns anywhere.
- Resolution: a new `stripMarkedBlock(filePath, startMarker, endMarker)` post-processing step in `sanitize-public-repo.ts` (same category as the existing `stripLetterboxdNpmScript`, which already edits a copied file after the plain tree copy). Each of the 4 shared files wraps its estimated-value-specific lines in `// ESTIMATED-VALUE-PUBLIC-EXCLUDE-START` / `-END` sentinel comments; the strip step deletes everything between each marker pair in the public copy only, so the public repo's copies of these files genuinely never contain the feature's code, not just a runtime-hidden version of it.
- `poster_image_path` was considered for its own dual-project migration (letting the public demo dataset get cached posters too), but the user decided against it - the public build exists only to demonstrate the codebase, not for real use, so it stays bundled into the private-only `0021` migration.
