**TECH STACK AND ARCHITECTURE**

This document turns the plan in AIM.md and STEP BY STEP PROCESS AND AUTOMATION.md into a concrete technical design. It doesn't replace those documents, it specifies how to build what they describe. If a future session changes any of these decisions, update this file and move the old decision to the Backlog section at the bottom rather than deleting it.



**REPO / MONOREPO LAYOUT**

One monorepo (Turborepo + npm workspaces — pnpm was the original plan, but its global install hit a Windows permissions error via corepack, so npm workspaces are used instead; functionally equivalent) during development, split into the public/private GitHub repos described in Claude.md at publish time (see PUBLIC VS PRIVATE BUILD PIPELINE below).

- apps/web — Next.js (TypeScript) web app. Deployed to Vercel. This is the Netflix/IMDB-hybrid browse and search experience described in WEB APP DESIGN.md.
- apps/mobile — Expo/React Native app. Same browse/search UI reused where practical, plus the barcode scanner screen. Exported to an APK via `eas build --platform android` so it can be sideloaded per STEP BY STEP PROCESS AND AUTOMATION.md's "export as .apk" note.
- packages/shared — TypeScript types for the DVD/collection schema, the Supabase client wrapper, search/filter/taste-profile logic, and other pure/fetch-based helpers used by both apps (crucially including `apps/mobile`) so the matching algorithm only exists once. Nothing here should need a Node-core module (`fs`, `util`, `stream`, ...) that Metro can't bundle.
- packages/backend — Node-only backend logic (currently just the barcode-scan resolver and its cover-photo image-matching, which needs Jimp for image decoding) that only `apps/web` and `scripts/` import, never `apps/mobile`. Split out from packages/shared specifically because Jimp broke Metro's bundling of the mobile app once it became reachable from shared's barrel export - see the BARCODE SCANNING PIPELINE section below for the full story.
- scripts/ — the Google Sheet ⇄ Supabase sync jobs and the public-repo sanitization script.

Reasoning: a single native codebase (Expo) covers both "export as .apk" and iOS later if wanted, and the shared package means the taste-profile/search logic behind Aim Three and Aim Four is written once and used identically on web and phone.



**DATABASE DESIGN (Supabase / Postgres)**

Supabase was chosen over a self-hosted SQL database because it gives a managed Postgres instance, auth, file storage (for DVD case images), an auto-generated REST/JS client, and Row Level Security, all on a free tier sufficient for a personal collection database. This satisfies STEP BY STEP PROCESS AND AUTOMATION.md step 1 ("copy the Google Sheet data into a high-performance SQL database that takes priority over the Sheet for processing time").

Two separate Supabase projects, not one project with filtered views:
- A private project holding the entire real collection and real taste-profile names.
- A public project holding only the Friends TV show, X-Men, Star Wars, and the Film Noir boxset, with anonymized taste-profile names, matching Claude.md's public-build description exactly.

Keeping these as two physically separate databases (rather than a filter flag on one database) means the public build can never accidentally expose private rows through a bug in a query filter.

Schema: one core table modeled directly on the "All DVDs and Specs" Google Sheet columns from RESOURCES.md (Title, Movie or TV, Season No., Part of a Season No., Episode Count, Release Date, Running Time, Genre, Director, Franchise, Sub-franchise, Rating, Format, Disc Count, Special Features, Special Features Disk Count, Special Features Disk Format, Animation/Live Action, Documentary, Collection, Name of Collection, Title in a Collection, Number of Titles in a Collection, Rotten Tomatoes Page, IMDB Page, Studio, Disk Region), plus the new columns STEP BY STEP PROCESS AND AUTOMATION.md already calls for:
- unique_id (primary key used for barcode re-scans and future column backfills)
- barcode_id (so re-scanning a title later doesn't require re-scanning the physical barcode)
- case_image_url (points at Supabase Storage)
- genre_location (the single genre the title actually sits under on the shelf, separate from the possibly-multiple Genre column, used for the shelf-location suggestion in Aim Five)
- last_updated (timestamp, needed for the Sheet sync below)
- steelbook (boolean, added migration 0003 - some items have a steel case with better artwork instead of a plastic one; see Claude/DEFINITIONS.md). Previously this was just a word typed into Format ("DVD Steelbook") - `scripts/src/backfill-steelbook.ts` (one-time, already run) stripped that word back out of Format for the 13 existing rows that had it and set this column instead, since packaging attributes deserve their own column rather than being buried in free text that's supposed to just say the disc format.
- release_name (text, nullable, added migration 0004 - the verbatim edition/packaging title as printed on the disc, e.g. "Gladiator Special Edition", when it differs from the canonical `title` used for OMDB matching and cataloguing, e.g. "Gladiator". Left null/"n/a" when they match. Manual-only in ConfirmScreen - unlike title/format, there's no reliable text signal for which words in a UPC listing are "part of the release name" vs. ordinary packaging noise, so no auto-fill guess is attempted.)

**Scanner-entered text normalization**: after the Format-spelling cleanup above kept resurfacing the same underlying risk for other free-text fields, `/api/scan/confirm` now normalizes every scanner-originated field before insert, so random capitalization/spacing typed on a phone keyboard never creates a near-duplicate category:
- `format` and `special_features_disc_format` go through `normalizeFormat` (packages/shared - the same fixed `FORMAT_ALIASES` table used for the Format backfill).
- `disk_region` and `genre_location` go through `apps/web/src/lib/canonicalizeValue.ts` - these have no fixed enum (unlike Format), so it does a live case-insensitive (`ilike`) lookup against whatever's already in `titles` and reuses that exact existing spelling/casing if found, falling back to the trimmed input only when nothing matches yet.
- `title` and `release_name` only get whitespace trimmed/collapsed (`cleanFreeText`, packages/shared) - never case-folded, since they're proper nouns/verbatim packaging text where casing is intentional (e.g. it would be wrong to silently rewrite "THX 1138" or a colon-suffixed collection name).
Verified end-to-end against the real database: a value differing only by leading/trailing whitespace and case correctly resolved to the exact existing genre_location's casing rather than creating a new entry.

Row Level Security: public read access for anything the browse/search UI needs; all writes require the authenticated owner (Supabase Auth, single account — see AUTH below). This is the actual security boundary, not just hiding UI elements.

**Format normalization**: the real Sheet had accumulated ~19 distinct spellings of Format for really 7 physical formats (casing drift like "BLu-Ray"/"Blu Ray", double spaces, "4k" vs "4K") - noticed via the Confirm screen's Format autocomplete showing several near-duplicate suggestions for the same thing. `packages/shared/src/titleParsing.ts`'s `FORMAT_ALIASES`/`normalizeFormat` is the single canonical mapping (DVD, DVD (Custom Burn), DVD 3D, Blu-Ray, Blu-Ray 3D, 4K UHD Blu-Ray, CD Movie - Custom Burn and the 3D variants are deliberately kept as their own distinct formats, not folded into plain DVD/Blu-Ray, since they're genuinely different physical media, not spelling variants), applied automatically to every Sheet sync from here on and also used to keep `extractFormatHint`'s scan-time guesses (`packages/shared/src/formatHints.ts`) spelled identically. `scripts/src/backfill-format-normalization.ts` (one-time, already run) cleaned up the 132 existing rows that predated this - verified end to end (Sheet edited, re-synced, and the resulting Supabase distinct-value counts checked against the predicted merge) down to exactly the canonical set with no strays.

**Sheet append bug (found via "Paper Planes," the first real scan-confirmed entry)**: `appendRowToSheet` used to call the Sheets API's `values.append` with an unbounded range (just the tab name), trusting its own "find the table, append after it" auto-detection. Against this Sheet's fixed 4000-row grid, that auto-detection was unreliable and consistently landed new rows at row 4000 regardless of where the real data actually ended (row 3064 at the time) - it silently misplaced every scan-confirmed append this way, leaving ~935 blank rows in between. Fixed by computing the target row explicitly: reading the Title column (`NOT NULL`, so always non-blank on a real row) via `values.get`, then writing with `values.update` at `data.values.length + 1` - sidesteps the ambiguous auto-detection entirely rather than trying to out-guess it. Verified live: a fresh append landed at the correct next row immediately after the fix.

**Running Time's Sheet format**: the real Sheet's existing convention is the unit typed directly after the number with no space (e.g. "154mins"), which a plain numeric write from the confirm route didn't match. `formatRunningTimeForSheet` in `packages/shared/src/titleParsing.ts` (registered in `SHEET_FIELD_FORMATTERS`) fixes this going forward; `toInt()` on the read side already tolerated the suffix fine (parseInt stops at the first non-digit character), so only the write path needed a formatter.

**Boolean Sheet formatting isn't actually uniform across columns**: `formatValueForSheet`'s blanket `boolean -> "y"/"n"` was silently wrong for Special Features specifically - noticed once a scan-confirmed row (Paper Planes) got written with "y" while every other row in the real Sheet uses full "Yes"/"No" for that column (confirmed: 1587 "no"/1429 "yes" vs. a single stray "y"). The distinction is real, not arbitrary: Collection and Title in a Collection's headers literally say "(y/n)" and their data genuinely favors that abbreviation, while Special Features' header has no such qualifier and its data favors the full word. `formatYesNoForSheet` (registered in `SHEET_FIELD_FORMATTERS` for `special_features` and `steelbook` - the latter this project's own new column, given the same convention for consistency with its similarly-unqualified header) fixes this; `toBoolean()`'s `YES_VALUES` set already accepted both spellings on the read side, so only the write path needed fixing. `scripts/src/backfill-yesno-normalization.ts` (one-time, already run) corrected the 15 existing mismatched cells (Paper Planes' Special Features + every Steelbook `y`/`n` from the earlier backfill) - deliberately left Collection/Title in a Collection untouched, since abbreviated `y`/`n` is genuinely their own established convention, not a bug.



**GOOGLE SHEET SYNC**

Phase 0 ran a one-off manual sync (`scripts/src/sync-sheet.ts`, Sheet → Supabase) to get the real ~3,063 existing entries into the private Supabase project for the first time — that script also auto-created the Unique Identifier/Barcode Identifier/Genre Location columns the Sheet didn't have yet, and backfilled a UUID into every row.

Ongoing sync is bidirectional and near-real-time, not one-way or manual, because the user will keep editing the Sheet directly (typos, genre reclassification, bulk cleanup) alongside app-originated writes, and the database must never go stale relative to either source:
- **Sheet → Supabase**: a Google Apps Script bound to the spreadsheet with an `onEdit(e)` trigger `UrlFetchApp.fetch()`s the edited row to a `/api/sheet-webhook` endpoint (`apps/web`, secret-gated), which upserts just that row into Postgres using the same field-normalization helpers as everything else (`packages/shared/src/titleParsing.ts`). See BARCODE SCANNING PIPELINE below — the Apps Script source lives in `apps/sheet-scripts/onEdit.gs` since Apps Script itself runs inside the Sheet, not in this codebase; the user pastes it in via Extensions → Apps Script.
- **Supabase → Sheet**: writes that originate from the app (barcode-scan confirms, later Direct Database Access edits) go to Supabase first, then push back to the Sheet via the Sheets API, reusing the same append/update logic `sync-sheet.ts` established.

The `last_updated` column (auto-set by a Postgres trigger on every row write) is available if last-write-wins conflict detection is ever needed, but isn't load-bearing yet since each direction currently writes disjoint fields per event rather than racing on the same row.



**BARCODE SCANNING PIPELINE (Aim One)**

Blu-ray.com is confirmed to have no API or sanctioned query path at all (their own forum: "Does blu-ray.com provide an API for developers? No" — asked repeatedly since 2018, never changed), and their per-IP scraping tolerance is undocumented and unprotected, so it's excluded entirely as a data source, not just deprioritized.

The user also clarified this isn't just steady-state logging of new purchases — the entire existing collection needs its barcode/case-image data backfilled too, which is a bulk operation, not a trickle. That reshapes the pipeline: **scanning and lookup are decoupled**, so a free API's daily rate limit never gates how fast the user can physically scan their shelves.

1. Expo camera screen (`expo-camera`'s `CameraView`, `barcodeScannerSettings.barcodeTypes: ['ean13','upc_a','upc_e']`, `onBarcodeScanned`, permission via `useCameraPermissions()` — confirmed current for SDK 57; the older `expo-barcode-scanner` package is deprecated/removed since SDK 51) reads the barcode and, once actually committed (see the hold-steady countdown below), writes `{ barcode, scanned_at }` to a new `pending_scans` Supabase table via a secret-gated endpoint, then returns straight to the camera. No network wait, no per-scan lookup — the user can scan hundreds of discs in one sitting.
   - **A 3-second hold-steady countdown gates every scan** (`COUNTDOWN_MS` in `ScannerScreen.tsx`, per the user's own request): the very first sighting of a barcode no longer queues it instantly - `pendingBarcodeRef` tracks `firstSeenAt` for the current hold, and only once the same code has been continuously in frame for the full 3 seconds does it actually queue, showing "Barcode detected - hold steady... N" in the meantime. This exists specifically to avoid queueing a barcode glimpsed only briefly while lining up the shot (a neighbouring disc's code passing through frame, a shaky first attempt at aiming) - only a barcode the user is deliberately holding still counts. `queued` on the same ref then prevents re-firing on every subsequent frame once that hold has already been committed, exactly like before.
   - Two independent debounce layers still prevent duplicate queueing on top of the countdown: `SIGHTING_GAP_MS` (2s, local state inside `ScannerScreen.tsx`) decides whether a new sighting is "still the same hold" (a brief gap between frames) or "you looked away and came back" (resets the countdown for a fresh hold), and `RECENT_QUEUE_COOLDOWN_MS` (5 minutes, per the user's own suggestion) separately remembers every barcode's last-queued time so pointing back at the same case a few seconds or minutes later doesn't create a second `pending_scans` row for it. Both are keyed on the literal barcode value, so two different physical releases of the same film — which necessarily have different barcodes — are never affected by either debounce. The 5-minute map lives in `App.tsx`, not `ScannerScreen.tsx` itself, since `ScannerScreen` unmounts every time the user navigates to Pending Scans and back (App.tsx's screen switch is plain conditional rendering, not a navigator that keeps screens mounted) — local state there would silently reset the cooldown on every trip to review scans. Deleting a pending scan (either the Pending Scans list's bulk delete, or Confirm screen's single discard) also forgets that barcode's cooldown entry immediately, per the user's own request: having just discarded it, they clearly want to rescan it right away rather than wait out the rest of the 5 minutes.
2. A **resolver** (reusable function, called from a manual script, an auto-poller, and, later, a scheduled job) works through `pending_scans` at a safe rate: looks the barcode up against UPCitemdb (chosen UPC/EAN lookup service — free tier, no signup/card, 100 requests/day; the only other options found either have no free tier at all or an undocumented one, and buying UPCitemdb's cheapest paid tier is $99/mo, which is only worth it as a one-time month if the free-tier backfill drain feels too slow later — not decided now), then cross-references OMDB for movie metadata (OMDB prioritized over IMDB per RESOURCES.md, since OMDB has a public API and IMDB doesn't) using OMDB's own `Type` field (`movie`/`series`/`episode`) to know whether TV-only fields even apply. Marks each pending scan `resolved` (found confident candidates) or `needs_manual` (nothing confident found).
   - **Auto-polling in `apps/web`**: `instrumentation.ts`'s `register()` hook (a stable Next.js server-boot hook, not a route) starts a 15-second `setInterval` that calls the resolver on whatever's pending (batch limit 20) for as long as `next dev`/the deployed server process is running — this replaced repeatedly running `npm run resolve-scans` by hand during real-device testing, which was mistaken for a bug ("I scanned it but it's not showing up") more than once before this existed. Deliberately still a poll rather than resolving on every `/api/scan/queue` call, so scanning and lookup stay decoupled and a bulk shelf-scanning burst can't blow through UPCitemdb's 100/day cap just by scanning fast — a big backlog drains gradually over many ticks instead of firing one lookup per scan back-to-back. The manual script and `/api/scan/resolve` route both still exist (the route is what a Vercel Cron job will call once deployed, superseding this poller then).
3. A pending-scans review screen (mobile) lists resolved/needs-manual entries; the user confirms the suggested match, edits fields, or fills in manually — mirroring Claude's own clarifying-question style per STEP BY STEP PROCESS AND AUTOMATION.md (skipping fields that don't apply, e.g. never asking for a season number on a movie).
4. **Review-screen auto-fill and candidate narrowing** — the review screen never presents a bare barcode; several fields start pre-filled as editable guesses, and the OMDB candidate list itself is narrowed before the user ever sees it:
   - `title` starts pre-filled with the UPC listing's own title, cleaned the same way the OMDB search query is (packaging/format words, marketplace-resale noise, and packaging-edition qualifiers like "Special Edition"/"Collector's Edition" stripped — those are marketing fluff, not a content distinction, unlike a genuinely different cut like "Final Cut" which the user does keep in a title). Always editable, never presented as confirmed.
   - `format` starts pre-filled from a text-pattern match on the listing (`extractFormatHint` in `packages/shared/src/formatHints.ts` — checks for 4K/UHD before Blu-ray so a "4K UHD Blu-ray" combo isn't miscategorized as plain Blu-ray). This can only work with words actually present in the listing text — if a listing just says "Blu-ray" with no "4K"/"UHD" mention at all even though the physical disc is a 4K combo pack, there's no text signal to catch that; the field stays user-editable specifically because this guess can be wrong.
   - The OMDB candidate list is narrowed using the listing's own year as a chronological upper bound (`extractProductYear` + `filterCandidatesByMaxYear`): a listing's year is the disc's *home-video release* year, not necessarily the film's, but home video always follows theatrical release, so any OMDB candidate whose Year is *after* the listing's year is eliminated outright — a disc can't exist for a film that hasn't been released yet. Never eliminates every candidate (falls back to the unfiltered list) since the extracted year is itself just best-effort text parsing.
   - When UPCitemdb's own listing has a product photo, it's shown on the review screen captioned as "your scanned item" specifically because it's a photo of the actual listing, not a generic poster — the most useful single signal for telling apart releases of the same film that share a title and year (special editions, different regions, different bonus-features packaging) but look different on the shelf. Candidates without their own photo still show OMDB's poster in the horizontal candidate list, but that's a generic per-*film* image, not a per-*edition* one.
   - **Auto-matching by cover photo**: when the listing has its own photo, it's automatically compared against every OMDB candidate's poster using perceptual image hashing (`matchPosterToCandidates` in `packages/backend/src/posterMatch.ts` — Jimp's pHash/compareHashes, a DCT-based hash compared by Hamming distance, normalized 0..1 where 0 is identical). Deliberately conservative: only reports a confident match when the best result is both close in absolute terms *and* clearly ahead of the runner-up, since a resale-listing photo of a plastic case often looks quite different from OMDB's stylized theatrical poster even for the objectively correct film (different framing, cropping, an added disc-shaped overlay, background) — thresholds were verified against synthetic identical/unrelated-image pairs (0 vs. ~0.375), not yet against a real photo-vs-poster pair from an actual scan, since no scan so far has had both a UPC photo and needed disambiguation. When confident, the review screen shows just that one matched candidate with a "Not this item" escape hatch that reveals the full poster list (everything it was compared against) to pick from manually instead; when not confident (or there's no listing photo at all), the full list shows as before with nothing pre-selected. Skipped entirely for collections, since a box-set's own cover doesn't correspond to any single film's poster.
   - This poster-matching code lives in a separate `packages/backend` workspace, not `packages/shared` — image decoding (Jimp, for the perceptual hash) pulls in Node-core modules (`fs`, `util`, `stream`) that Metro (the mobile app's bundler) can't resolve, and `packages/shared` is the one package the mobile app also depends on. `packages/backend` depends on `packages/shared` and is itself only imported by `apps/web`'s API routes and `scripts/`, never by `apps/mobile`.
   - Explicitly **not implemented**, and moved to the backlog rather than built: listing alternate physical releases/editions of a film once it's been identified (e.g. "here are the other known DVD/Blu-ray releases of this film"). This hits a hard data-availability wall rather than an effort one — OMDB holds exactly one entry per film with no per-edition/per-pressing data at all, and no API in this stack tracks that (Blu-ray.com, which would have it, has no API and is already excluded entirely — see above). The user's plan is to invent spreadsheet categories/manual workarounds for this instead, to be specified later (see Claude/To Do list.md's BACKLOG).
   - **Format / Disk Region / Genre Location are autocomplete fields, not free-typed with no help**: `apps/mobile/src/lib/fieldOptions.ts` loads every distinct existing value for these three columns from `titles` (public-read RLS, so the anon key can query it directly), and `AutocompleteInput` (`apps/mobile/src/components/AutocompleteInput.tsx`) filters that list as the user types, offering a tap-to-fill suggestion while still accepting anything typed as free text. There's no fixed enum in the schema for any of these three columns - typing a genuinely new value once just makes it appear as a suggestion for every future scan, since the option list is nothing more than "whatever's already in the collection."
   - **Disk Region narrows by Format** (`getDiskRegionOptions` in `packages/shared/src/formatHints.ts`, verified against current region-code references rather than assumed): DVD offers 1/2/3/4/5/6/All (region 7 is reserved/never used on retail product and region 8 is airline/cruise-only, both excluded as unrealistic for a physical collection), Blu-ray offers A/B/C/All, and 4K UHD Blu-ray - which carries no region coding at all - defaults straight to "All" (auto-filled the moment Format is recognized as 4K, but only while the field is still blank, so it never overwrites a deliberate manual entry). An unrecognized format (VHS, CD, ...) falls back to the full unfiltered list of existing Disk Region values instead of a hardcoded scheme, since none applies. **Disk Region is a fixed multi-select, not free text** (`MultiSelectChips` in `apps/mobile/src/components/MultiSelectChips.tsx`) - unlike Format/Genre Location/Rating/Studio, region codes are a genuinely closed set that can't gain new members over time, and some discs are legitimately coded for more than one region at once, so the field is a toggleable set of chips rather than a single autocomplete value; the selected codes are joined into one string ("2, 4") at submit time, matching the existing plain-`text` column rather than needing an array column. Selecting "All" clears every other selection and vice versa, since being region-free is contradictory to being coded for specific individual regions. No `canonicalizeValue` normalization is needed for this field anymore - the option set is fully closed client-side, so there's no free-typed casing/spacing to drift. **"Not Listed"** (`NOT_LISTED_REGION` in `formatHints.ts`, appended to every format's option list) covers a disc that simply prints no region information anywhere on its packaging - distinct from "All", which means the packaging affirmatively states region-free (or the format's own scheme has no regions at all, like UHD). Added after the user found a real disc with no region info printed at all, rather than the app just assuming one. `MultiSelectChips` now takes a generic `exclusiveOptions` prop (default `["All"]`) so both "All" and "Not Listed" are mutually exclusive with every other option and with each other, instead of "All" being hardcoded as the only special case. Since "Not Listed" is now always appended, the old 4K-auto-defaults-to-"All" effect could no longer key off "the option list has exactly one entry" (that's now 2 for UHD) - it uses the new `isRegionFreeFormat` helper instead, which checks the format text directly.
   - **Steelbook** is a plain boolean switch next to Special Features (see the steelbook/release_name column notes in DATABASE DESIGN above).
   - **Special Features Disc Count / Format of Special Features Discs** only appear once Special Features is switched on *and* disc count is more than 1 - there's nothing to count when there are no special features, and a single-disc release can't have a separate bonus-features disc. Confirmed with the user this AND condition (rather than disc-count alone) matches their intent; these two fields aren't exclusive to collections - any multi-disc release, box set or not, can have one of its discs be a dedicated bonus-features disc.
   - **Release Name** is manual-only (see DATABASE DESIGN above) - it sits right under Title/before Format in the review screen, shared across every member title for a collection scan exactly like Format/Disc Count/Steelbook already are, since a box set's release name describes the one physical object, not any single film inside it.
   - **Rating and Studio only appear as manual fields when TMDb can't provide them** - since TMDb now auto-fills both (see the TMDb section below), asking the user to type in something TMDb is about to supply anyway would be redundant. `/api/scan/tmdb-preview` (a read-only, purely informational lookup - the actual authoritative one that gets stored still happens independently inside `/api/scan/confirm`) is called from `ConfirmScreen` the moment a single candidate is selected; the manual Rating/Studio fields stay hidden while that check is in flight and only reveal individually if TMDb genuinely came up empty for that specific field. With no candidate selected at all (pure manual entry, no `imdbId` to look up), the fields show immediately, since TMDb can never be tried in that case. **Unlike every other manual field, these are NOT shared across a multi-title collection** - a box set's cover only ever shows one rating/studio for the entire set, which isn't necessarily any individual film's own rating, so manual Rating/Studio entry is hidden entirely for a multi-title selection (and independently nulled out server-side in `/api/scan/confirm`, as a safety net beyond just hiding the UI); each member title instead gets its own from TMDb once confirmed.
   - **Rating normalization**: like Format, the real Sheet had casing drift ("pg", "m") and a couple of stray typos ("R\`16", "Rr16") on top of the real NZ classification scheme (G/PG/M/R12/R13/R15/R16/R18). `RATING_ALIASES`/`normalizeRating` in `packages/shared/src/titleParsing.ts` is the canonical mapping, applied on every Sheet sync and in `/api/scan/confirm`'s manual Rating field - `rating` stays free text overall (OMDB's own US-style `Rated` value also flows through this column and isn't forced into the NZ table). `scripts/src/backfill-rating-normalization.ts` (one-time, already run) cleaned up the 4 existing rows that predated this.
   - Explicitly **not implemented**: an automated online lookup for Rating/Studio (e.g. from IMDb's parental-guide/company-credits pages) for the collection-member case where there's no single physical case to read from. IMDb's own robots.txt states outright that "any device, tool, or process designed to data mine or scrape the content using automated means is prohibited without prior written permission" - confirmed by fetching it directly - so building that against IMDb isn't something this project does; OMDB's own `Rated`/`Production` fields were checked as a possible substitute and don't reliably solve this either (confirmed live against Paper Planes: `Rated` was the US-style "Not Rated" rather than any NZ/Oceania certificate, and `Production` was blank). TMDb (themoviedb.org) has a genuine free public API that tracks per-country release certifications and production companies and was raised as a real candidate worth pursuing, pending the user obtaining a free API key.
   - **Rotten Tomatoes IS automated** (`lookupRottenTomatoesPage` in `packages/backend/src/rottenTomatoes.ts`), since RT's robots.txt is far more permissive (only a few specific paths disallowed - plain `/m/<slug>` movie pages aren't). OMDB's own `Ratings` array already reports whether a title has a critics score at all (a `"Rotten Tomatoes"` source entry, e.g. `"85%"`) with zero RT requests needed; only once that's confirmed does the function fetch one guessed slug (`https://www.rottentomatoes.com/m/<slugified-title>`) and cross-check the page's own schema.org JSON-LD block - both the film name and the Tomatometer score must match what OMDB already reported, or it returns null rather than a guessed link. Deliberately never overrides a link the user already typed in manually. Verified live: correctly resolved and saved Paper Planes' real page, and independently confirmed the guard rejects both a mismatched score and a nonexistent title rather than false-positiving.
   - **Manual title-search fallback for a barcode that returned nothing at all** (`apps/web/src/app/api/scan/title-search/route.ts`, `searchTitleOnOmdb` in `apps/mobile/src/lib/scanApi.ts`): sometimes UPCitemdb has no listing whatsoever for a barcode, meaning the resolver never had any title text to search OMDB with in the first place - the old behaviour dumped the user straight into a blank manual-entry form with no candidate list at all. `ConfirmScreen` now detects this specific case (`candidates.length === 0 && !upcProduct && !hasSearchedOrSkipped` - deliberately narrower than "OMDB found no match," since a listing with its own product photo/description still gives the user something to manually fill in from) and shows a single "what's the title?" text field first. Submitting it calls the new route, which hands results back into the exact same candidate list state the automatic pipeline populates - so poster selection, cover-photo auto-matching, the TMDb Rating/Studio preview, and Confirm all work completely unchanged from that point on, with no separate code path to maintain. A "Skip - enter manually instead" link bypasses the search entirely (for a title OMDB likely won't have, e.g. an obscure regional release) and prefills the ordinary manual Title field with whatever was typed. Both the typed query and any search results survive navigating away and back, via the same `confirmDrafts.ts` cache every other in-progress field on this screen already uses. **A single candidate (from either the automatic resolver or a manual search) is auto-selected** rather than making the user tap it - nothing to disambiguate when there's only one option, and it's still fully reversible (tapping it again deselects it like any other candidate).
   - **Typo correction for the manual title-search route** - built after empirically disproving the original assumption behind it. It was first assumed TMDb's own search API would be meaningfully more typo-tolerant than OMDB's literal substring search, and built as a second parallel search pass on that basis; live testing then showed this was wrong - TMDb's search returned zero results for realistic typos ("Jurrasic Park", "Lord of the Rngs", "The Shawshenk Redemption" all returned nothing from both OMDB and TMDb). That TMDb-search pass was kept anyway (it's still a genuinely different index that occasionally has a title OMDB lacks, and is now re-run with the corrected query too - see below), but doesn't solve typos on its own. Real typo tolerance is now three layered passes in the route, each merged into the final candidate list by imdbID (never replacing the previous pass's results, only adding to them - per the user's own explicit design that a spelling correction should never hide "results from what the user actually input"):
     1. OMDB + TMDb search using the user's exact typed text (unchanged).
     2. The same two searches again using a spelling-corrected version of the text (`correctSpelling` in `packages/backend/src/spellcheck.ts`) - an `nspell`/`dictionary-en` Hunspell-style English dictionary corrector, run only on individual words the dictionary both flags as misspelled and has a suggestion for (skips words already correct, and words 2 characters or shorter, e.g. "Ex" in "Ex Machina"). Verified live: fixes "Jurrasic" -> "Jurassic" and "Gladiaor" -> "Gladiator" correctly, but is also verified to sometimes guess wrong ("Titanik" -> "Titania", "Rngs" -> "Rags") and to return no correction at all for a name that isn't a real English word in the first place ("Shawshenk" - since "Shawshank" itself isn't a dictionary word either). A wrong guess is a low-risk failure mode specifically because pass 1's literal results are always present alongside it - it just adds an irrelevant extra candidate rather than replacing the correct one.
     2b. `dictionary-en` is ESM-only (a top-level `await` inside its own module) and is loaded via a **dynamic** `import()` inside `spellcheck.ts` rather than a static one - a static import broke every script in `scripts/` that transitively imports anything from `@danflix/backend`'s barrel export (confirmed live: `npm run refresh:tmdb` failed under `tsx`, which transforms scripts to CommonJS by default, and esbuild can't transform an ESM top-level-await module into CJS). A dynamic `import()` is left alone by that transform and Node natively supports loading an ESM module this way regardless of the caller's own module format, fixing it without changing any consumer's module settings.
     3. Only when passes 1 and 2 together found nothing at all: a fuzzy match against `tmdb_title_index` (`supabase/migrations/0006_tmdb_title_index.sql`, `0007_tmdb_fuzzy_rank_by_popularity_band.sql`) - a local copy of every real TMDb movie title (imported from TMDb's public daily bulk export, `https://files.tmdb.org/p/exports/movie_ids_MM_DD_YYYY.json.gz` - URL pattern and per-line schema `{adult, id, original_title, popularity, video}` confirmed live by downloading and inspecting a real file rather than trusting the docs summary alone, which didn't fully list the fields), matched via Postgres's `pg_trgm` trigram similarity extension through a `fuzzy_search_tmdb_titles` RPC function (PostgREST can't express the `%` trigram operator through its normal filter syntax). This is the pass that actually catches an invented/proper name a generic English dictionary never could ("Shawshenk" -> "The Shawshank Redemption", "Rngs" -> "The Lord of the Rings", "Titanik" -> "Titanic") - verified live against all three. Ranks by similarity first, but rounds it to one decimal place before ranking so near-identical matches fall into the same band and popularity breaks the tie within it (fixed live after an obscure foreign title with marginally higher raw similarity - "Bife 'Titanik'", popularity 1.9 - initially outranked the real "Titanic", popularity 45.5, on a 0.015 similarity difference alone). Bulk-imported via `scripts/src/refresh-tmdb-title-index.ts` (`npm run refresh:tmdb-title-index` - ~1.24 million non-adult titles, batched upserts of 2000; run by hand for now, weekly is plenty since TMDb regenerates the export daily and new titles are the only thing that changes). Resolving a fuzzy hit's IMDb id/poster/year still costs one `/movie/{id}` TMDb call per hit (same as the search-pass candidates), so this stays a last-resort fallback rather than always-on. **A separate `tmdb_tv_title_index`** (`0009_tmdb_tv_title_index.sql`, `scripts/src/refresh-tmdb-tv-title-index.ts` - ~231k rows from TMDb's daily `tv_series_ids_MM_DD_YYYY.json.gz` export, schema `{id, original_name, popularity}`, no `adult` field at all unlike the movie export) exists purely to support auditing the existing collection's TV/documentary titles for misspellings the same way (see BACKLOG note below) - the manual title-search route itself is movie-only (`omdbSearch`/`searchTmdbMovies` search movies), so this second index isn't wired into that live route, only used ad hoc via `fuzzy_search_tmdb_tv_titles`. Both index-building migrations bake in the exact-match-priority fix from the start (0008's lesson learned on the movie index).
   - **"Custom/homemade disc" toggle skips spelling correction entirely** - the collection's `format = "DVD (Custom Burn)"` discs (32 rows) are the concrete real-world case the typo-correction passes above can actively hurt: many are non-English/obscure franchises with genuinely unusual-looking names, and a few are the user's own creations never listed on IMDb/OMDB/TMDb at all - "correcting" toward the nearest English word or nearest real TMDb title is more likely to produce a wrong, confusing suggestion than to catch an actual typo for these. Since Format itself isn't chosen yet at the point the manual title-search step runs (title comes before format in the flow), the user instead flags this manually with a checkbox right in that step; checking it sends `skipCorrections: true` to `/api/scan/title-search`, which then skips both the dictionary-spellcheck pass and the fuzzy-title-index fallback and runs only the literal OMDB+TMDb search. Verified live: searching a real typo ("Jurrasic Park") normally returns 11 corrected candidates, but returns none at all with `skipCorrections` set - confirming the toggle genuinely disables correction rather than just hiding it.
   - **The Pending Scans "+" button creates a barcode-less manual entry** for discs that were never going to have anything to scan in the first place (the user's own custom-burned creations). `pending_scans.barcode` is nullable (`0010_pending_scans_barcode_nullable.sql`) specifically for this - a manual entry is inserted directly with `status: "needs_manual"` and empty `resolved_candidates`, bypassing `"pending"` entirely so `resolvePendingScansBatch`'s poller never touches it (there's nothing to look up: no barcode, no UPC listing). Since `resolved_candidates` is empty and `barcode` is null, `ConfirmScreen`'s existing `needsTitleSearch` check (`candidates.length === 0 && !upcProduct`) is already true immediately - a manual entry lands on the same manual title-search step as a barcode that scanned but returned nothing, with zero additional branching needed there. Every other `scan.barcode`-dependent code path (the confirm route's `barcodeId`, the backfill-match "attach to existing entry" flow, the scan-cooldown forget-on-discard callback) treats a null barcode as "nothing to attach/forget" rather than erroring - genuinely correct behavior, not a workaround, since there never was a barcode for these to begin with.
   - **Rating and Studio ARE now automated too, via TMDb** (`themoviedb.org`) rather than IMDb - `lookupTmdbFields`/`fetchTmdbFieldsById`/`refreshTmdbFields` in `packages/backend/src/tmdb.ts`. TMDb has a genuine free public API (unlike IMDb), so this is what the "automated pipeline for Rating/Studio in a collection" idea became once the IMDb-scraping option was ruled out. Per-entry, keyed by `entry.imdbId` via TMDb's `/find` endpoint (external-id lookup, no title-text search needed) - genuinely per-film data, so unlike the manual Rating/Studio fields it applies to every member of a collection scan, which is exactly what solves the original "the box only has one rating, not each film's own" problem. Priority order at confirm time: a manual entry (single-title scans only, same restriction as before) > TMDb's NZ/Oceania certification + primary production company > OMDB's `Rated`/nothing. Verified live against the real Paper Planes IMDb id: TMDb's NZ certification was "G" (exactly matching the physical case) and its first-listed production company was "Arenamedia" (exactly matching the earlier manual research) - both independent confirmations that TMDb's data is accurate for this collection.
   - **Franchise and Animation/Live Action are now scan-form fields too** - added after the user scanned Casper's Haunted Christmas and found it logged with no Franchise at all and the wrong Animation/Live Action value. The root cause wasn't a bad automated guess: neither field had ever been asked for anywhere in the mobile scan form, so every barcode-scanned title silently got Franchise blank and (per `/api/scan/confirm`'s own code) Animation/Live Action hardcoded to the literal string `"Live Action"` regardless of the truth - this had been happening to every scanned title, not just this one. Franchise stays a plain, always-visible `AutocompleteInput` field on `ConfirmScreen` (prefilled but always editable, never hidden - unlike Rating/Studio). Animation/Live Action, after a follow-up question, works more like Rating/Studio instead:
     - **TMDb has no "Live Action" genre at all** - its genre list (Action, Adventure, Animation, Comedy, Crime, Documentary, Drama, Family, Fantasy, History, Horror, Music, Mystery, Romance, Science Fiction, TV Movie, Thriller, War, Western) either tags "Animation" or doesn't; "Live Action" is purely this collection's own inference from that absence. So once TMDb has actually answered for a title, the two cases are handled asymmetrically rather than both getting the same free-text field: **confirmed live action** (no "Animation" genre) hides the field entirely and locks the value to `"Live Action"`, same as Rating/Studio hiding once TMDb has an answer - there's genuinely nothing for the user to pick. **Confirmed animated** keeps the field visible as a real style dropdown (`fieldOptions.animationOrLiveAction` with `"Live Action"` filtered out of the options list, since it's not a valid answer once TMDb has confirmed Animation), for the *specific* style (2D/3D/Puppet/Claymation/Stop-Motion/Anime/hybrid - this collection's own existing data already uses all of these, TMDb has no such field at all) which stays a manual choice.
     - **`isAnimated` is three-valued** (`true`/`false`/`null`), not a plain boolean, in `fetchTmdbFieldsById`/`lookupTmdbFields` (`packages/backend/src/tmdb.ts`) and `TmdbPreview` (`apps/mobile/src/lib/scanApi.ts`): `false` is a confirmed "TMDb has genre data and Animation isn't in it", but `null` covers both "no TMDb match for this IMDb id at all" and "the detail fetch itself failed" - genuinely unknown, not a confirmed live-action answer. Conflating `null` into `false` (the original implementation, fixed after being asked directly what TMDb's actual categories were) would have hidden the field and silently forced `"Live Action"` on a title TMDb was never actually able to answer for. `null` behaves like "no candidate selected at all" - field stays visible, full option list, no forced value.
     - **A blank confirmed-animated field can't be allowed to fall through to the server's default.** `/api/scan/confirm` still defaults a blank `animation_or_live_action` to `"Live Action"` (the right call when there's truly no signal - a multi-title collection scan, or no candidate selected). But if TMDb has confirmed Animation and the user leaves the now-visible style dropdown untouched, the mobile client sends `"Animation"` instead of `null` in that one specific case, so the server's blanket default can never mislabel a title TMDb already confirmed isn't live action.
     - **Franchise prefill via Wikidata** (`packages/backend/src/wikidata.ts`) - verified before writing any code that TMDb's own `belongs_to_collection` field doesn't reliably capture franchise membership (it's `null` for Casper's Haunted Christmas despite obviously being a Casper film - no free "franchise database" exists at all), and separately verified that Wikidata's own documentation (`wikidata.org/wiki/Wikidata:Data_access`) explicitly permits bot/API access to its SPARQL query service - unlike IMDb's outright ban, the `Disallow: /sparql`/`Disallow: /w/` lines in its robots.txt are there to stop search-engine crawlers from indexing those endpoints, not a ban on the deliberate queries Wikidata's own docs teach people to make (followed their etiquette requirements regardless: a descriptive User-Agent, treating a 429 as "back off"). Queries Wikidata's P179 ("part of the series") property, keyed by IMDb id (P345). **P674 ("characters") was tried too as a fallback and dropped after live testing exposed real false positives** - Gladiator (a standalone film, pre-2024 sequel) returned "Marcus Aurelius" as its "featured character", a real historical figure who appears as a dramatized character across many unrelated productions about Rome, not evidence of an actual franchise; a follow-up query confirmed there was no way to algorithmically prefer the "right" character among several plausible candidates either. P179 alone is far more precise (Wikidata editors only set it when a genuine series exists) at a real cost in recall - Casper's Haunted Christmas itself has no P179 claim, so its own Franchise field still needs manual entry even now; that's the honest trade-off, not a bug.
     - **Manual entry for both** uses the exact same `AutocompleteInput`/`fieldOptions.ts` pattern as Genre Location - typing the first few letters offers existing values to pick from (the "dropdown of pre-existing entries" the user asked for). Franchise gets the same case/whitespace dedup as Genre Location via `canonicalizeValue` in `/api/scan/confirm` (it's exactly as open-ended - an ever-growing list the user builds up, not a small fixed set); Animation/Live Action gets a proper alias table instead (`ANIMATION_ALIASES`/`normalizeAnimationOrLiveAction` in `packages/shared/src/titleParsing.ts`, same pattern as `RATING_ALIASES`) since the real Sheet already had 20 distinct typo'd casings of "Live Action" alone by the time this was investigated (some needing an explicit alias entry beyond simple case-folding, e.g. "Live Aciton"/"Live Acrion"/"Lice Action" - genuine letter-level typos, not just casing) - all backfilled in the Sheet + Supabase (`scripts/src/backfill-animation-normalization.ts`, one-time/already run), deliberately leaving genuine hybrid descriptions ("Live Action/Animation Hybrid", "2D Animation and 3D Animation", ...) untouched since those are real combination values, not typos.
     - **TMDb's actual API Terms of Use** (fetched directly and quoted verbatim, not assumed - the general Site Terms of Use the user first found is a different document covering website membership/user contributions, not API use) explicitly prohibit two things relevant here: caching any TMDb-sourced data for longer than 6 months, and displaying TMDb content without a specific attribution notice + logo ("This [product] uses TMDB and the TMDB APIs but is not endorsed, certified, or otherwise approved by TMDB", less prominent than the app's own branding). The caching limit directly conflicts with this project's "store once, keep forever" pattern used for every other field, so two new columns track it: `tmdb_id` (the TMDb movie id, found once via `/find`) and `tmdb_synced_at` (last successful refresh). `refreshTmdbFields` re-fetches anything overdue (never synced, or synced >~5 months ago - a safety buffer under the 6-month limit) on a 1-hour interval in `apps/web/instrumentation.ts` (checks are cheap since almost always nothing is due) and via `npm run refresh:tmdb` for manual/testing use. The user explicitly chose to build this refresh rather than skip TMDb or use it display-only, since ratings/studio names can genuinely change over time anyway (re-classifications, studio mergers/renames) independent of the compliance angle.
     - **`rating_is_manual`/`studio_is_manual` columns protect anything a human actually typed in** (the physical case, or the original Sheet before this feature existed) from ever being silently overwritten by the refresh job - both default to `true` (so the existing ~3063-row collection was automatically protected the moment the migration ran, no separate backfill needed) and are only ever set to `false` by the scan-confirm route, and only when the corresponding field wasn't manually provided. Verified live: a manual override at confirm time correctly took priority over TMDb's values and set both flags true; a fully-manual row was correctly skipped entirely by the refresh job even when deliberately backdated past the cutoff, while a TMDb-sourced (non-manual) row deliberately backdated the same way was correctly picked up and its `tmdb_synced_at` renewed.
     - **Attribution is still owed, not yet built**: the TMDb logo + required notice need to appear once the actual browsable web app (Phase 2+) displays this data publicly - noted here so it isn't forgotten, but not blocking this backend work, since the mobile Confirm screen is a private single-owner cataloguing tool, not the public-facing surface the attribution requirement is really aimed at.
   - **In-progress form state survives leaving the screen**: `apps/mobile/src/lib/confirmDrafts.ts` is a module-level cache, keyed by pending scan id, holding everything the user has typed/selected on this screen. ConfirmScreen restores from it on mount instead of recomputing fresh defaults, and saves to it on every change - needed because ConfirmScreen fully unmounts every time the user navigates to Pending Scans and back (same reason the scan-cooldown map lives in App.tsx, not ScannerScreen), which was previously silently discarding anything entered on an incomplete scan. Cleared only once the scan reaches a terminal state (confirmed, dismissed, discarded, or attached to an existing entry) - a still-incomplete scan keeps its draft indefinitely.
   - **Keyboard avoidance on this screen went through five attempts before settling**: `KeyboardAvoidingView`'s own `"height"` behavior on Android left a blank gap above the keyboard (it double-adjusts on top of Android's native window resize); removing that behavior fixed the gap but let the keyboard cover fields again; `react-native-keyboard-aware-scroll-view` (a dedicated library, meant to fix exactly this) then proved inconsistent in its own right during real testing - sometimes still blocked a field, other times over-corrected and pushed the Confirm button half outside the safe area; a fourth attempt added a static extra bottom padding (`KEYBOARD_SAFETY_PADDING`) as a manual safety margin, but a static value doesn't know the keyboard closed - the user found that scrolling to the bottom with the keyboard open and then closing it left that same dead space permanently, cutting content off or leaving a gap depending on scroll position. Landed on a plain `ScrollView` wrapped in `KeyboardAvoidingView` with `behavior` only set on iOS (`"padding"`) and Android relying entirely on its own native window resize (`app.json`'s `softwareKeyboardLayoutMode`) - explicitly accepting, as a known tradeoff, that the focused field wouldn't automatically snap into view.
     - **That tradeoff turned out not to be acceptable in practice** - the user reported the keyboard blocking lower fields and AutocompleteInput's dropdown results again once they'd used the screen more (reserving room for the keyboard was never the missing piece; nothing ever *moved the scroll position* to bring a field that was already below the fold into that reserved room). Fifth attempt, and the one that actually closes the gap: manual scroll-to-focused-field built directly on RN's own public `UIManager.measureInWindow` (`apps/mobile/src/lib/scrollIntoView.ts`) - deliberately not another third-party library, having already been burned once by `react-native-keyboard-aware-scroll-view`'s own internal inconsistency. A `Keyboard.addListener` pair tracks the live keyboard height (reset to 0 on hide, so it can never go stale the way the static-padding attempt did); every plain `TextInput` on the screen gets a ref and calls `scrollFieldIntoView(findNodeHandle(ref.current))` `onFocus`; `AutocompleteInput` (`apps/mobile/src/components/AutocompleteInput.tsx`) does the same internally via its own wrapping-`View` ref and an `onFocusScroll` prop, called twice (immediately on focus, and again ~120ms later) so the second measurement includes the dropdown's own height once it's actually rendered - the first pass alone would only account for the bare input. The handler measures the focused node's position in the window, compares it against `screen height - keyboard height`, and only scrolls (via a tracked `onScroll` content-offset ref, never React state, to avoid a re-render on every scroll tick) when the node would genuinely be covered - never fights a field that's already visible.
5. **Collections**: since individual titles inside a box set have no barcode of their own, the resolver additionally strips filler words from the collection's product title ("4-Film Collection", "Box Set") to extract a likely franchise/director/actor name, searches OMDB for that, and presents the results as a checklist in the review screen ("which of these are actually in this set?") rather than assuming automatically. Checked titles get their own prefilled entries; an "add a title not found here" manual option covers gaps. Each member title keeps its own real, verbatim `title` (confirmed against the live data - e.g. "The 39 Steps", "Sabotage") plus a `name_of_collection` naming the physical box set; when a box set's own name is too vague to be unique on its own (e.g. "Hugh Grant Collection 4 Favourites" — there could be more than one box set with that same base name over time), the user's convention is to suffix `name_of_collection` with a colon and the comma-separated list of titles actually inside that specific set (confirmed in the real data, e.g. "Alfred Hitchcock A Collection of 10 Classic Alfred Hitchcock Movies: Murder, The Skin Game, Rich and Strange, ..."). This doesn't affect single-title backfill matching (point 8 below), which matches on `title`, not `name_of_collection` - but it will matter once box-set barcode matching is built: disambiguating which physical box set a scan belongs to must compare the full colon-suffixed `name_of_collection` string, not just its vague prefix.
6. **Documentary chronology**: the user's physical shelf splits documentaries into a contemporary/alphabetical section and a "History Documentary" section ordered by the era each one *depicts* (often explicit in the title/synopsis — "The Spanish Civil War", "1936-1939"). A nullable `depicted_era_start` (integer year) column on `titles` is prefilled by a regex pass over the title+synopsis looking for a year/decade/range, falling back to a manual field when nothing is found — no LLM/AI inference call added for this, the regex-plus-manual-fallback approach covers what the user described.
7. On confirm, the completed entry (and every checked title in a collection) is written to Supabase, then to the Sheet.
8. **Backfill matching** (single-title scans only, not yet extended to collections): before creating a new row, the confirm flow checks whether the chosen title is already in the collection without a barcode attached — the actual bulk-backfill case, since most of the ~3,063 existing entries were typed in from the Sheet and have never been scanned. Matching is by base title text (ignoring cut-suffix differences like "Final Cut"/"Director's Cut" — the user names titles verbatim except when a box set distinguishes cuts inline), then narrowed using format/disc-count hints pulled from the UPC product text, but only when a hint actually narrows the set — an unreliable hint should never eliminate a real candidate. If exactly one candidate remains, it's offered as an automatic match; if more than one remains, the user picks from the narrowed list; if none match, it proceeds to create a new row as normal. Attaching to an existing entry only ever sets the barcode + case image plus a conservative refresh of fields that genuinely come from IMDb/OMDB (release date, genre, director, rating, IMDb page) — never packaging fields the user already entered by hand (format, disc count, disk region, franchise, genre location, etc.), and never runtime when the matched title looks like a specific cut/edition, since OMDB only has one canonical runtime per film, not one per cut.
9. Shelf-location suggestion: alphabetical order within `genre_location`, except when `genre_location` is the History Documentary bucket, which orders by `depicted_era_start` instead.
10. The scanner returns to the camera view, ready for the next disc.

Note: neither Rotten Tomatoes nor Letterboxd exposes a public API. Their scores are needed for search/sort (WEB APP DESIGN.md's Advanced Search filters) but not for identifying a disc, so fetching those can happen asynchronously after the entry is created rather than blocking the scan flow.

**HOSTING / KEEP-ALIVE**

Both Supabase projects are on the free tier, which auto-pauses a project after 7 days with no activity (confirmed by an actual pause-warning email Supabase sent for the public project in September 2026, since it's a demo dataset that doesn't get real day-to-day traffic the way the private project does from personal scanning/testing). A pause is recoverable within 90 days from the dashboard, but the goal is to just not let it happen.

Fix: scripts/src/keep-alive.ts does a trivial read (select unique_id from titles limit 1) against each project it has credentials for, and .github/workflows/keep-alive.yml runs it on a schedule (every 3 days, comfortably inside the 7-day window) via GitHub Actions - so it keeps running even if no one's local machine is on. Credentials are GitHub Actions repo secrets: SUPABASE_URL/SUPABASE_ANON_KEY for the private project, PUBLIC_SUPABASE_URL/PUBLIC_SUPABASE_ANON_KEY for the public one. Both use the anon key rather than the service-role key the other scripts in this folder need - titles' RLS already permits a public select, so there's no reason to hand a more powerful key to a scheduled CI job than the task requires. Either target is skipped rather than failed if its secrets aren't set, so this doubles as a runnable-by-hand single-project check (npm run keep-alive from the repo root) when only one side is configured locally. A failed ping exits non-zero, which shows as a red Action run and (per GitHub's default notification settings) emails the repo owner - a free early-warning signal if a project's URL/key ever goes stale, separate from the inactivity-pause problem this was built to solve.
